# Decision: Phase 0 durable execution engine: extend the current engine; no Temporal, Conductor or Pi Durable adoption

Status: proposed by the Phase 0 build (TRD-023, bead `foreman-83q8j.9.1`); not accepted until the operator reviews it. The operator may veto it in review, and no engine change is acted on before then (constitution §5: architecture changes need approval). This record decides nothing about migrating the engine: its decision is to keep it. A veto means the comparison below is re-run with the operator's choice, not that any work already built is reverted.

Evidence base: `origin/main` at `1d316d3f` (PRs #848, #850, #851, #853, #854, #855, #856, #857 merged), PRD `PRD-2026-a804d1c7` v1.1.13, TRD `TRD-2026-a804d1c7` v1.0.17 (amendment PR #858, open at the time of writing; its limitation list (i) to (xl) is reproduced below). Every `file:line` was read on disk on 2026-11-11 and every test name was grep-checked against its file on the same day; nothing was re-run for this record (see "How the results were obtained").

## Context

Phase 0 of the SunStone software factory (umbrella `PRD-2026-b7c2e941`) is a prove-and-close-gaps phase. The PRD fixes the expected outcome as "extend the current engine" and admits Temporal or Conductor only for a criterion the evidence shows cannot be closed in the current engine (PRD section 1, AC-001-2, AC-001-3). REQ-001 is this record: it maps every criterion of REQ-002 to REQ-006 (and REQ-007) to source evidence, test evidence and a pass or fail result, names each criterion that is not fully met with the engine decision that follows, and states the cost of the alternatives.

What Phase 0 built (merged PRs): PR 1 (#848, `52ead8e5`) durable phase attempts, the durable boot-cleanup budget, the run-level resume record; PR 2 (#850, `3e326778`) the five-boundary restart suite, unresolvable resume bases, cancellation across a restart; PR 3 (#851, `74f1df26`) human waits and question expiry across a restart; PR 4 (#853, `76512737`) effect keys, reconcilers, the durable-store report, the doctor section; PR 5 (#854, `a49f4d59`) task-provider claim, complete, fail and reopen keyed and reconciled; PR 6 (#855, `d3d3b6f8`) phase inputs and project-context identity recorded; PR 7 (#856, `718a2f2f`) execution profile, fail-closed network policy on the workflow door, docker proofs; PR 8 (#857, `1d316d3f`) skill preflight against pi's real loader.

## Decision

**Extend the current event-sourced engine. No adoption work is listed for Temporal, Conductor or Pi Durable.** The decision is conditional on the operator accepting the "not fully met" list below, and it is not the "every criterion passes" outcome of AC-001-3:

- 20 of the 30 acceptance criteria pass, 6 of those with a stated caveat (AC-002-1, AC-002-6, AC-002-7, AC-003-4, AC-004-3, AC-006-2).
- 10 are named below as **not fully met** and are not marked passed: AC-004-2, AC-004-5, AC-005-1, AC-005-2, AC-005-3, AC-006-1, AC-006-3, AC-006-4, AC-007-1, AC-007-2. For each, the table "Criteria not fully met" gives the engine decision: whether the gap is closable inside the current engine (and the bead that closes it) or is accepted for Phase 0.
- None of the 10 is a criterion that cannot be closed in the current engine, so AC-001-2's trigger for a Temporal or Conductor migration is not met. This is reasoned per criterion in "Criteria not fully met" and compared against the alternatives in "Alternatives considered"; it is a conclusion from that comparison, not a presupposition. The one criterion where an external engine would supply the property by construction (AC-004-5, a durable record of effect intent) is closed in the current engine by a deployment switch the doctor reports, at lower cost than any migration.
- Closing work that remains inside the current engine is not adoption work and is listed only where a bead exists: `foreman-by6nl`, `foreman-tnlqt`, `foreman-rsbx1`, `foreman-6vlx6`, `foreman-87h5g`, `foreman-t2627`, `foreman-p7asb`, `foreman-f6zmv` (all open, read with `br show` on 2026-11-11; they are in the shared bead database and not yet in the ledger file `.beads/issues.jsonl`, which is landed once at the end of the build).

### Limitations

Stated as shipped, each with its bead where one exists. Line references in this list are the TRD 1.0.17 wording where the cited line was not re-read; the ones read on 2026-11-11 are given in the criteria table above. Where the TRD's cited line has drifted since it was written, the current location is given in parentheses.

(i) The per-phase fields (`input_artifacts`, `context`, `execution_profile`, `prior_worktree_discarded`) are read from `ProjectionStore.phases_for_run/1` for every phase while the run status DTO (`RunStatus`) carries only `current_phase`, a limitation against PRD AC-005-1's "existing status surface".

(iv) REQ-004's guarantees hold only with a durable idempotency store, meaning a repo that is switched on and answering (`config :foreman_server, :jido_ecto, enabled: true`, the only switch the code reads (`FOREMAN_JIDO_ECTO_ENABLED` is only a comment at `config/prod.exs:75`), and `JIDO_CHECKPOINT_DATABASE_URL` set, both off or empty by default in production, `config/prod.exs:70-78,119-120`): with no repo `KeyStore` is ETS-only, no key survives a restart, boot sees no ambiguous key, and a crash during a push, a `gh pr create` or a provider call is invisible to recovery and the effect is repeated on resume, so PRD AC-004-5's "durably recorded" cannot hold there; and with a repo that is configured but down, `list_by_status/1` falls back to the ETS keys (`lib/foreman_server/idempotency/key_store.ex:444-457`, the TRD's `:236-250` has drifted), so boot's sweep finds none and the effect is repeated the same way; effect writes deliberately do not fail closed on a non-durable store (dev and test run on the fallback), boot reconciliation is not changed to read the store with failure reporting, REQ-004 is proven only against a store that is switched on and answering, and that store is a deployment precondition which `foreman_doctor` reports (TRD-014).

(v) PRD AC-004-2 and AC-004-3 (v1.1.11) block only a run that is not terminal when its effect verdict is reached: a terminal run, usually the run of a boot `reopen`, cannot be blocked (`run.block` is rejected, `lib/foreman_server/aggregates/run.ex:801-804` with `reject_terminal_mutation` at `:1427`, the TRD's `:766-771,1348-1349` has drifted; `run.recovery_attempt` carries the same guard at `:766`, TRD-005), so its verdict is surfaced by a warning log, the `effect_on_terminal_run` telemetry event, the key staying `ambiguous` and the `foreman_doctor` "Unresolved effect keys" section, and nothing is repeated; the verdict and reason code are not stored for a terminal run, so the doctor section shows the key, class, run id and the run's current status and an operator reads the verdict from the log (TRD-012, TRD-014, TRD-015).

(viii) An orphan run-slot entry that exhausted the boot cleanup budget (PRD AC-002-6) is recorded and skipped, never retried with a fresh budget, and is not a blocked run: it clears only when its holder or waiter leaves the stream by another route (the Dispatcher's terminal release or the 30 s backstop sweep over holders), Phase 0 builds no operator verb to re-arm it, and an exhausted waiter that no release promotes, or a holder whose release keeps failing, stays listed in `queue_status.orphan_recovery` (TRD-003); and AC-002-6's "an entry recorded at 3 failures that fails again is at 4" holds only while the entry stays in the `run_slots` stream, because a plain restart's boot scan releases a terminal-run holder successfully, which clears its count (the specified lifecycle).

(xxvi) The rule that a reopen key is never marked unresolved is a hard-coded class check in `BootReconciliation.repeatable_effect?/2` (`:1069`, `TaskProvider.repeatable?/1`), not a `Reconciler` callback, and a reopen key stays retryable while a `paused` run is blocked on its verdict.

(xxvii) `input_artifacts` records what the executor made available at phase start, not proof the phase opened it: PRD AC-005-1's "which artifacts it read" is met as "which it was given", and the code produces at most one input.

(xxviii) `PhaseContextRecorded` means built and recorded, not that the agent started (it is appended before steering is consumed, and `steer_consume_failed`, `lib/foreman_server/workflow/run_executor.ex:1948`, can still fail the launch), the identity covers the project-context text only (not the operator progress addendum, steering or provider prefix), the aggregate does not validate `input_artifacts` at `phase.start` or `phase.retry`, and a resume's `PhaseRetried` clears `:context` until the relaunch records it again (a window with no context); the docker-jobsite gap of (iii) also covers a resumed jobsite delivering different context than its start.

Limitations PR 7 found:

(xxix) Host `cleanup` is always recorded unenforced with a reason (the worktree is removed only on the executor's own finish paths, a crash mid-phase skips them and boot reclaims only a terminal run's clean worktree), and credentials are recorded unenforced on both backends, pointing at `PRD-2026-aba4b79c`.

(xxx) A docker-jobsite profile never reaches a phase entry (the docker jobsite emits no phase events, so `ExecutionProfile.resolve(:docker_jobsite, ...)`, `lib/foreman_server/jobsite/execution_profile.ex:101`, has no production caller), its filesystem reads `enforced` unless a mount is the host root `/` (a mount of a parent of the worktree still reads enforced), its mount list is supplied by the caller and not read from `lib/foreman_server/jobsite/sandboxes/docker.ex`, and its `always` cleanup mapping was not verified against the jobsite's `cleanup/3` and the boot sweep.

(xxxi) A refused RESUMED run that had already claimed leaves its provider issue `in_progress` (the refusal dispatches only `dispatch_task_execution_fail`, the provider `fail` effect is not issued; the next boot's reopen sweep reopens it) and its worktree retained (`cleanup_run_worktree` sees no `run_worktree` at kickoff), the same gap exists for the provider and model preflight refusal, and a run that already started phases when the policy changed is failed terminally at its next resume (tested only for a resumed run with no prior phases).

(xxxii) The crash test's boot sweep removes objects carrying the test event store's `foreman.owner` digest, so a concurrent run against the same test database with a live docker jobsite would be swept (`BootRecovery` could take the sweep owner from config).

(xxxiii) A project that already had a `none` or `allowlist` network policy, which the host door silently ignored, is now refused on the host door with `{:isolation_unsupported, :network, :host_workflow}`: a breaking change for operators, with the way out being the docker jobsite door or the default policy, and an unknown stored mode is refused as non-default.

(xxxiv) AC-006-3 and AC-006-4 rest on `:docker`-tagged tests run once on the author's machine (Docker Desktop for macOS, not CI): mounting the host `/` shows the VM's root there, so that mutation turns the outside-path test red only on its positive control, with a marker file beside the worktree read as the direct probe.

Limitations PR 8 found:

(xxxv) `:missing` is rarely reachable on a typical host (pi extensions or unresolvable packages make a nonexistent skill `:unverifiable`; the stock-workflow skills resolve `:available` against a real home), so the refusal of PRD AC-007-1 and AC-007-2 "at admission" applies to a provably complete lookup only (a clean pi setup, or tests with an empty home); an `:unverifiable` verdict is never silent (a warning is logged per phase and the phase's `execution_profile.skill` records it).

(xxxvi) The verdict is checkout-scoped: absence is proven against the registered project checkout's working copy, not the worktree's base-ref content, and a project-scoped find is `:unverifiable` because pi decides project trust at run time for a worktree that does not exist at admission.

(xxxvii) `:missing` is asserted against pi 1.5.0's loader only (a different pi could load more places), and pi's `trust.json` and `hosted-git-info` beyond https URLs on github.com, gitlab.com and bitbucket.org with exactly `user/repo` are not modelled (every other git form is `:unverifiable`).

(xxxviii) Conservative over-approximations only downgrade `:available` to `:unverifiable`: a plain `*` or `?` entry in settings `skills` is treated as filtering auto-discovered directories, a YAML plain scalar starting with a digit, sign or `.` makes a description unverifiable, and a `SKILL.md` ignored at a scan root short-circuits descent (pre-existing).

(xxxix) A refused run's terminal reason is the struct tuple (`{:capability_preflight_failed, [...]}`), the readable phrase (`PreflightFailure.summarize/1`) is in the log only.

(xl) An unexpected exception from `project_env/1` propagates (no catch-all rescue, AGENTS.md 5.2): the executor crashes inside kickoff before any claim and `RunSupervisor` restarts it as for any kickoff crash; boot recovery after a repeated crash was not traced and no test raises there.

## Future path (not built)

**Pi Durable** (`earendil-works/pi`, `packages/durable`, `@earendil-works/pi-durable`) is an agent-level durable harness that checkpoints each model turn and tool call. It is listed here and not as a replacement in the alternatives table, because it is session persistence for one agent conversation, not workflow, attempt, recovery-budget or external-effect reconciliation. Facts read from its README on 2026-11-11: it is a Node (npm) library, marked "**Experimental.** The API changes without notice between releases"; storage is SQLite, JSONL, IndexedDB or a Cloudflare Durable Object; a tool call's intent is committed before `execute()` runs and the tool reruns after a crash only when declared `replay: "safe"`, otherwise the model receives an `interrupted` error result; it has a `restartLimit` (default 5) and signals for waits. Why it does not replace the effect registry: its tool contract is declarative per tool, while the effect registry consults external truth (the remote branch head, `gh pr list --state all`, the provider's issue state) and covers effects the agent never performs (`AutoPR` push and PR create, provider calls in `RunExecutor`).

- **Cost of adopting it.** A sidecar and a new harness adapter (it is a Node library; Foreman's harness providers are `[:pi, :claude]`); session durability would become a pi-only capability, which would have to surface in the execution profile (TRD-018) and in provider parity for skill preflight (TRD-021, TRD-022). The seams to settle are session state against the phase attempt number, a resumed session's context against a re-provisioned worktree and a fresh project-context bundle (TRD-004, TRD-017), and tool-call idempotency inside the session against the effect intent keys.
- **Rollback.** The package is experimental and its API changes without notice between releases, so the rollback column is the risk: pinning a version and carrying a fork, or removing the sidecar and falling back to per-phase resume, which is the engine as it stands. No Phase 0 code depends on it.
- **Not built, not scheduled.** Nothing in this record asks for it. If a criterion fails and the alternatives table is used, Pi Durable gets a row there too (TRD-023).

**Closing work inside the current engine** is the bead list above, not a future platform: `foreman-by6nl` (refuse undecided keys; order the sweep before executors resume), `foreman-tnlqt` (existing-PR outcome in `AutoPR`), `foreman-rsbx1` (dashboard reset for blocked and paused runs), `foreman-6vlx6` (record the provider's actual assignee on the key), `foreman-87h5g`, `foreman-t2627`, `foreman-p7asb`, `foreman-f6zmv` (the four PR 3 review findings).
