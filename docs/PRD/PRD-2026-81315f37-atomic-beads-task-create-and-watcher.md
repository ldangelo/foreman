---

**Boundary problem.** Today, `foreman task create` lands a task in the
Foreman projection store while leaving the matching bead to be created
upstream on the next watcher tick (or never). That is a correctness gap:
two systems can disagree about what tasks exist, and the bead can be lost.

**Promise.** This slice delivers **synchronous in-process all-or-nothing
for the normal path** — the bead and the task are created together when
a request hits `task.create`. The contract is **compensating consistency,
not true atomicity**: the in-process hook guarantees no `TaskCreated`
event is emitted when `br create` fails (failure-as-error contract), and
the orphan janitor (REQ-023) absorbs the residual gap when the Actor
crashes between `br create` success and `EventStore.append_to_stream`
confirmation, or when compensation (`br close`) fails. Within the
configurable grace window the two stores converge to zero orphan backlog.

**Foreman-originated beads are tagged.** Every Beads issue this PRD creates carries `agent_context.foreman = {task_id, command_id, origin, linked_at}` so the watcher can distinguish Foreman-managed beads from operator-managed ones and so the orphan janitor never closes an issue it did not create. The linkage between Foreman task and Beads bead rides on the single `TaskCreated` event (`external_id` populated at the Actor hook), so a single append carries both signals at once; no second event is emitted for the linkage.

## 2. Background and Evidence

### 2.1 What we observed in the Foreman codebase

- **Aggregate stays pure.** `packages/foreman_server/lib/foreman_server/aggregates/task.ex` lines 163-195 — the `task.create` handler already extracts `external_id: Aggregate.get(payload, :external_id)` from the payload and embeds it in the resulting `TaskCreated.external_id`. The aggregate does no I/O. The bead-creation call MUST live outside the aggregate, in the Actor's command-dispatch path (`packages/foreman_server/lib/foreman_server/aggregate/actor.ex:156-223`, `do_dispatch/4`). The PRD does NOT modify the aggregate.
- **Actor state shape is `{module_state, version}`.** `aggregate/actor.ex:156-223` — `do_dispatch/4` invokes `aggregate.handle_command(state, payload)`, receives `{:ok, event_spec}`, and forwards to `normalize_to_event_data`. The PRD replaces this single `handle_command/2` call with a **two-stage aggregate finalization** that preserves the slice invariant ("every emitted event is owned by an aggregate's `handle_command/2`, no module fabricates events"); see the explicit contract in REQ-020 and AC-020-1. Briefly: stage 1 calls `handle_command/2` on the original (unenriched) command to validate; stage 2 calls `BeadsAdapter.create/2` only if stage 1 returned `{:ok, _}` and the project supports `:create`; stage 3 enriches the command payload with `external_id` and calls `handle_command/2` AGAIN to obtain the aggregate-emitted `TaskCreated{external_id: bead_id}` event; stage 4 normalises and appends that event unchanged. The aggregate stays pure throughout (no I/O at any stage).
- **Optimistic concurrency already retries.** `aggregate/actor.ex:248-267`, `reload_after_conflict/1` — when `EventStore.append_to_stream/3` returns `{:error, :wrong_expected_version}`, the actor reloads and re-decides. The PRD's retry-safety requirement (REQ-024) is that the SAME `command_id` MUST NOT trigger a second `br create` call on retry. The Actor already has a deterministic `event_id_for/2` (lines 226-234) keyed on `command_id`; the in-flight bead cache extends this principle.
- **`TaskCreated.external_id` is an existing optional field.** `packages/foreman_server/lib/foreman_server/events/task_created.ex` — `@enforce_keys [:task_id, :project_id, :title, :status, :task_type]`; `external_id` is an optional field (default `nil`). The bead-linkage signal rides entirely on this already-registered field — the aggregate simply populates it via the command payload when the Actor calls `handle_command/2` with an enriched payload (the two-stage finalization in REQ-020). No `EventCodec` re-registration is required because no new field or new event type is being registered; the existing `TaskCreated` event already serialises `external_id` in its payload.
- **The read projection silently drops `external_id`.** `packages/foreman_server/lib/foreman_server/projection_store.ex:772-795` — `apply_event_by_type(state, "TaskCreated", payload)` builds a task projection map; the field list omits `external_id`. A read-side query cannot discover the bead ID even when the event carries it. The PRD closes this gap (AC-025-1).
- **`BeadsAdapter` advertises 9 capabilities today.** `packages/foreman_server/lib/foreman_server/task_providers/beads_adapter.ex:26-43` — `capabilities/0` returns `supports: [:claim, :close, :reopen, :annotate, :set_priority, :set_assignee, :list_dependencies, :add_dependency, :remove_dependency]`. The PRD extends this set to include `:create`.
- **`TaskProvider` behaviour declares 11 callbacks.** `packages/foreman_server/lib/foreman_server/task_provider.ex` — `name/0`, `capabilities/0`, `available?/0`, `list_ready/2`, `get/2`, `claim/3`, `complete/3`, `fail/3`, `reopen/3`, `set_priority/3`, `add_dependency/3`. The PRD adds `create/2`, raising the total to 12. The behaviour-shape test at `packages/foreman_server/test/foreman_server/task_provider_test.exs:12` and `:24` MUST be updated (currently asserts `length(callbacks) == 11`); line 24 has a duplicate length assertion.
- **`ProviderError.context` is a closed allowlist.** `packages/foreman_server/lib/foreman_server/task_providers/provider_error.ex` — `build_context/1` raises `ArgumentError` on any key not in `[:id, :command, :exit_code, :stderr_byte_count, :sanitized?, :redacted_fields, :missing_fields, :current_assignee_present?]`. The new `br create` failure codes route through the existing factory; no new context keys are introduced.
- **`CommandGateway` operator-type allowlist is `task.update`-averse.** `packages/foreman_server/lib/foreman_server/command_gateway.ex:41` — `@allowed_operator_types ~w(project.register project.update project.archive task.create task.approve task.retry run.cancel)`. This PRD does NOT add any system-issued operator type for the linkage signal; the bead ID flows through `TaskCreated.external_id` and the linkage is captured by the aggregate's own event. `task.update` remains absent from `@allowed_operator_types` (it would be the wrong primitive — generic updates are rejected for typed-event reasons per the slice invariant).
- **`EventCodec` strict mode rejects unknown typed events.** `packages/foreman_server/lib/foreman_server/event_codec.ex:60-92` — `@registry` maps event_type strings to modules. Lines 98+ — `@enforce_keys_registry` is the parallel validation map. A new typed event MUST be in both, or `EventCodec.decode!/2` raises `ArgumentError`. This PRD introduces NO new typed events — the linkage signal rides on the existing `TaskCreated` event so the codec registry is not extended; this is a deliberate simplification that flows from the slice invariant (every emitted event is owned by an aggregate's `handle_command/2`; the Actor must not manufacture a second event for the linkage).
- **Two opt-in supervisor flags already exist for similar slices.** `packages/foreman_server/lib/foreman_server/application.ex:114-132` — `maybe_project_provider_projector_child/0` and `maybe_json_schema_cache_child/0` are opt-in via `:start_project_provider_projector?` and `:start_json_schema_cache?` (both default `false` in `config/test.exs`, true elsewhere). The PRD introduces two sibling flags in the same style: `:start_beads_watcher?` and `:start_beads_orphan_janitor?`.

### 2.2 What we observed in Beads Rust (`br`)

All facts below were obtained by running `br --version` (0.2.19) against the local `.beads/beads.db` (issue prefix `foreman`).

- **`br create --json` returns the bead verbatim.** Output shape: `{id, title, description, status, priority, issue_type, created_at, created_by, updated_at, source_repo, source_repo_path, compaction_level, original_size}`. No `dependencies`/`dependents` (default `[]`). The `id` field is the canonical bead ID (e.g. `foreman-abc`).
- **`br create` flags.** `--title`, `-t --type`, `-p --priority`, `-d --description`, `-a --assignee`, `-l --labels`, `--agent-context <JSON>`, `--db`, `--json`. **No `--id`** — IDs are auto-generated by Beads. Attempting to pass `--id` returns a validation error (code `VALIDATION_FAILED` per the `br` envelope schema).
- **`br create --agent-context` accepts inline JSON.** The flag accepts a JSON string that Beads persists on the issue and surfaces in the JSONL file under `agent_context`. This is the per-bead tagging channel the PRD uses to mark Foreman-originated issues. The `foreman` key holds `{task_id, command_id, origin: "foreman", linked_at: <ISO8601>}`.
- **`br close` is reversible-ish.** It transitions the issue to `closed`. For Foreman's compensating-close path (AC-020-3) this is the right primitive: the bead has no Foreman work binding it, and a fresh `task.create` retry will land a new bead.
- **`br list --json --label <L>` filters by label.** The watcher uses this to enumerate tagged beads without parsing the JSONL itself for shape validation, falling back to the JSONL for fields `br list` omits. (JSONL is the source of truth for the synchronous create's compensating-consistency contract; `br list` is an operator-surfacing query.)

### 2.3 Consequence for the design

The work splits into a synchronously-paired Actor hook (writes) and an asynchronously-tail pair (reads + cleanup). The writes path is correctness-critical: a `task.create` that loses the linkage is a data-integrity bug. The reads path is convenience: a watcher that misses an event or a janitor that closes an issue prematurely is a recovery problem, not a correctness one (the orphan janitor's job is to keep the two stores eventually consistent within a bounded grace window). The compensation path (`br close` on append failure) covers the most common write-side failure ordering. The remainder — Foreman crashed between bead creation and append, Foreman crashed between append and link-emit — falls to the orphan janitor with a deterministic close decision.

## 4. Requirements

### 4a. Write-Side (synchronous, Actor-mediated)

### REQ-020: Must | High | Two-stage aggregate finalization: synchronous `task.create` bead creation in the Actor hook (compensating consistency — not true atomicity)
`ForemanServer.Aggregate.Actor.do_dispatch/4` MUST run a **two-stage aggregate finalization** for every `task.create` command whose target project has Beads-management enabled. The Actor validates the original (unenriched) command through `aggregate.handle_command/2` first, then performs `BeadsAdapter.create/2` I/O only if validation succeeds and the project supports `:create`, then re-runs `aggregate.handle_command/2` with the bead ID injected into the command payload. The aggregate stays pure throughout — it NEVER does I/O; the Actor NEVER fabricates events or merges fields into event specs. The contract is **compensating consistency, not true atomicity**: the in-process hook delivers synchronous all-or-nothing for the normal path (AC-020-1 happy path; AC-020-5 failure path — no `TaskCreated` event is emitted when `br create` fails), and the orphan janitor (REQ-023) absorbs the residual escape paths (Actor crash between `br create` success and append confirmation, or compensation `br close` failure) within the configurable grace window (default 300s, override via `:beads_orphan_grace_ms`).

**Two-stage contract.** Stage 1 (validate, pure): `aggregate.handle_command(state, original_cmd)` returns `{:error, _}` or `{:ok, %{event_type: "TaskCreated", payload: %{...external_id: nil...}}}` (a single event-spec map — the actual `ForemanServer.Aggregates.Task.handle_command/2` contract is `{:ok, %{stream_id:, event_type:, payload: %{...}}}`, NOT a list of typed structs) — no I/O is performed by the aggregate. Stage 2 (Beads I/O): if stage 1 returned `{:ok, _}` AND the project has Beads-management enabled with `:create` in `capabilities.supports` AND `cmd.payload.external_id` is `nil` (atom key per `CommandGateway`'s payload-key convention), the Actor invokes `BeadsAdapter.create/2`. On `{:error, %ProviderError{}}` the Actor returns the error from `do_dispatch/4` without `normalize_to_event_data` and without `EventStore.append_to_stream` — no event is emitted. Stage 3 (re-decide, pure): the Actor enriches the command payload with `:external_id = bead_id` (an existing optional field on `TaskCreated`) and calls `aggregate.handle_command/2` again, which deterministically produces `event_spec.payload.external_id == bead_id`. The aggregate emits the enriched event; the Actor NEVER mutates `event_spec` after `handle_command/2` returns.

- AC-020-1: Given a `task.create` command is dispatched for a project whose `task_provider` capability list includes `:create` and whose payload `external_id` is `nil`, when the Actor enters `do_dispatch/4` and stage 1 returns `{:ok, %{event_type: "TaskCreated", payload: %{...external_id: nil...}}}`, then the Actor invokes `ForemanServer.TaskProvider.Registry.route(:create, %{project_id: id})` to resolve the provider, calls `provider.create(project_id, %{title, description, priority, task_type, dedupe_key})` with the `command_id` from the command envelope as the correlation handle, and on `{:ok, %TaskProvider.Issue{id: bead_id}}` stage 3 re-runs `aggregate.handle_command(state, %{original_cmd | payload: Map.put(original_cmd.payload, :external_id, bead_id)})` which deterministically returns `{:ok, %{event_type: "TaskCreated", payload: %{...external_id: bead_id...}}}`. The aggregate emitted the event with `external_id` populated; the Actor never merged or fabricated the field. **Happy-path verification only** — the `TaskProvider.Issue{id}` round-trips through stage-3 re-decide → aggregate-emitted `TaskCreated.payload.external_id == bead_id` → stage-4 normalize → stage-5 append.
- AC-020-2: Given `br create` succeeds and the resulting `TaskCreated` event is appended to the event store with `external_id: "foreman-abc"`, when the projection rebuilds, then the task map returned by `ProjectionStore.get_task/2` includes `external_id: "foreman-abc"` and `GET /api/tasks/:id` returns the bead ID in the response body — `external_id` round-trips through the event envelope to the read model without manual intervention.
- AC-020-3: Given `br create` succeeded and the resulting bead ID is stored in `state.in_flight_beads[command_id]`, when the subsequent `EventStore.append_to_stream/3` returns `{:error, :wrong_expected_version}`, then the Actor's bounded-retry path consults `state.in_flight_beads[command_id]` first (REQ-024 / AC-024-1). On **cache hit** (the normal case — the Actor survives the failed append), the Actor reloads state via `Aggregate.load/2`, re-runs `aggregate.handle_command/2` with the cached `external_id` already present in the payload (the AC-020-6 stage-3 path, NOT a fresh `BeadsAdapter.create/2` call), and retries the append with the new `expected_stream_version`. No `br close` and no cache clear happens on a retry attempt — the bead ID is the same one created during the original stage 2, and the aggregate deterministically re-emits `TaskCreated{external_id: bead_id}`. Compensation (`BeadsAdapter.complete(project_id, bead_id, %{transition_comment: "foreman-compensation:append-conflict-retry-exhausted" or "…re-decision-rejected"})` + cache clear + error surfaced to caller) triggers ONLY on (a) **bounded-retry exhaustion** — the retry counter reaches `@max_conflict_retries` and the final attempt also failed with `:wrong_expected_version`, or (b) **post-reload re-decision rejection** — the reloaded state makes the original command invalid (e.g. `handle_command/2` returns `{:error, :phase_terminal}` or another domain rejection). On compensation failure the Actor emits `[:foreman_server, :task_provider, :beads, :create, :compensate_failure]` and the orphan janitor (REQ-023) takes over on its next grace-window scan. The **CLOSE-ONLY-ONCE** guarantee holds: `in_flight_beads[command_id]` is consulted before any close, and once cleared no subsequent close is issued for the same logical command — the bead (if still on disk) becomes orphan territory and janitor-handled. Cache miss on retry is impossible in a stable Actor (cache is process-local) — only an Actor crash produces a fresh dispatch, which follows the AC-020-1 path with empty cache.
- AC-020-4: Given the target project has no `task_provider` registered, or has one registered without `:create` in `supports`, when a `task.create` command is dispatched, then the Actor skips the `BeadsAdapter.create/2` call entirely (stage 2 is a no-op) and the original stage-1 event spec flows through to `normalize_to_event_data` with `external_id: nil` (the legacy behaviour) — the synchronous hook is a no-op for non-Beads projects. The gate is `capabilities.supports` membership, not a separate flag.
- AC-020-5: Given the synchronous hook is about to call `BeadsAdapter.create/2` for a `task.create` command on a Beads-enabled project, when the adapter returns `{:error, %ProviderError{code: code, retryable?: retryable, ...}}` (any of `INVALID_TITLE`, `INVALID_PRIORITY`, `INVALID_ISSUE_TYPE`, `DUPLICATE_TASK_ID`, `CREATE_FAILED` per REQ-026 — or any future `br create` failure mode that the existing CodeMap factory recognises), then the Actor returns `{:error, %ProviderError{}}` from `do_dispatch/4` **without** invoking stage 3 (`handle_command/2` re-decide) **without** invoking `normalize_to_event_data` and **without** calling `EventStore.append_to_stream` — NO `TaskCreated` event is emitted, NO Foreman task is created, the operator's `foreman task create` invocation fails with the provider error code in the response body, and the `in_flight_beads` cache is NOT populated for this `command_id`. Telemetry `[:foreman_server, :task_provider, :beads, :create, :failure]` is emitted carrying `command_id`, `code`, `retryable?`, the proposal `task_id`, and `project_id`. The `retryable?` flag is surfaced to the caller (NOT auto-reissued) so the operator — or upstream orchestration layer — can decide whether to retry; non-retryable codes (`INVALID_TITLE`, `INVALID_PRIORITY`, `INVALID_ISSUE_TYPE`, `DUPLICATE_TASK_ID`) propagate to the operator verbatim.
- AC-020-6: **NEW (watcher-import branch).** Given a `task.create` command reaches the Actor with `cmd.payload.external_id` pre-populated (the JSONL watcher in REQ-022 synthesises this envelope shape and routes via `dispatch_system/2`, which the CommandGateway boundary invariant — AC-020-7 — allows), when stage 1 validates, the aggregate's `Aggregate.get(payload, :external_id)` mirrors the value into the stage-1 event-spec payload — so stage 1 returns `{:ok, %{event_type: "TaskCreated", payload: %{...external_id: bead_id...}}}` with `external_id` ALREADY populated. The Actor detects this at the outer pattern match (`when not is_nil(stage1_payload.external_id)` clause) and SKIPS the `BeadsAdapter.create/2` call entirely (stage 2 is a no-op for pre-populated `external_id`) — the existing stage-1 event_spec is the final event. NO `br create` is issued (the bead already exists in `.beads/issues.jsonl`); the Foreman task is created against the existing bead ID. Telemetry: emit `[:foreman_server, :task_provider, :beads, :create, :skipped_watcher_import]` with `command_id`, `bead_id`, `task_id`, `project_id` so operators can verify the path is exercised. The watcher-import branch uses the SAME single-event-linkage path as the operator-driven case — `TaskCreated.payload.external_id == bead_id` is the linkage; no second event is emitted.
- AC-020-7: **NEW (CommandGateway boundary invariant).** `ForemanServer.CommandGateway.dispatch_operator/2` MUST reject `task.create` with non-nil `envelope.payload.external_id` at the existing envelope allowlist guard — the check is `get_in(envelope, [:payload, :external_id]) != nil` (atom keys per `CommandGateway`'s payload-key convention) and the rejection returns `{:error, :external_id_not_allowed_via_operator}`. `dispatch_system/2` is unchanged and remains the trusted path for the watcher-import branch (AC-020-6) and any future system-issued dispatch that needs to supply a pre-existing `external_id`. The boundary invariant is enforced once at the CommandGateway allowlist; the Actor does NOT perform its own origin check (avoiding redundant enforcement). This invariant prevents operator-issued payloads from bypassing `BeadsAdapter.create/2` by supplying a fabricated `external_id` — only system dispatch can carry the watcher-import branch payload shape.

### REQ-021: Must | High | Foreman-originated beads carry an `agent_context` tag
Every bead the synchronous hook creates MUST carry `agent_context.foreman` so the watcher (REQ-022), orphan janitor (REQ-023), and operator `foreman doctor` output can distinguish Foreman-managed beads from operator-managed ones. The tag is the only signal that authorises any cleanup logic to act on a bead.

- AC-021-1: Given the synchronous hook invokes `br create` for a Foreman task, when constructing the argv, then the adapter appends `--agent-context '{"foreman":{"task_id":"<task_id>","command_id":"<command_id>","origin":"foreman","linked_at":"<iso8601-utc>"}}'` (with the four fields escaped per `BeadsAdapter.scrub_argv/1` per `PRD-2026-48f7b420` REQ-019); the bead persists this metadata and surfaces it in subsequent `br show` and JSONL output.
- AC-021-2: Given a bead carries `agent_context.foreman.command_id` matching the dispatching `command_id`, when the orphan janitor (REQ-023) or operator `foreman doctor` inspects the bead, then the read path recognises it as Foreman-managed and is authorised to close it on the recovery criteria in REQ-023; foreman-untagged beads are NEVER touched by the orphan janitor.
- AC-021-3: Given `BeadsAdapter.create/2` constructs the `--agent-context` payload, when the JSON encodes, then the four fields `task_id`, `command_id`, `origin`, `linked_at` are always present; `origin` is the literal string `"foreman"`; `linked_at` is ISO8601 UTC; `task_id` and `command_id` are the exact strings from the dispatching command envelope (no remapping, no truncation).

### REQ-022: Must | High | JSONL watcher for bi-directional sync
A supervised process (`ForemanServer.TaskProviders.BeadsWatcher`) MUST tail `.beads/issues.jsonl` (path resolved via `br where --db <db> --json` for each registered project), parse entries, and for every NEW entry whose `agent_context.foreman` is absent AND whose title matches a Foreman-issued intent (i.e. the bead was created by an operator OUTSIDE Foreman but appears intended for Foreman), emit a `task.create` command routed through `ForemanServer.CommandGateway.dispatch_system/2` (the trusted system path) with `external_id` pre-populated to the bead's ID so the Actor's watcher-import branch (AC-020-6) detects the existing linkage and skips `BeadsAdapter.create/2`. The watcher is opt-in via `:start_beads_watcher?` config flag (default `false`).

- AC-022-1: Given a project is registered with `task_provider: %{provider: BeadsAdapter, config: %{database_path: "<abs>"}}` and `:start_beads_watcher?` is `true`, when the supervisor boots, then `ForemanServer.TaskProviders.BeadsWatcher` starts one tail process per registered project. **Boot phase (one-shot):** the watcher reads the entire JSONL from offset 0 (full replay). For each line it suppresses foreman-tagged beads (AC-022-3), checks `ProjectionStore` for an existing task with `external_id == bead.id` and skips if already imported (AC-022-2 dedupe; emits `[:watcher, :reconciled]`), and only dispatches a synthetic `task.create` for NEW operator-originated beads (AC-022-2; emits `[:watcher, :imported]`). **Tail phase (continuous, after boot):** the watcher captures the boot-completion cursor and enters tail mode using `:file.open/2` + read-until-EOF + `Process.send_after(self(), :read_more, interval_ms)` polling (interval default 2s, override via `:beads_watcher_poll_ms`). **Boot cursor semantics (3-way cursor priority):** on completion of the boot replay, `read_offset` is set to the byte position of the START of the FIRST LINE NOT TERMINALLY DISPATCHED — (a) the start byte of the first transient complete-line if the loop stopped at a transient; (b) the start byte of any trailing fragment if the file ends on an unterminated JSONL line; (c) the file size (EOF) if the file ends on a terminator. `partial_line` is the bytes of the FIRST LINE NOT TERMINALLY DISPATCHED — transient-line bytes from the split, trailing fragment bytes from `last_segment`, or `""` respectively (observability only, NOT required for correctness). This preserves partial trailing bytes AND queued lines behind a transient across the boot→tail-mode transition. **Tail offset advance rule (in-memory only):** the watcher's `read_offset` advances to the post-dispatch byte position **only after** the synthetic `task.create` dispatch reaches a **terminal outcome**. The terminal set is the aggregate's `task.create` domain rejection set as defined in `packages/foreman_server/lib/foreman_server/aggregates/task.ex` (`handle_command` head for `"task.create"`): `{:already_exists, :task, task_id}` (rare race; the dedupe missed but the task already exists), `{:invalid_task_status, status}` (defensive), `{:project_archived, project_id}` (project was archived mid-watch), `:project_id_required` (defensive — watcher always carries `project_id`). **Any other `{:error, _}`** returned by `CommandGateway.dispatch_system/2` — including `ProviderError{retryable?: true}` (a transient `BeadsRunner` blip, `BR_DATABASE_LOCKED`, etc.) and crash-level signals (process death, network blip, `:wrong_expected_version` bubbling past the Actor's bounded retry) — is classified as **transient**: the watcher retries with the **same deterministic `command_id`** derived from `{project_id, bead_id}` (AC-022-2) and does NOT advance `read_offset` across the retries. The terminal/transient classification mirrors the existing `ProviderError.retryable?` convention from `BeadsAdapter.CodeMap` and the `project_error_metadata/1` convention in `CommandGateway`, where the keyword `retryable: false` is the discriminator; the watcher's terminal set is the explicit aggregate domain-rejection list because the watcher-import branch does NOT route through `BeadsAdapter.create/2` (so `ProviderError` is not produced) and the only terminal errors are the aggregate's own rejections. **Trailing-line buffer (3-way cursor priority + Option A):** `read_offset` is the byte position of the START of the FIRST LINE NOT TERMINALLY DISPATCHED — (a) the start byte of the first transient complete-line if the loop stopped at a transient; (b) the start byte of any trailing fragment if the file ends on an unterminated JSONL line; (c) the file size (EOF) if the file ends on a terminator. `partial_line` is the bytes of the FIRST LINE NOT TERMINALLY DISPATCHED — transient-line bytes from the split, trailing fragment bytes from `last_segment`, or `""` respectively (observability only, NOT required for correctness on the next poll). On every poll: (1) read from `read_offset` to EOF via `:file.read(file_handle, eof - read_offset)` — do NOT prepend `partial_line` (the transient-line or fragment at the seat, if any, is part of the read result); (2) split the bytes on `\n`; (3) process complete lines sequentially in order, stopping at the first transient dispatch; (4) on a terminal dispatch, advance `read_offset` past `byte_size(line) + 1` (the line and its terminator); (5) on a transient dispatch, HOLD `read_offset` at the transient-line start (NOT advance to the next line's start) and stop the loop — queued lines behind the transient are NOT skipped; the next poll re-reads the transient complete-line at `read_offset` and dispatches with the same deterministic `command_id`. A write that straddles a poll boundary is never dropped or double-counted, and a transient dispatch never skips queued lines: the transient complete-line (or trailing fragment) is held at `read_offset` until a terminal dispatch, and the next poll re-reads the held line(s) plus any newly appended bytes — no prepending, no duplication, no loss, no skipping. No durable offset store is required — the boot-phase replay combined with `ProjectionStore` dedupe (AC-022-2) is the cross-restart safety net; operator beads that arrived during downtime are recovered on the next boot's replay. **Telemetry:** `[:watcher, :replay_started]` on boot, `[:watcher, :replay_completed]` once replay finishes (carries `lines_processed`, `lines_imported`, `lines_suppressed`, `lines_reconciled`), `[:watcher, :imported]` for each new dispatch, `[:watcher, :reconciled]` for AC-022-2 dedupe hits, `[:watcher, :skipped]` for AC-022-3 suppression.
- AC-022-2: Given the watcher reads a new JSONL line for a bead that has NO `agent_context.foreman` tag, when it parses the entry, then it checks against the latest `TaskCreated` projection (via `ProjectionStore`): if a Foreman task already exists with the same bead ID in its `external_id`, the entry is a no-op (already imported). Otherwise, the watcher invokes `ForemanServer.CommandGateway.dispatch_system/2` with a synthetic command envelope whose `command_id`, `aggregate_id`, and payload `task_id` are **all derived deterministically from `{project_id, bead_id}`** (e.g. `task_id = "beads:" <> project_id <> ":" <> bead_id`, `aggregate_id = "task:" <> task_id`, `command_id = "beads-cmd:" <> project_id <> ":" <> bead_id`) — the payload also carries `{external_id: <bead_id>, title: <bead.title>, description: <bead.description>, priority: <bead.priority>, task_type: <bead.issue_type>, project_id: <project_id>}`. Determinism is mandatory: Actor dedup indexes `event_id` by `command_id` within `aggregate_id` (per `command_gateway.ex:48,70-73` and the slice invariant), so a non-deterministic `command_id` or `aggregate_id` would let a retry that arrives after a successful-but-acked-as-failed first dispatch create a duplicate `TaskCreated`. **`dispatch_operator/2` is REJECTED for this envelope** because the watcher's payload carries non-nil `external_id`; this is the AC-020-7 boundary invariant at work — only system dispatch can supply a pre-existing `external_id` to the Actor.
- AC-022-3: Given the watcher reads a new JSONL line for a bead that DOES have `agent_context.foreman` (Foreman-originated), when it parses the entry, then the entry is suppressed — the watcher does NOT re-issue a `task.create` (the Foreman task already exists by definition). The check is `Map.has_key?(parsed["agent_context"] || %{}, "foreman")`. The watcher emits `[:foreman_server, :task_provider, :beads, :watcher, :skipped]` with the bead ID for observability.
- AC-022-4: Given `:start_beads_watcher?` is `false`, when the supervisor boots, then `BeadsWatcher` is NOT added to the supervision tree and no tail processes exist — there is no sync direction from Beads → Foreman. Per-AC opt-in matches the `JsonSchemaCache` precedent (`config :foreman_server, :start_json_schema_cache?, false` in `config/test.exs`).

### REQ-023: Must | High | Orphan janitor closes Foreman's stranded beads
A supervised process (`ForemanServer.TaskProviders.BeadsOrphanJanitor`) MUST periodically scan the JSONL for beads tagged with `agent_context.foreman` whose `linked_at` is older than the configured grace window (default 300s, override via `:beads_orphan_grace_ms`), and verify against `ProjectionStore` that the corresponding Foreman task exists and is in a non-orphaned state. Orphan conditions: (a) bead is foreman-tagged but no Foreman task with that `external_id` exists; (b) bead is foreman-tagged and a Foreman task exists but the task is `closed`/`failed` (the Foreman-side story is done but the bead survived). For case (a) the bead is closed via `BeadsAdapter.complete/3` with transition-comment `"foreman-orphan:no-task"`. For case (b) the bead is closed with `"foreman-orphan:terminal-task"`. Untagged beads are NEVER touched.

- AC-023-1: Given `:start_beads_orphan_janitor?` is `true` and a project is registered with Beads-management, when the supervisor boots, then `BeadsOrphanJanitor` starts one scanner process per registered project. The first run happens after the grace window to avoid racing the synchronous hook on first boot (the synchronous hook has up to 30s `br create` latency plus append latency; the grace window absorbs that). Subsequent runs are bounded by `:beads_orphan_scan_interval_ms` (default 60s).
- AC-023-2: Given the janitor finds a foreman-tagged bead whose `linked_at` is older than the grace window and no Foreman task with `external_id == bead.id` exists in the projection, when it processes the orphan, then it calls `BeadsAdapter.complete(project_id, bead_id, %{transition_comment: "foreman-orphan:no-task"})` and emits `[:foreman_server, :task_provider, :beads, :orphan, :janitor, :closed]` carrying `bead_id`, `project_id`, and the elapsed milliseconds since `linked_at`.
- AC-023-3: Given the janitor finds a foreman-tagged bead whose linked Foreman task is `closed` or `failed`, when it processes the orphan, then it calls `BeadsAdapter.complete(project_id, bead_id, %{transition_comment: "foreman-orphan:terminal-task"})` and emits `[:foreman_server, :task_provider, :beads, :orphan, :janitor, :closed]` with the same metadata plus the `task_id` and `task_status`.
- AC-023-4: Given the janitor finds a bead that is NOT foreman-tagged (no `agent_context.foreman`), when it inspects the bead, then the entry is skipped regardless of the corresponding task's state — the janitor NEVER closes an issue it did not create. The check is `Map.has_key?(parsed["agent_context"] || %{}, "foreman")`. The skip emits `[:foreman_server, :task_provider, :beads, :orphan, :janitor, :retained]` for observability so operators can see that the entry was found-but-skipped.
### REQ-024: Must | High | Actor hook guard via `command_id`-keyed in-flight bead cache
The Actor MUST maintain an `in_flight_beads: %{command_id => bead_handle}` field on the state map, consulted BEFORE any `BeadsAdapter.create/2` call. The cache prevents two `br create` invocations for the same logical command (initial dispatch + reload_after_conflict retry) and lets the Actor distinguish "bead should exist for this command but doesn't" from "bead genuinely needs to be created" without re-issuing the `br create` when the bead is already on disk.

- AC-024-1: Given the Actor's `do_dispatch/4` is about to invoke `provider.create/2`, when it consults `state.in_flight_beads[command_id]`, then if a `bead_handle` is present (from the initial attempt or a previous retry) the Actor skips the `br create` call and reuses the cached bead ID for stage-3 re-decide (stage 2 is skipped on cache hit). If absent, the Actor issues the `br create` call as in AC-020-1 and stores the returned `bead_handle` in `state.in_flight_beads` under `command_id` before continuing.
- AC-024-2: Given the event has been successfully appended (terminal outcome: append confirmation returns `{:append_ok, count}`), when the Actor reaches the terminal branch, then it removes the `command_id` entry from `in_flight_beads`. The cache is also cleared on the rare **compensation path** (terminal retry exhaustion or post-reload re-decision rejection — see AC-020-3) AFTER the `br close` completes, so a subsequent retry observes the post-compensation state without recursing into a second `br close`. The cache is NEVER cleared between append attempts — only on terminal success or terminal compensation, never on transient `:wrong_expected_version`.
- AC-024-3: Given the Actor crashes and is restarted by its supervisor (`restart: :permanent`), when the fresh actor runs `init/1` and replays the event stream via `Aggregate.load/2`, then the `in_flight_beads` map is empty — the cache is process-local state and does NOT survive a crash. The replay commits the append outcome; if the append had succeeded the bead ID is now in the event and the next command proceeds normally; if the append had not succeeded no bead ID was ever published and the orphan janitor (REQ-023) handles the strander on its grace-window check.
- AC-024-4: Given two concurrent `task.create` commands for DIFFERENT `command_id`s reach the Actor within the same `do_dispatch` window, when both attempt `provider.create/2`, then each carries its own cache entry; the cache is keyed by `command_id` and the two paths do not collide on the bead ID lookup. There is no shared cross-command state; the cache is a `:map` not a single slot.

### REQ-026: Must | Medium | `br create` failure modes mapped in `BeadsAdapter.CodeMap`

- AC-026-5: Given `br create` fails for any other reason (signal, timeout, generic envelope, unexpected exit code) that does not match one of the four specific rows, when the adapter processes the error, then `CodeMap`'s `CREATE_FAILED` fallback row fires with `retryable?: true` (the failure may be transient). The fallback row follows the unknown-code policy from PRD-2026-48f7b420 REQ-008-2: `retryable?` is propagated from `br.retryable`.

## 7. Risks and Open Questions

### Risks
1. **Synchronous `br create` latency.** Each `task.create` now incurs a `br` subprocess round-trip (spawn + argv parse + JSONL append) inside the Actor hook. The synchronous hook is bounded by the per-call timeout from PRD-2026-48f7b420 REQ-009 (30s default). **Mitigation:** AC-020-3 compensation path handles append-conflict failures; REQ-023 janitor handles cron-drop cases. The latency is on the create path only (read paths — `list_ready`, `get` — are unchanged).
2. **Actor crash between bead creation and append.** If the Actor crashes after `br create` returns success but before `EventStore.append_to_stream` confirms, the bead is on disk in Beads but no Foreman task exists. **Mitigation:** REQ-023 orphan janitor picks up the bead on its grace-window scan (configurable, default 300s — covers normal `br create` latency + append latency + restart time). AC-024-3 makes the in-flight cache process-local so it does not survive the crash; the janitor is the recovery path.
3. **Watcher-storm scenario (boot replay).** On every boot the watcher reads the entire JSONL from offset 0 (full replay per AC-022-1). For a JSONL with N existing entries, replay is O(N) reads where each line takes one of three paths: foreman-tagged → skip (cheap), already-imported → no-op ProjectionStore check (cheap), operator-originated → dispatch. **Mitigation:** AC-022-2 dedupe makes the steady-state replay cost ~1 read + 1 short ProjectionStore lookup per line (no event-store appends for already-imported beads). The orphan janitor (REQ-023) absorbs any foreman-tagged residual the replay missed. Telemetry `[:watcher, :replay_started]` / `[:watcher, :replay_completed]` carries `lines_processed` / `lines_imported` / `lines_suppressed` / `lines_reconciled` so operators can size the storm. The replay is bounded by `lines_processed * (read + parse + dedupe_lookup)`; a future ops decision (out of scope here) is to add a JSONL compaction step or a streaming FSEvents watcher if N grows past operator tolerance.
4. **Tag-spoofing risk.** A Beads CLI operator could theoretically write `agent_context.foreman` themselves on a bead that Foreman did not create, fooling the watcher into suppressing it. **Mitigation:** the orphan janitor (REQ-023) is the safety valve — even a spoofed-tagged bead is closed only if no corresponding Foreman task exists with `external_id == bead.id` after the grace window. The Foreman-origination signal is "linked_at + command_id from THIS command" — the Actor captures `command_id` from the dispatching envelope and uses it both in the tag AND as the in-flight cache key (AC-024-1), so a spoofed tag without a matching `command_id` audit trail is detectable. The detection path is `[:foreman_server, :task_provider, :beads, :create, :command_id_mi

### Open Questions
None — all 3 ambiguity markers are resolved (see §5). The remaining items below are intentional v1 out-of-scope gaps.

### Known out-of-scope gaps (not blocking v1)
1. **No streaming watcher upgrade.** REQ-022 polls the JSONL on a 2s tick. A `:file.inotify` / FSEvents-based tail would reduce steady-state latency but is not portable and adds a dep. Deferred.
2. **No multi-project scan optimisation.** The orphan janitor (REQ-023) and watcher (REQ-022) iterate registered projects independently. A shared scanner with one tail per `.beads/` directory and per-project routing would reduce resource usage on N-project deployments. Deferred.
3. **No `foreman doctor` integration for orphan backlog.** Operators can see the recent telemetry (`[:foreman_server, :task_provider, :beads, :orphan, :janitor, :closed]`) in `foreman doctor task_provider`, but a stack-rank of "oldest orphan" is a v2 enhancement. Deferred.
4. **No interactive UI for orphan conflict resolution.** When the janitor finds a bead whose linked task is in a state the operator wants to preserve (e.g. a manually-marked `closed` task the operator does not want linked to a closed bead), the janitor closes the bead automatically. A future PRD will add an `OrphanHoldQueue` for operator review. Deferred.
5. **No integration with `foreman task update` flows.** The PRD does not add `external_id` mutation paths through the operator surface; a future PRD will reconcile task-title changes, priority changes, and dependency adds against Beads. The `BeadsAdapter.create/2` callback does not extend to those flows.

## 8. Self-Critique

1. **Synchronous hook is a single point of latency.** Every `task.create` now waits on `br create`. If `br` is misbehaving, every create hangs for the full timeout. **Mitigation documented:** AC-020-3 handles append-conflict; REQ-023 janitor handles cron-drop; PRD-2026-48f7b420 REQ-009-2 enforces SIGTERM-then-SIGKILL on the subprocess layer. [No REQ added — coverage is sufficient.]
2. **The two supervisor flags (`start_beads_watcher?` and `start_beads_orphan_janitor?`) default to `false`.** A first-deploy environment that wants the watcher but not the janitor (or vice versa) gets mismatched behaviour. **Suggested resolution:** the four combinations are observable in `foreman doctor` output (each flag's state appears with a green check or red minus); operators are expected to opt into both for production but the flags exist for staged rollouts. [No REQ added — operator decision.]
3. **`agent_context.foreman.command_id` lives in the bead's metadata, not the operational audit log.** A future PRD could expose a `foreman bead audit` CLI surface to look up bead ID → task ID → run ID → command_id. [Out-of-scope in v1; user-facing diagnosis surfaces can read telemetry events instead.]
4. **The orphan janitor closes via `BeadsAdapter.complete/3` with deterministic transition-comments.** A future Beads release could add a policy that rejects the deterministic default comment. **Suggested resolution:** PRD-2026-48f7b420 REQ-015-3 / AC-015-3 already fabricates a deterministic default `foreman-run:<run_id>:<artifact_path>` for the post-execution path; the orphan janitor uses the same pattern with `foreman-orphan:<reason>` keys. If a future policy rejects these, the entire framework's comment-fabrication falls; the orphan janitor's specific comments are a subset. [Covered by inherited PRD-2026-48f7b420 REQ-015; no additional REQ needed.]
5. **Watcher-imported tasks already carry the bead ID at create time.** A `task.create` issued by the watcher (AC-022-2) carries `external_id: bead.id` in its payload — the bead is the source, the Foreman task is the destination, and the linkage is the link. The watcher routes through `CommandGateway.dispatch_system/2` (the trusted system path; AC-020-6); `dispatch_operator/2` rejects the same payload shape at the allowlist guard (AC-020-7) so an operator cannot fabricate a `task.create` that bypasses bead creation by adding an `external_id`. **Suggested resolution:** the Actor's two-stage finalization detects `payload["external_id"] != nil` after stage-1 validation, SKIPS the `BeadsAdapter.create/2` call (no `br create`), and re-runs stage-3 `handle_command/2` with the enriched cmd; the aggregate emits `TaskCreated{external_id: bead_id}` unchanged. The trust invariant is enforced once at the CommandGateway boundary — the Actor does not need its own origin check. [REQ-020 AC-020-6 captures this as a standalone AC; AC-020-7 captures the boundary invariant.]

### 1.0.5 — 2026-08-10 (3-way cursor priority for boot + tail-mode read)

- **Advisory #22 (blocker) — single-cursor invariant.** The earlier trailing-line buffer design (`partial_line` prepended on next poll, `read_offset` advanced past fragment bytes) carries a subtle transient-dispatch duplication bug at the exact poll boundary where a complete line spans a fragment + new bytes AND the dispatch is transient: the next poll re-reads the fragment bytes from the advanced `read_offset` while `partial_line` is empty, so the fragment is dropped on the next transient retry (or duplicated if the next poll also reads past the line break). The 1.0.5 cascade replaces the trailing-line buffer with a single-cursor invariant under a 3-way cursor priority (Option A): `read_offset` is the byte position of the START of the FIRST LINE NOT TERMINALLY DISPATCHED — (a) the start byte of the first transient complete-line if the loop stopped at a transient; (b) the start byte of any trailing fragment if the file ends on an unterminated JSONL line; (c) the file size (EOF) if the file ends on a terminator. `partial_line` is the bytes of the FIRST LINE NOT TERMINALLY DISPATCHED — transient-line bytes from the split, trailing fragment bytes from `last_segment`, or `""` respectively (observability only, NOT required for correctness). Every poll reads from `read_offset` to EOF (no prepending); on a terminal dispatch `read_offset` is moved past `byte_size(line) + 1` (the line and its terminator); on a transient dispatch `read_offset` is held at the transient-line start and the loop stops — the first transient complete-line is seated at `read_offset` and is re-read on the next poll with the same deterministic `command_id`, preserving ordering without prepending or skipping queued lines behind it. The exhaustive terminal set (advisory #19) and the wrapper-shape classifier (advisory #20) are unchanged.

### 1.0.3 — 2026-08-10 (watcher restart-contract pivot)
