## 1. Executive Summary

`foreman_run_get_logs` currently returns `UNAVAILABLE` for known runs because Foreman has no durable run-log data source. The worker event model already defines `WorkerStdout` and `WorkerStderr` events on `worker:<run_id>:<worker_id>` streams, but production worker code does not emit them. Console `Logger` output is not keyed by `run_id` and cannot answer MCP log reads after a run ends.

This PRD requires Foreman to persist stdout/stderr emitted by worker runtimes, expose those records through `foreman_run_get_logs`, and preserve clear error semantics for unknown runs, empty logs, malformed requests, and storage failures. The feature is a read-model and worker-output capture capability, not a general logging redesign.

## 2. Background and Evidence

Task title: `Implement durable run log store for foreman_run_get_logs`.

Task description: `foreman_run_get_logs returns UNAVAILABLE. - `packages/foreman_server/test/foreman_server/mcp/tools_test.exs` asserts the current `UNAVAILABLE` behavior and missing-producer message.

## 3. Personas

### 3.1 Agentic MCP client

Needs to call `foreman_run_get_logs` after a failed or completed run and inspect worker output without reading server console files or SSHing into the host.

### 3.2 Foreman operator

Needs durable, bounded, secret-safe logs for troubleshooting stuck, failed, or surprising runs across restarts.

### 3.3 Foreman maintainer

Needs a design that reuses existing worker streams, event codec, projections, and typed MCP error contracts without creating permissive fallbacks or duplicate logging boundaries.

## 4. Goals and Non-Goals

### Goals

- Persist stdout/stderr generated by Foreman worker runtimes as durable, run-addressable log records.
- Make `foreman_run_get_logs` return useful log data for known runs, including after terminal state.
- Preserve Foreman's strict absent-vs-empty-vs-error semantics.
- Reuse `WorkerStdout`/`WorkerStderr` and worker streams unless the TRD proves they cannot satisfy retention/query requirements.
- Provide ordering metadata sufficient to reconstruct interleaved worker output.
- Add tests proving production producer wiring, read-model rebuild, MCP response shape, and failure behavior.

### Non-Goals

- Replacing application-wide `Logger` or building centralized observability.
- Capturing unrelated server logs as run logs.
- Adding live log streaming UI.
- Changing task/run state-machine semantics.
- Inferring logs from phase artifacts when no worker output was persisted.

## 5. Assumptions

- Foreman's existing event store remains the source of truth for durable worker events.
- Worker stream naming remains `worker:<run_id>:<worker_id>`.
- A known run with no captured output should return an empty log collection, not `UNAVAILABLE`.
- Log records should preserve stdout/stderr channel identity.
- Default retrieval should be bounded to protect MCP payload size [NEEDS CLARIFICATION: What default and maximum log byte/line limits should `foreman_run_get_logs` enforce?].

## 6. Functional Requirements

### REQ-001: Persist worker stdout/stderr as durable run logs

Priority: Must  
Complexity: High  
Risk: [RISK: Incorrect event shape or stream placement could create data that survives but cannot be queried consistently.]

Foreman must persist each captured worker stdout and stderr unit as durable run-addressable log data.

- AC-001-1: Given a worker produces stdout, when Foreman captures that output, then a durable `WorkerStdout`-equivalent record is committed with `run_id`, `worker_id`, channel, content, and sequence/order metadata.
- AC-001-2: Given a worker produces stderr, when Foreman captures that output, then a durable `WorkerStderr`-equivalent record is committed with `run_id`, `worker_id`, channel, content, and sequence/order metadata.
- AC-001-3: Given Foreman restarts after output was committed, when projections rebuild, then the output remains queryable by `run_id`.

### REQ-002: Wire production worker output producers

Priority: Must  
Complexity: High  
Risk: [RISK: Tests may pass against `WorkerProtocol.emit/2` while production workers still never call it.]

Production worker runtime code must emit stdout/stderr events through the supported worker protocol boundary, not only through tests or fixtures.

- AC-002-1: Given `JidoHarnessWorker` or the active production adapter runs an agent that produces stdout, when output is observed, then production code calls `WorkerProtocol.emit(:worker_stdout, ...)` or an equivalent approved boundary.
- AC-002-2: Given the worker emits stderr, when output is observed, then production code calls `WorkerProtocol.emit(:worker_stderr, ...)` or an equivalent approved boundary.
- AC-002-3: Given output capture fails, when the worker continues or exits, then the failure is surfaced as a typed/logged operational condition and does not silently downgrade `foreman_run_get_logs` to false-empty output.

### REQ-003: Return retrievable logs from `foreman_run_get_logs`

Priority: Must  
Complexity: Medium

`foreman_run_get_logs` must return log records for a known run instead of `UNAVAILABLE` once a durable producer and read path exist.

- AC-003-1: Given a known run has captured stdout/stderr, when an MCP client calls `foreman_run_get_logs` with its `run_id`, then the response contains those log records.
- AC-003-2: Given a known run has no captured output, when the client calls `foreman_run_get_logs`, then the response is a successful empty result with metadata that indicates no records matched.
- AC-003-3: Given persisted logs exceed the response bound, when the client calls `foreman_run_get_logs`, then the response is truncated or paginated deterministically [NEEDS CLARIFICATION: Should log retrieval use limit/offset pagination, cursor pagination, tail semantics, or byte-range semantics?].

### REQ-004: Preserve stream, worker, and ordering metadata

Priority: Must  
Complexity: Medium

Each returned log entry must include enough metadata to understand source, channel, and ordering.

- AC-004-1: Given one worker emits multiple stdout/stderr records, when logs are returned, then ordering follows committed worker sequence and event timestamp.
- AC-004-2: Given multiple workers emit logs for one run, when logs are returned, then each entry identifies `worker_id`, channel, sequence, timestamp, and content, with deterministic cross-worker ordering [NEEDS CLARIFICATION: Should cross-worker ordering prefer committed event-store position, event timestamp, or worker sequence plus tie-breaker?].

### REQ-005: Distinguish absent runs, empty logs, and store failures

Priority: Must  
Complexity: Medium

The API must keep existing typed boundary discipline: absent, empty, malformed, and failed reads are distinct.

- AC-005-1: Given `run_id` does not identify a known run, when logs are requested, then the MCP error is `NOT_FOUND`, not an empty list.
- AC-005-2: Given `run_id` identifies a known run with no output, when logs are requested, then the response is success with empty data, not `UNAVAILABLE`.
- AC-005-3: Given the log store/read path fails, when logs are requested, then the response is a typed failure that names the read failure and is not reported as success.

### REQ-006: Bound log volume and retrieval payloads

Priority: Must  
Complexity: Medium

Log capture and retrieval must enforce bounded resource usage.

- AC-006-1: Given a worker emits unbounded output, when capture runs, then Foreman enforces a documented maximum retained volume per run and/or per worker [NEEDS CLARIFICATION: Should truncation happen at capture time, retrieval time, or both?].
- AC-006-2: Given logs are truncated, when `foreman_run_get_logs` returns data, then the response indicates truncation and the amount or direction of omitted content.

### REQ-007: Protect secrets and unsafe output

Priority: Must  
Complexity: High  
Risk: [RISK: Durable logs can preserve secrets that previously only existed in ephemeral console output.]

Foreman must prevent durable run logs from becoming an unsafe secret sink.

- AC-007-1: Given output contains configured secret-like values or known credential patterns, when Foreman persists logs, then the stored or returned content is redacted according to documented policy [NEEDS CLARIFICATION: Which redaction policy/pattern list should apply to worker logs?].
- AC-007-2: Given an MCP client is unauthorized, when it requests logs, then existing MCP auth denies access consistently with other run-detail tools.
- AC-007-3: Given log content contains control characters or terminal escapes, when logs are returned, then clients receive safe serialized content without transport injection.

### REQ-008: Support retrieval after run terminal state

Priority: Must  
Complexity: Medium

Logs must remain available after runs complete, fail, are cancelled, or are marked stuck.

- AC-008-1: Given a run reaches a terminal state after producing logs, when `foreman_run_get_logs` is called later, then logs remain available.
- AC-008-2: Given worker cleanup emits late lifecycle events, when logs are queried, then previously committed logs are not lost or overwritten.

### REQ-009: Rebuild projections from committed events

Priority: Must  
Complexity: Medium

The log read model must rebuild correctly from committed event-store data.

- AC-009-1: Given the projection store starts from an empty state and replays committed events, when worker stdout/stderr events are present, then `run_logs/1` can return them.
- AC-009-2: Given replay sees malformed or unsupported log events, when rebuild runs, then the failure is loud or quarantined according to existing projection error conventions, not silently treated as empty logs.

### REQ-010: Expose operational diagnostics

Priority: Should  
Complexity: Medium

Foreman should expose enough diagnostics to identify whether log capture, storage, or retrieval is failing.

- AC-010-1: Given log capture is active, when an operator inspects run/activity diagnostics, then they can see whether log events were emitted and persisted.
- AC-010-2: Given `foreman_run_get_logs` cannot return logs due to a system condition, when the error is returned, then the message names the failing layer at a safe level of detail.

### REQ-011: Cover reset, purge, and retention behavior

Priority: Should  
Complexity: Medium  
Risk: [RISK: Reset or cleanup paths may leave logs orphaned or delete evidence unexpectedly.]

Foreman should define how run logs behave under reset, purge, worktree cleanup, and retention.

- AC-011-1: Given a run is reset or retried, when logs are queried, then the response clearly distinguishes prior-attempt logs from current-attempt logs [NEEDS CLARIFICATION: Should logs be grouped by phase/attempt in addition to run/worker?].
- AC-011-2: Given retention expiry or purge applies to a run, when logs are queried, then the response follows a documented expired-log semantic [NEEDS CLARIFICATION: Should expired logs return empty success, `GONE`, or a typed `UNAVAILABLE` variant?].

### REQ-012: Keep MCP/API contracts total and typed

Priority: Must  
Complexity: Medium

The MCP tool implementation must remain total over the `ProjectionStore.run_logs/1` return contract.

- AC-012-1: Given `ProjectionStore.run_logs/1` returns each documented success or error tuple, when `foreman_run_get_logs` handles it, then every tuple maps to a typed MCP success or error.
- AC-012-2: Given an unexpected return appears, when the tool handles it, then it fails loudly with a diagnostic error rather than reporting success.

### REQ-013: Test end-to-end worker log retrieval

Priority: Must  
Complexity: High  
Risk: [RISK: Unit-only tests can miss the production wiring gap that caused the current defect.]

The implementation must include tests from production capture through MCP retrieval.

- AC-013-1: Given a test worker/adapter emits stdout and stderr through the same production boundary, when a run completes, then `foreman_run_get_logs` returns both channels.
- AC-013-2: Given the event store is replayed into a fresh projection, when the same run is queried, then logs are still returned.
- AC-013-3: Given unknown run, empty known run, malformed params, and store failure cases, when MCP tests run, then all four cases assert distinct outcomes.

### REQ-014: Document operator expectations

Priority: Should  
Complexity: Low

Foreman docs should explain what `foreman_run_get_logs` returns and what it does not return.

- AC-014-1: Given the feature ships, when an operator reads MCP or CLI docs, then they can identify retention limits, truncation behavior, redaction behavior, and expected empty vs missing-run responses.

### REQ-015: Avoid treating logger console output as run logs

Priority: Should  
Complexity: Low

Foreman must not present application `Logger` console messages as durable run logs unless they are explicitly captured and keyed to a run by the worker-output path.

- AC-015-1: Given server code writes ordinary `Logger` messages unrelated to worker stdout/stderr, when `foreman_run_get_logs` is called, then those messages are absent from run logs.

## 7. Non-Functional Requirements

Covered by REQ-006, REQ-007, REQ-008, REQ-009, REQ-010, REQ-011, REQ-012, and REQ-014.

- Performance: bounded capture and retrieval; deterministic pagination/truncation.
- Security: existing MCP auth plus durable-log redaction and safe serialization.
- Reliability: event-store durability and projection replay.
- Scalability: per-run/per-worker volume limits.
- Observability: diagnostics for producer, store, read, and truncation conditions.
