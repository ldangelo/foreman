## 3. pi - measured behaviour

### 3.1 Steer (script `pi_live.exs`, scenarios A/B/C; timelines `pi-A-events.txt` etc.)

- A: prompt "run `sleep 10`, then write ALPHA to result.txt". `steer/3` sent as soon as the `:tool_call` event appeared (+4.7 s) with "write BETA instead". Result: `{:ok, "request_..."}`; an `:input_accepted` event with `payload.kind == "steer"` and `request_id` arrived 100 ms later (`12:06:02.229`). pi **queued it for delivery after the in-flight tool finished** (the 10 s `sleep` ran to completion), then the model acted on it in the same agent run: file ended `BETA`. So: *delivered to the running turn at the next tool boundary - not rejected, not deferred to a new turn.*
- B: steer issued immediately after `send_message` (before any tool call), "b.txt must contain TWO instead of ONE": final file `TWO`.
- steer when idle: `{:error, :no_active_turn}` (Worker clause). Follow-up while busy: `{:ok, turn_id}`, `info.queued_turns == 1`, runs after the current turn.
- **Defect 1 (upstream, blocks v2): turn lifecycle is wrong for multi-step pi turns.** `Adapters.Pi.map_event(%{"type" => "turn_end"})` maps pi's per-LLM-iteration `turn_end` to `:turn_completed` (`adapters/pi.ex:306`); `agent_end` is the true end. In A the harness turn completed at `12:06:12.846` (after the first tool result) and `Session.await/3` returned `text: "I'll run the command and create the file."` and `result.txt == "ALPHA"` while pi was still working; the steered BETA work happened afterwards (file read `BETA` 8 s later), emitting events with `turn_id: nil` and two more `:turn_completed` (12:06:14, 12:06:16), the session reporting `session_idle` throughout, plus one `decode_error` provider_event. Consequences: `await` returns early with truncated text; `steer/3` after the first tool boundary fails with `:no_active_turn`; an operator "steer" cannot be reliably targeted. Fix is in the pi adapter/transport (complete the turn on `agent_end`, ignore intermediate `turn_end`). **E6 v2 must not ship until this is fixed or worked around.**

### 3.2 provider_session_id
`TurnResult.provider_session_id`, `SessionInfo.provider_session_id` and every event's `provider_session_id` were `nil` for the whole pi session (pi `--mode rpc` never emits the `session` header event the mapper looks for). The id exists on disk: `~/.pi/agent/sessions/--<cwd>--/<ts>_<uuid>.jsonl`, first line `{"type":"session","id":"<uuid>",...}`. Fix options: issue pi RPC `get_state` after start (not implemented), or read the header file. This is the E0-S1/S2 capture path for the Session door; the one-shot `Run` path (pi `--mode json`) is separate. Resumed sessions do report the id (`E1`: `provider_session_id: "01a15e5a-..."`).

### 3.3 Interrupt (`pi_live.exs` D, `pi_live2.exs`)
`Session.interrupt(sid, :active)` -> `:ok` within ms; turn result `status: :interrupted`; events `turn_interrupted{"reason"=>"interrupted"}`, `session_idle`, then a stray `turn_completed`. `ps` before: `hypa ... -c sleep 117` -> `sleep 117` process tree; after (1 s): gone. Session `state: :idle`, `active_turn_id: nil`, and a following `send_message` on the **same** session worked (answered `PINEAPPLE`, the word given in the interrupted turn - context preserved). So interrupt = abort of the turn + kill of tool children; the long-lived pi RPC process stays up (could not confirm the pi pid through `ps` filtering - `ps` showed only the tool tree; reuse of the session proves liveness). Closing the session (`Session.close`) leaves no tool process.

### 3.4 Approvals
None for pi. Not declared; `approval_mode: :prompt` rejected: `%Jido.Harness.Error{message: "unsupported value for normalized session option", details: %{value: :prompt, allowed: [:default, :auto_approve], field: :approval_mode}}`. pi tools run unattended. Nothing to wire for E8 on pi.

### 3.5 Resume after the process is gone (`pi_live.exs` E)
After `Session.close` (pi process terminated) and a new `Session.start(:pi, %{provider_session_id: <uuid from session file>})` in the same cwd: new turn answered `PINEAPPLE` (context continuity from the interrupted/earlier turns) - **works**, result carries the id. `provider_options: %{continue: true}` (`--continue`, newest session of cwd) also worked. **Unknown id** (`00000000-dead-beef-...`): the pi process exits 1 on start; the Session stays `:idle`/non-error, the first turn returns `status: :failed` with `error: %{"exit_status" => 1, ...}` and the transport GenServer crashes with `{:process_failed, :failed}` (logged `[error]`). Failure surfaces only at first turn - Foreman must treat `turn_failed` on a resumed first turn as "resume unsupported".

## 4. Approvals measured on ACP (opencode) - input for E8 `Aggregates.ToolCall`

`opencode_live.exs`, `approval_timeout_ms: 20_000`, approval_mode `:default`.

Event (type `:approval_requested`, `request_id` is the JSON-RPC id as string, `provider_session_id` present, `turn_id` of the active turn):
```
%{type: :approval_requested, request_id: "0", provider: :opencode,
  provider_session_id: "ses_ea1a20410ffearMn8OCj4st87E", turn_id: "turn_4Dkh...",
  payload: %{
    "options" => [%{"kind"=>"allow_once","name"=>"Allow once","optionId"=>"once"},
                  %{"kind"=>"allow_always","name"=>"Always allow","optionId"=>"always"},
                  %{"kind"=>"reject_once","name"=>"Reject","optionId"=>"reject"}],
    "tool_call" => %{"kind"=>"edit","name"=>"write","status"=>"pending","title"=>"hello.txt",
                     "toolCallId"=>"call_01a1...","rawInput"=>%{"content"=>"HELLO\n","path"=>"hello.txt"},
                     "locations"=>[%{"path"=>"/tmp/s2-scratch-oc/hello.txt"}],
                     "content"=>[%{"type"=>"diff","path"=>"...","oldText"=>nil,"newText"=>"HELLO\n"}]}}}
```
(`transports/acp.ex:239-248, 376-381`.) While pending: `SessionInfo.state == :awaiting_approval`, `pending_approvals: 1`.

Response API: `respond_approval(sid, request_id, %{decision: :approve | :deny, scope: :once | :session, reason: ...})` - **decisions are `:approve`/`:deny`, not allow** (`approval_response.ex`). A bare `:approve`/`:deny` atom also accepted.

Measured outcomes:
- **deny** -> `:ok`; `:approval_resolved` event `payload {"decision"=>"deny","scope"=>"once"}`; file NOT created; turn ended `status: :interrupted` (opencode cancels the turn on a reject, text "I'll create the file using the write tool.").
- **approve once** -> `:ok`; turn `completed`, `approved.txt == "YES\n"`.
- **unanswered** -> Worker timer `approval_timeout_ms` (default `:infinity` = hangs forever) fires `{:approval_timeout, id}` (`session/worker.ex:344-367`): auto-**deny**, `:approval_resolved` payload `{"decision"=>"deny","scope"=>"once","reason"=>"timeout"}`; turn `:interrupted`, file not created, session reusable. **E8 must set `approval_timeout_ms` explicitly**; with the default a headless session waits forever (`:awaiting_approval`).
- `respond_approval` with an unknown `request_id` -> `{:error, :not_found}`; on a transport without approvals -> unsupported error (gate order: lookup first, so pi returns `:not_found`).

## 5. Migration risk: workflow door One-shot `Run` -> `Session` (HIGH)

| Concern | Today (`Driver.run` in `JidoHarnessWorker`) | Session |
|---|---|---|
| Log capture | `log_events/1` maps a finished `RunResult.events`: `output_text_delta/final`, `command_output_delta` -> stdout; `provider_event` with `payload["stream"]=="stderr"` -> stderr (`jido_harness_worker.ex:243-290`). Batch at `:agent_done`. | Events come from `Session.replay/stream` per cursor; pi emits stdout-ish text as `output_text_*` (same types) but stderr arrives as `provider_event` with `kind`/`stream`, and **text after a premature `turn_completed` has `turn_id: nil`** (3.1) - per-turn filtering would drop it. Needs a new cursor-based live tailer; replay default `limit: 100` must be raised. |
| Terminal detection | `Driver.await(run_id)` returns `RunResult`. | `Session.await(sid, turn_id)` - wrong for pi multi-step turns (3.1): the worker would mark the phase done after the first tool call. **Showstopper until Defect 1 is fixed.** |
| Cancellation | `RunControl.register_agent(run_id, harness_run_id)` via `on_start`; `cancel_agent` -> `Run.cancel(harness_run_id)` (`run_control.ex`, used by `workflow/dispatcher.ex` for cancel/pause/RunDeleted). | `Run.cancel` does not accept a session id. Need `RunControl` to store `{:session, sid}` and call `Session.interrupt` + `close`. Every `cancel_agent` caller changes. |
| Heartbeat / lease | `JidoHarnessWorker` heartbeats from its own `Process.send_after` timer independent of the agent; agent runs in a monitored Task. | Same worker shell works, but Session processes are supervised by `Jido.Harness.SessionManager` outside the worker: if the worker dies the session/CLI is **orphaned** (must `close` in terminate; `Run` is linked to its owner today). Journals persist in `~/Library/Caches/jido_harness/<session_id>` and need retention/pruning. |
| Usage / provider_session_id (E0-S1/S2) | `RunResult.usage` / `provider_session_id`. | `TurnResult` carries both, but pi's session id is nil (3.2) and `usage` arrives per LLM turn in events. |
| Timeouts | `runtime_timeout_ms`/`idle_timeout_ms` per run. | `turn_runtime_timeout_ms`, `turn_idle_timeout_ms`, `session_idle_timeout_ms`, `approval_timeout_ms`; on turn timeout Worker interrupts (`:turn_timeout_interrupt_failed` fails the session). Different failure taxonomy; `JidoHarnessAdapter.normalize_raw_error` would need Session errors. |
| Stuck-state | none | Bogus resume leaves a "healthy" idle session with a dead transport (3.5). |

Recommendation: keep the workflow door one-shot; use Session only for new thread kinds (chat/jobsite follow-ups) where an owning process (GenServer) holds `session_id`.

## 6. v1 "pause -> resume with injected message" fallback - exact scope

Existing machinery: `run.pause` -> `RunControl.request(:pause)` + `cancel_agent`; the jobsite door's `AgentRunner` already accepts `:resume_session` -> `provider_session_id` (`jobsite/agent_runner.ex:28-43, 91-106`) which Driver forwards to the one-shot `RunRequest`. The workflow door's `resume_from` is a **phase index** restart (`run_executor.ex:312-326`) with a fresh agent and no provider session.

Must cover:
1. **Capture the provider session id on every provider before pause is offered.** pi: `Run` mode (verify its `RunResult.provider_session_id`; not tested here) or the Session door needs `get_state`/session-file read (3.2). claude: result id (code path `managed.ex:83-87`, `claude.ex:92`). Without an id, steering is unavailable: the command must reject with an explicit `:no_provider_session` error, not silently restart the phase.
2. **Resume flags:** pi `--session <uuid>` (measured) or `--continue` (measured, but picks the newest session in cwd - unsafe when several runs share a cwd; prefer `--session`); claude `--resume <id>` [UNVERIFIED live]; `--fork-session` exists for both (`claude.ex:12,105`, `pi.ex` `--fork`) if the original must be preserved.
3. **Injection mechanism: prompt of the resumed turn**, not `Session.send_message`. The resumed one-shot run's prompt = `operator message` (prefixed `"[Operator steer]"`) followed by "continue the previous task"; resume re-reads full history from the provider session, so the original prompt must **not** be re-sent (measured: resumed pi session recalled `PINEAPPLE` from a prior turn with only the new question in the prompt). This needs no Session API, works with Run on every provider, and matches the existing one-shot door.
4. **Pause semantics:** pi/claude both lose only the in-flight tool (interrupt kills tool children, session history kept). Uncommitted worktree changes are kept by `Workflow.JobsiteObserver` pause handling; the resumed agent sees them.
5. **Failure behaviour when resume is unsupported or the id is stale:** pi exits 1 on an unknown id and the failure shows up only as `turn_failed {"exit_status"=>1}` on the first resumed turn (3.5); claude `--resume` with an unknown id exits non-zero similarly [UNVERIFIED]. Required: classify a first-turn failure of a resumed run as `:resume_unsupported`, keep the run paused (do not fall through to a fresh run that would silently drop the injected message), and surface the original operator message back to the operator as undelivered.
6. **One message at a time:** multiple queued operator messages are concatenated in arrival order into one prompt.

## 7. What E6 / E8 should build or drop

- **E6-S5 (steering):** build v1 = pause -> resume with injected message exactly as in section 6. Gate v2 live steering per provider on a `Steerer` capability field (`steer: :native` pi only). Do not build live steer for claude. Prerequisites for pi v2: (a) fix `turn_end` -> `agent_end` mapping; (b) capture pi session id (`get_state`); (c) extend Foreman's `AgentRuntime.JidoHarness.Session` wrapper with `steer/3`, `interrupt/2`, `follow_up/3`, `replay/2`; (d) add an owner process and `RunControl` session registration. Message-delivery semantics to document: pi delivers at the next tool boundary, not immediately (a 10 s tool completes first).
- **E8-S3 (approvals):** `Approvals.Capability.mode/1` = `:native` for ACP transports (opencode, kimi), `:none` for pi and claude (headless claude `--permission-mode default` has no interactive channel through the managed one-shot transport). Build ToolCall producers from `:approval_requested`/`:approval_resolved` events only for ACP transports, using the payload above (`tool_call.kind/name/rawInput/locations/content`, `options[].optionId/kind`). Always pass an explicit `approval_timeout_ms` (default is infinite hang); treat the timeout `approval_resolved` (`reason: "timeout"`) as an auto-deny. Everything else stays Foreman-level approval gates (merge gate, phase `approval_mode`); the "waiting on you" state for pi/claude comes from questions/PR signals only. `Session.start(:pi, approval_mode: :prompt)` must never be generated.
- **Drop:** any plan to deliver live steer to claude; any plan to rely on `respond_approval` for pi/claude.
