# Spike S5: Remote worker (run a thread on the user's own machine) — design only (D2)

Scope: design only, no product code. Paths are under `packages/foreman_server/lib/foreman_server/`. Seams marked **[V]** were read in code; the Jido `RunRequest` internals were not re-read here (marked [UNVERIFIED]).

## 1. Seam analysis

## 2. Transport options

| Option | Pros | Cons |
|---|---|---|
| **A. Reverse WebSocket** (worker dials server; Phoenix Channel or raw WS) | Works behind NAT/firewall with no inbound port on the user machine; bidirectional (server→worker steer/cancel, worker→server events) on one connection; server already Phoenix. | Needs a socket endpoint, reconnect/resume logic, per-frame auth. |
| B. HTTP long-poll + POST | Plain HTTP, easy to proxy. | Higher latency for steer/cancel, two channels, more ordering work. |
| C. Server SSH into the user machine | No agent software to install. | Requires inbound reachability and storing user SSH keys on the server (violates §6); poor heartbeat/event semantics. |

**Recommendation: A, reverse WebSocket**, with the worker as a small standalone agent (Elixir release or Node/Go binary) that wraps the existing Jido harness locally. B is an acceptable degraded fallback only if a proxy blocks WS.

## 3. Worker-agent contract (frames, JSON, string keys, versioned `v:1`)

Worker → server:
- `hello {token, machine_id, name, capabilities{providers[], git_version}, protocol:1}`
- `claim {}` / server answers `assign {thread_id, run_id, project_id, repo_url, base_ref, branch, request(RunRequest minus cwd/env secrets), lease_ms}`; assignment is *offered* to a worker, worker acks with `accepted` or `rejected{reason}`.
- `event {thread_id, seq, type, payload}` where `type` ∈ the `WorkerProtocol.emit/2` set (`worker_started`, `heartbeat`, `assistant_message`, `tool_call_finished`, `worker_stdout`, `worker_stderr`, `worker_exited`); `seq` is the worker's own monotonic counter **scoped per thread assignment** (one counter per `(machine_id, thread_id)`, starting at 1 on `accepted`; a worker running several threads keeps independent counters), used only for dedupe/resume, **not** the event-store sequence.
- `artifact {thread_id, name: diff.patch|changed-files.txt|commits.json|transcript.jsonl, bytes, sha256}` (chunked). Explicit byte limits, enforced by the server **while receiving** (reject when declared `bytes` exceeds the cap; abort the upload when received bytes exceed the declared size; never buffer before checking): `diff.patch` <= `max_diff_bytes`, `transcript.jsonl` <= `max_transcript_bytes` (existing config); `changed-files.txt` and `commits.json` need **new** caps (proposed `max_changed_files_bytes` / `max_commits_bytes`, e.g. 256 KiB each; values are a proposal, not measured) plus an **aggregate** per-thread cap across all artifacts (proposed: sum of the four caps). **One over-cap rule:** an artifact whose declared or received `bytes` exceeds its cap (or pushes the thread past the aggregate cap) is **rejected whole** (upload aborted, nothing stored, a `capture_errors` entry recorded, and the manifest marks that artifact unavailable: `diff_status: "unavailable"` for the diff); the server never stores a server-truncated remote artifact. Only `transcript.jsonl` may be bounded by the worker (truncate **before** upload, declare the truncated size and `truncated: true` in the frame, field proposed here; maps to the existing `transcript_truncated` semantics); `diff.patch`, `changed-files.txt` and `commits.json` have no valid partial form and are all-or-nothing. **Upload integrity (proposal, not implemented):** chunks are staged in a temporary file per `(thread_id, name)` and published to the archive by atomic rename only after the received byte count equals the declared `bytes` **and** the SHA-256 of the received bytes equals `sha256`; on mismatch the staged file is deleted and a `capture_errors` entry is recorded, so `Capture` never reads a partial artifact. After a reconnect, `resume` is extended per artifact: the server answers with the staged `received_bytes` for each in-flight artifact and the worker either continues from that offset (the server re-verifies the full digest at the end) or sends `artifact_abort {thread_id, name}`; the server discards the staged partial on `artifact_abort`, on declared-size/digest mismatch, and when the thread reaches a terminal state without completion. Note: the current `Capture.store_diff/5` (`review/capture.ex:384-405`) bounds `diff.patch` but writes `Git.changed_files/3` output unbounded, so the remote-upload path (and arguably the local one) must add this bound; not changed in this docs-only spike.
- `done {thread_id, status, branch_pushed, head_sha, provider_session_ids[]}` (per thread; a worker running several threads sends one `done` for each)
- `resume {thread_id, last_acked_seq}` after reconnect (one per active thread; `last_acked_seq` is the per-thread counter above).

Server → worker:
- `ack {thread_id, seq}` (cumulative, per thread), `steer {thread_id, text}` (queued input), `cancel {thread_id}` / `pause {thread_id}` (from `RunControl` intent), `lease_renew {thread_id}`, `revoke {thread_id}`; every control frame names the target thread so a worker running several threads can route it.

Heartbeat: worker sends `heartbeat` at < `heartbeat_timeout_ms/2` (Tracker default 60 s); the proxy converts to `emit(:heartbeat,…)`.

## 4. Auth model and cwd validation

- **Per-machine token**, minted by the server, shown once, stored hashed (SHA-256, constant-time compare). Carries `machine_id`, `project_ids[]` scope, `expires_at`.
- **Pairing**: operator generates a single-use pairing code (10 min TTL) in the UI/CLI; `foreman worker pair <code>` on the machine exchanges it for the token. No long-lived secret is ever typed or sent in a URL. The code is an authentication credential, so the exchange endpoint must enforce (requirements; **none implemented or tested here**): (a) entropy: >= 128 bits from a CSPRNG (e.g. 22+ base64url chars), or if a short human-typed code is wanted, >= 8 chars of a 32-symbol alphabet (40 bits) **only together with** (b) and (c); (b) rate limiting of exchange attempts per source IP and globally, with exponential backoff; (c) failed-attempt handling: a code is invalidated after N (e.g. 5) failed exchanges against it or after the global failure threshold trips, and failures return a uniform error with constant-time comparison of the stored hash; (d) atomic single-use consumption: the code is stored hashed and redeemed by one atomic compare-and-delete/`UPDATE ... WHERE consumed_at IS NULL` so two concurrent exchanges cannot both mint a token; (e) every attempt (success/failure) is audited. Verification of these controls at the endpoint is a required follow-up test.
- **Scope**: token only authorises `hello`/`claim` for its listed projects; the proxy rejects frames whose `run_id`/`thread_id` was not assigned to that machine. Existing `BearerAuth`/`RequireAuthenticated` plugs (`foreman_server_web/router.ex:15-23`, fail-closed when no token set) are the model; the socket needs its own connect-time check, as these plugs are HTTP-pipeline only.
- **Revocation**: delete/disable the token row; the live socket is force-closed; in-flight threads go to the offline path.
- **cwd validation**: the server stores no remote `cwd`. The worker config has a `workspace_roots` allowlist; the worker creates worktrees under `<root>/.foreman/worktrees/<thread_id>`, resolves symlinks with `realpath`, and refuses any path outside the roots (including `..`). This is the "allowlisted `cwd` validation hook" the E6 thread model may adopt: thread records carry `execution_target: :server | {:worker, machine_id}`, and server-side `cwd` checks apply only to `:server`.

## 5. Git and PR production

**Chosen: remote clones/uses its own checkout, pushes the branch to the origin, server opens the PR.** Rationale: the code and the user's git credentials stay on their machine; the server needs only `gh` access, which `phase_pr.ex` already uses (but see the correction below: its push/PR steps assume a local checkout). Rejected alternative: server clones and ships a bundle — it needs the repo and its credentials on the server for every remote project, and it duplicates `Worktree`. Fallback when the worker cannot push (no remote access): upload `git bundle`/diff as an artifact and mark the thread `needs_push` (not in first slice).

**Correction: `phase_pr.ex` is NOT unchanged for remote runs.** `Workflow.PhasePR` runs `git rev-list`, `git push -u origin <head_branch>` and `gh pr create` through `System.cmd` with `cd: request.cwd` (`workflow/phase_pr.ex:150, 188, 308-309`), i.e. it assumes the checkout is on the server and gh infers the repository from it. For a remote thread the server has no such checkout, so the design requires: (1) the **worker** performs the commit comparison (`rev-list`) and the push, reporting `branch_pushed`, `head_sha` and `commits.json` in `done`; (2) the server-side PR step takes explicit repository metadata (`owner/name`, base branch, head branch) and runs `gh pr create --repo <owner/name> --head <branch> --base <base>` from a neutral cwd, with no dependency on a local checkout; (3) `PhasePR` therefore needs a remote-aware request variant (it is not reused as-is); (4) the `needs_push` artifact fallback stays for workers that cannot push. Whether the server's `gh` credentials can open a PR for a branch pushed by the user's credentials is [UNVERIFIED].

## 6. Event-store implications

- Remote output enters through the proxy, not directly: the worker never writes events. The proxy calls `WorkerProtocol.emit/2` → `Tracker.dispatch_lifecycle/3`, and Tracker atomically allocates the `worker:<run_id>:<worker_id>` sequence (**[V]** `worker_protocol.ex` doc: Tracker is sole owner of sequence allocation). Remote `seq` is therefore never trusted as a store sequence.
- Idempotency: the proxy keeps `last_acked_seq` per thread and drops `seq <= last_acked_seq`, so replay after reconnect does not duplicate `WorkerStdout` events. **Replay idempotency is not established until the cursor is durable.** ETS does not survive a proxy crash, and the event-store sequence is not the worker's `seq` (above), so rebuilding the cursor from the stream is only valid if the worker's remote `seq` is itself stored. Required design: persist `{thread_id, remote_seq}` inside the same event that carries the forwarded payload (a `remote_seq` field on the `worker:<run_id>:<worker_id>` events written through `Tracker.dispatch_lifecycle/3`), so `last_acked_seq` = max `remote_seq` over the thread's stored events; on proxy restart rebuild from that. **Ack ordering:** the proxy sends `ack {thread_id, seq}` only after the event carrying that `remote_seq` has been durably appended; the worker discards its buffer only on ack. A crash between append and ack causes a replay that the rebuilt cursor deduplicates. Whether `Tracker.dispatch_lifecycle/3` can carry the extra field is [UNVERIFIED]; until verified, replay deduplication must be considered unproven. [OPEN] exact record shape.
- If an operator-visible `worker.record` HTTP endpoint is ever wanted, it must be a system-only route behind the machine token; it is **not** needed with the WS proxy, which is the recommended design. `Aggregates.Worker.handle_command(%{type: "worker.record"})` (`aggregates/worker.ex:239`) is reused unchanged.

## 7. Failure model

| Failure | Behaviour |
|---|---|
| Socket drops, worker alive | Worker keeps running the agent, buffers events (bounded, disk spill), reconnects with `resume {last_acked_seq}`. Proxy process stays alive for a grace window (e.g. 2× heartbeat timeout) so Tracker does not see `:DOWN`; on resume it replays. |
| Machine offline > grace | Proxy exits → Tracker `:DOWN` path → worker failed → run `failed` with reason `worker_offline`. Branch may have pushed commits; the Review archive records `diff_status: "unavailable"` with a `capture_errors` entry (existing manifest semantics). |
| Resume after offline | v1: **no automatic resume of an in-flight agent**; the thread is failed and the operator may re-run, reusing the pushed branch as `base_ref`. Provider session ids are archived (`provider_session_ids`), so a later provider-level resume is possible but out of the first slice. |
| Server restarts | Workers reconnect; unknown `thread_id` → server replies `revoke`; worker abandons and cleans its worktree. Server boot recovery (`jobsite/boot_recovery.ex`) already fails orphaned jobsites. |
| Duplicate claim / two workers | Server assigns exactly one worker per thread; `accepted` is idempotent, second claim gets `rejected`. |

## 8. Security

- Secrets (provider keys, env, `.env`, bead credentials) **do not leave the server by default**. The worker uses the **user's own** provider credentials from its machine; the assignment carries no env map. An operator can opt in per project (`remote_env_allowlist: [..]`) to send named variables; values are redacted in logs by the existing worker log policy (`overwatch/worker_log_policy.ex`).
- Transcript/diff upload may contain secrets: run the existing redaction before persisting server-side.
- TLS only; token never in URL; `hooks.host` stays rejected; the worker executes only the `RunRequest` it was assigned, not arbitrary server-supplied commands, i.e. no generic remote `exec` frame is exposed outside the assigned thread.
- A compromised token can run agents on one machine only; it cannot read other projects' data (scope check) — it can, however, feed forged transcripts/diffs for its own threads, so Review verdicts from remote threads are labelled `executed_on: machine_id`.

## 10. Reused unchanged

`WorkerProtocol.emit/2` and the event-type set; `Tracker` (sequencing, heartbeats, leases, `:DOWN`); `Aggregates.Worker`/`worker.record`; `CommandRouter`/`EventCodec`; `RunControl` intent store; the `Jobsite.Runner` behaviour contract; `Review.Archive`, `Analyzer`, `Evaluator`, `BeadSink` (all server-side after upload); the server-side `gh` integration (`Workflow.PhasePR` itself is **not** unchanged: it needs the remote-aware variant described above); `BearerAuth` as the auth-style precedent; `Jobsite.Spec` `hooks.host` rejection.

## 11. Needs change

`Jobsite.Git`/`Worktree` get a remote-executed counterpart (worker-side); `Review.Capture` needs a pre-supplied-artifacts entry; a `Runners.Remote` + `Sandboxes.Remote`; thread/jobsite spec gains `execution_target`; `RunControl` cancel needs a remote translation; new socket endpoint, machine/token store, pairing flow, worker binary.

## 13. Recommendation: **DEFER** (leaning GO as a later epic)

Feasible without changing Tracker sequence allocation (forwarded events do persist a `remote_seq` so the cursor can be rebuilt after a proxy crash, so the event payload or a durable cursor record does change), because `WorkerProtocol.emit/2` is already the boundary. But it is a ~5-week security-sensitive epic (new auth surface, new binary to ship) that nothing in the P0 build set depends on. Record "remote worker threads" in E16 docs as out of scope for now, with these reasons. Adopt now only the cheap hook: thread model carries `execution_target` (default `:server`) and server-side `cwd` validation is applied only to `:server` targets.

**Smallest first slice (if later approved, ~8 d):** one pre-paired worker, one project, no steer/pause, no auto-resume: tasks 1 (token only, no pairing UI), 2 (no resume), 3 (no buffering), 4, and 5 (push branch, server opens PR); offline = run failed. Validates the `emit/2` bridge end-to-end before the rest is built.
