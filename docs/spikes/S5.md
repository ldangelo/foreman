# Spike S5: Remote worker (run a thread on the user's own machine) — design only (D2)

Scope: design only, no product code. Paths are under `packages/foreman_server/lib/foreman_server/`. Seams marked **[V]** were read in code; the Jido `RunRequest` internals were not re-read here (marked [UNVERIFIED]).

## 2. Transport options

| Option | Pros | Cons |
|---|---|---|
| **A. Reverse WebSocket** (worker dials server; Phoenix Channel or raw WS) | Works behind NAT/firewall with no inbound port on the user machine; bidirectional (server→worker steer/cancel, worker→server events) on one connection; server already Phoenix. | Needs a socket endpoint, reconnect/resume logic, per-frame auth. |
| B. HTTP long-poll + POST | Plain HTTP, easy to proxy. | Higher latency for steer/cancel, two channels, more ordering work. |
| C. Server SSH into the user machine | No agent software to install. | Requires inbound reachability and storing user SSH keys on the server (violates §6); poor heartbeat/event semantics. |

**Recommendation: A, reverse WebSocket**, with the worker as a small standalone agent (Elixir release or Node/Go binary) that wraps the existing Jido harness locally. B is an acceptable degraded fallback only if a proxy blocks WS.

## 3. Worker-agent contract (frames, JSON, string keys, versioned `v:1`)

Worker → server:
- `hello {token, machine_id, name, capabilities{providers[], git_version}, protocol:1}`
- `claim {}` / server answers `assign {thread_id, run_id, project_id, repo_url, base_ref, branch, request(RunRequest minus cwd/env secrets), lease_ms}`; assignment is *offered* to a worker, worker acks with `accepted` or `rejected{reason}`.
- `event {seq, type, payload}` where `type` ∈ the `WorkerProtocol.emit/2` set (`worker_started`, `heartbeat`, `assistant_message`, `tool_call_finished`, `worker_stdout`, `worker_stderr`, `worker_exited`); `seq` is the worker's own monotonic counter, used only for dedupe/resume, **not** the event-store sequence.
- `artifact {name: diff.patch|changed-files.txt|commits.json|transcript.jsonl, bytes, sha256}` (chunked, size capped by the existing `max_diff_bytes`/`max_transcript_bytes` config).
- `done {status, branch_pushed, head_sha, provider_session_ids[]}`
- `resume {thread_id, last_acked_seq}` after reconnect.

Server → worker:
- `ack {seq}` (cumulative), `steer {text}` (queued input), `cancel {}` / `pause {}` (from `RunControl` intent), `lease_renew`, `revoke {}`.

Heartbeat: worker sends `heartbeat` at < `heartbeat_timeout_ms/2` (Tracker default 60 s); the proxy converts to `emit(:heartbeat,…)`.

## 4. Auth model and cwd validation

- **Per-machine token**, minted by the server, shown once, stored hashed (SHA-256, constant-time compare). Carries `machine_id`, `project_ids[]` scope, `expires_at`.
- **Pairing**: operator generates a short single-use pairing code (10 min TTL) in the UI/CLI; `foreman worker pair <code>` on the machine exchanges it for the token. No long-lived secret is ever typed or sent in a URL.
- **Scope**: token only authorises `hello`/`claim` for its listed projects; the proxy rejects frames whose `run_id`/`thread_id` was not assigned to that machine. Existing `BearerAuth`/`RequireAuthenticated` plugs (`foreman_server_web/router.ex:15-23`, fail-closed when no token set) are the model; the socket needs its own connect-time check, as these plugs are HTTP-pipeline only.
- **Revocation**: delete/disable the token row; the live socket is force-closed; in-flight threads go to the offline path.
- **cwd validation**: the server stores no remote `cwd`. The worker config has a `workspace_roots` allowlist; the worker creates worktrees under `<root>/.foreman/worktrees/<thread_id>`, resolves symlinks with `realpath`, and refuses any path outside the roots (including `..`). This is the "allowlisted `cwd` validation hook" the E6 thread model may adopt: thread records carry `execution_target: :server | {:worker, machine_id}`, and server-side `cwd` checks apply only to `:server`.

## 5. Git and PR production

**Chosen: remote clones/uses its own checkout, pushes the branch to the origin, server opens the PR.** Rationale: the code and the user's git credentials stay on their machine; the server needs only `gh` access, which `phase_pr.ex` already uses unchanged. Rejected alternative: server clones and ships a bundle — it needs the repo and its credentials on the server for every remote project, and it duplicates `Worktree`. Fallback when the worker cannot push (no remote access): upload `git bundle`/diff as an artifact and mark the thread `needs_push` (not in first slice).

## 6. Event-store implications

- Remote output enters through the proxy, not directly: the worker never writes events. The proxy calls `WorkerProtocol.emit/2` → `Tracker.dispatch_lifecycle/3`, and Tracker atomically allocates the `worker:<run_id>:<worker_id>` sequence (**[V]** `worker_protocol.ex` doc: Tracker is sole owner of sequence allocation). Remote `seq` is therefore never trusted as a store sequence.
- Idempotency: the proxy keeps `last_acked_seq` per thread and drops `seq <= last_acked_seq`, so replay after reconnect does not duplicate `WorkerStdout` events. The proxy state must survive a proxy crash: persist `last_acked_seq` via a worker-stream event or ETS plus rebuild-from-stream. [OPEN] choose at implementation.
- If an operator-visible `worker.record` HTTP endpoint is ever wanted, it must be a system-only route behind the machine token; it is **not** needed with the WS proxy, which is the recommended design. `Aggregates.Worker.handle_command(%{type: "worker.record"})` (`aggregates/worker.ex:239`) is reused unchanged.

## 7. Failure model

| Failure | Behaviour |
|---|---|
| Socket drops, worker alive | Worker keeps running the agent, buffers events (bounded, disk spill), reconnects with `resume {last_acked_seq}`. Proxy process stays alive for a grace window (e.g. 2× heartbeat timeout) so Tracker does not see `:DOWN`; on resume it replays. |
| Machine offline > grace | Proxy exits → Tracker `:DOWN` path → worker failed → run `failed` with reason `worker_offline`. Branch may have pushed commits; the Review archive records `diff_status: "unavailable"` with a `capture_errors` entry (existing manifest semantics). |
| Resume after offline | v1: **no automatic resume of an in-flight agent**; the thread is failed and the operator may re-run, reusing the pushed branch as `base_ref`. Provider session ids are archived (`provider_session_ids`), so a later provider-level resume is possible but out of the first slice. |
| Server restarts | Workers reconnect; unknown `thread_id` → server replies `revoke`; worker abandons and cleans its worktree. Server boot recovery (`jobsite/boot_recovery.ex`) already fails orphaned jobsites. |
| Duplicate claim / two workers | Server assigns exactly one worker per thread; `accepted` is idempotent, second claim gets `rejected`. |

## 8. Security

- Secrets (provider keys, env, `.env`, bead credentials) **do not leave the server by default**. The worker uses the **user's own** provider credentials from its machine; the assignment carries no env map. An operator can opt in per project (`remote_env_allowlist: [..]`) to send named variables; values are redacted in logs by the existing worker log policy (`overwatch/worker_log_policy.ex`).
- Transcript/diff upload may contain secrets: run the existing redaction before persisting server-side.
- TLS only; token never in URL; `hooks.host` stays rejected; the worker executes only the `RunRequest` it was assigned, not arbitrary server-supplied commands, i.e. no generic remote `exec` frame is exposed outside the assigned thread.
- A compromised token can run agents on one machine only; it cannot read other projects' data (scope check) — it can, however, feed forged transcripts/diffs for its own threads, so Review verdicts from remote threads are labelled `executed_on: machine_id`.

## 10. Reused unchanged

`WorkerProtocol.emit/2` and the event-type set; `Tracker` (sequencing, heartbeats, leases, `:DOWN`); `Aggregates.Worker`/`worker.record`; `CommandRouter`/`EventCodec`; `RunControl` intent store; the `Jobsite.Runner` behaviour contract; `Review.Archive`, `Analyzer`, `Evaluator`, `BeadSink` (all server-side after upload); `Workflow.PhasePr` and `gh` on the server; `BearerAuth` as the auth-style precedent; `Jobsite.Spec` `hooks.host` rejection.

## 11. Needs change

`Jobsite.Git`/`Worktree` get a remote-executed counterpart (worker-side); `Review.Capture` needs a pre-supplied-artifacts entry; a `Runners.Remote` + `Sandboxes.Remote`; thread/jobsite spec gains `execution_target`; `RunControl` cancel needs a remote translation; new socket endpoint, machine/token store, pairing flow, worker binary.

## 13. Recommendation: **DEFER** (leaning GO as a later epic)

Feasible without touching the Tracker or event model, because `WorkerProtocol.emit/2` is already the boundary. But it is a ~5-week security-sensitive epic (new auth surface, new binary to ship) that nothing in the P0 build set depends on. Record "remote worker threads" in E16 docs as out of scope for now, with these reasons. Adopt now only the cheap hook: thread model carries `execution_target` (default `:server`) and server-side `cwd` validation is applied only to `:server` targets.

**Smallest first slice (if later approved, ~8 d):** one pre-paired worker, one project, no steer/pause, no auto-resume: tasks 1 (token only, no pairing UI), 2 (no resume), 3 (no buffering), 4, and 5 (push branch, server opens PR); offline = run failed. Validates the `emit/2` bridge end-to-end before the rest is built.
