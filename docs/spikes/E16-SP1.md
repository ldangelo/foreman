# E16-SP1: UI accessibility / performance tooling and browser e2e harness

Decision date 2026-10-22. Bead `foreman-nb8w2.1`.

## Question

Which tool can run axe-core, a keyboard-path check and a WebSocket-traffic count against the Phoenix LiveView pages of this repo?

## Findings (all observed)

- `scripts/e2e-task-approval` is a Bourne shell script, not a browser harness; it cannot run axe.
- `ExUnit` / `Phoenix.LiveViewTest` has no real browser: no computed styles, no focus, no WebSocket frames. It stays the right tool for server-side render/validation assertions (already used by `project_workspace_live_test`, `project_settings_live_test`).
- Node 26 and Playwright's Chromium are installable on a dev machine without devbox changes: `npm install` in `scripts/e2e/ui-a11y` (3 packages) + `npx playwright install chromium` (about 100 MiB headless shell).
- `/dashboard/runs` serves **no JavaScript** (router uses `put_root_layout(false)`; only the workspace live_session has `Workspace.Layouts.root`), so `window.liveSocket` is undefined there. It is scanned as static HTML. axe found two real serious violations on it (no `<title>`, no `<html lang>`); deferred as bead `foreman-70eq6`.
- The LiveView WebSocket is rejected with 403 when the page is opened as `http://127.0.0.1:<port>`; the dev endpoint's origin check only accepts `localhost`. Use `localhost`.
- The `phx-connected` CSS class is not applied by this app; "mounted" is detected with `window.liveSocket.isConnected()`.

## Decision

**Playwright (node) + `axe-core`**, in `scripts/e2e/ui-a11y/` (own `package.json`, `node_modules` git-ignored). The eval `browser` helpers were not used: they are not available to a contributor or to CI.

| What | Where it runs |
|---|---|
| render/validation/budget assertions | CI (`mix test`, LiveViewTest) |
| axe scan, keyboard order, idle WebSocket frame count | **Local acceptance**, `node scripts/e2e/ui-a11y/ui_a11y.mjs` |

It is deliberately **not** a CI job: it needs a running server on a migrated Postgres, a seeded project with a live thread (thread cards only exist for runs, and creating one needs a workflow plus an agent), and a 100 MiB browser download. The scan itself takes about 25 s; the setup is the cost and it would be a new heavy, flaky-prone piece of infrastructure. Revisit if a deterministic run-fixture seed (no agent) is added.

## Install and run

```
cd scripts/e2e/ui-a11y && npm install && npx playwright install chromium
# server up on a throwaway DB/port, project seeded with >= 1 thread
node ui_a11y.mjs --base http://localhost:47671 --token <FOREMAN_API_TOKEN> --project <id> \
     [--idle-seconds 10] [--max-idle-frames 2] [--report <file.md>]
```

Exit code 0 only if: zero serious/critical axe violations (wcag2a/2aa/21a/21aa + best-practice) on workspace and settings; Tab reaches the composer, its Send button, the first thread action, and on settings the instructions field before `Save settings`, with a visible focus ring at every stop; Enter on Save updates the `#notice` live region; and idle non-heartbeat LiveView frames <= `--max-idle-frames`.

## Evidence (run 2026-10-22, dev server on private DB `foreman_uia11y`, port 47671, project with 2 working pi/minimax threads)

Full output: `docs/lessons/ui-a11y-report-2026-10-22.md`. Summary: workspace 0 axe violations (39 rules passed), settings 0 (37 passed), runs 2 serious (deferred, `foreman-70eq6`); keyboard checks ok; idle workspace and settings 0 frames in 10 s (counter sanity: 2 frames observed during mount).

The checks can fail: (a) axe failed the `runs` page with real violations before it was marked deferred; (b) with `--max-idle-frames 0 --idle-seconds 20` and a `task.create` posted mid-window, the run FAILED with `idle workspace: 1 LiveView frames in 20s`.

## GO / NO-GO: automated WebSocket-traffic counting

**GO.** Playwright's `websocket` `framesent`/`framereceived` events count LiveView frames reliably; heartbeats are excluded by payload. Idle pages produce 0 frames, and a projection event produces exactly the expected refresh frame. Caveat: the count is only "near zero" while the project has no concurrent events; the script is meant for a quiet project (running agents emit worker output events, which the workspace ignores, as observed).
