## 1. Verdict

**GO.** One run, one worktree per repository, one branch + one PR per touched repository is buildable without
touching the Run aggregate's shape, because the existing event model is already per-operation for worktrees
(`vcs:<operation_id>` streams, `ProjectionStore.worktrees_for_run/1` already returns a list) and per-run-id for PRs.
Three scope decisions, each pre-authorised by the "S3 outcome changes" paragraphs of the E12 beads:

| Decision | Outcome |
|---|---|
| Jobsite door multi-repo | **Out of v1.** Typed rejection only (§9). Engine/Executor/Observer/aggregate/resume are single-worktree end to end (27 `ctx.worktree`/`.worktree` uses in `jobsite/*`, 11 `worktree_path\|base_sha` uses in `aggregates/jobsite.ex`, resume rebuild `jobsite/executor.ex:515-580`). E12-S8-T3/T4 are dropped. |
| Per-repo task-provider binding | **Out of v1.** One provider per project stays. `repositories[].task_provider` is a reserved key that must be `nil` (non-nil → typed error). E12-S9 shrinks to `repo_id` targeting. |
| Per-phase `worktree: {repo: id}` | **Not added.** Worktree is deliberately workflow-level/run-scoped (`run_executor.ex:2156-2183` explains the removal of the phase-level block). Every run repo is provisioned once; the agent's cwd is always the primary worktree. |

**Delivery order / safety gate (new, required).** Until E12-S5/S6 land, a multi-repo run would commit in repo b and
open no PR for it. Therefore E12 adds a run-start gate (`:multi_repo, runs: false` by default): a run whose
resolved repo set has more than one element is refused with `{:error, :multi_repo_runs_disabled}`. The gate flips to
`true` only in E12-S12. This is what makes "repositories + worktrees first, PR/merge second" shippable in two releases
without a separate epic.

## 3. Data model (deliverable 1)

### 3.1 Where it lives — decision: dedicated events on the existing `project:<id>` stream

Not `project.config`. Reasons: (a) `merge_config/2` (`project.ex:381`) is a shallow key-by-key replace, so a list under
`config.repositories` is last-writer-wins with no per-repo identity, no per-repo idempotency and no add/remove audit;
(b) the audit field `added_by` (operator vs `run:<id>`, needed by E12-S10) belongs on an event; (c) project events are
read raw, so new events/keys cost no EventCodec work and old binaries ignore the new event types (§2 row 2).

`project.register` does **not** accept `repositories` in v1 (drops E12-S1-T3). Register with `path`, then
`project.repo.add`. One entry point removes the "which entry is primary" ambiguity.

### 3.2 `repositories[]` entry (v1)

```elixir
@type repository :: %{
        id: String.t(),                # ^[a-z0-9][a-z0-9-]{0,31}$ ; unique within the project; immutable
        path: String.t(),              # absolute, realpath-canonical, a git work tree; unique within the project
        default_branch: String.t() | nil, # nil = "branch checked out at run start" (legacy semantics). NEVER defaulted to "main".
        primary: boolean(),            # exactly one true: the project's `path`
        vcs: %{adapter: "git"},        # only "git" in v1
        task_provider: nil,            # RESERVED; non-nil rejected {:error, {:repo_task_provider_unsupported, id}}
        added_by: String.t() | nil,    # "operator:<id>" | "run:<run_id>"
        added_at: String.t()
      }
```

Deliberately omitted vs the plan's "VCS/PR settings": `vcs.remote` (AutoPR/`Jobsite.Git.push` hard-code `origin`),
`pr.draft` (no `--draft` anywhere in `auto_pr.ex`), `pr.base_branch` (the PR target is the branch the work was cut from,
by an explicit earlier decision — `run_executor.ex:1755-1769`), `pr.enabled` (no coherent semantics: an edited repo that
is never proposed is stranded work). Unknown repo keys are rejected (`{:unknown_repo_keys, keys}`), so each can be
added later as an additive change when a consumer exists.

ID charset has no `_`, so mapping `-`→`_` and upper-casing for env var names is injective (`a-b` ≠ any other id).

### 3.3 Events (stream `project:<project_id>`; typed, `@derive Jason.Encoder`, following `events/jobsite_request_audited.ex`)

```elixir
ProjectRepositoryAdded   # @enforce_keys [:project_id,:repo_id,:path,:added_by,:at]
  project_id, repo_id, path, default_branch :: String.t()|nil, vcs :: map(), task_provider :: nil,
  added_by, at
ProjectRepositoryRemoved # @enforce_keys [:project_id,:repo_id,:removed_by,:at]
  project_id, repo_id, removed_by, at
```

No `primary` on events: the primary is never added or removed by event; it is always `path`.

### 3.4 Aggregate (`Aggregates.Project`)

State gains `repositories: []` (non-enforced; ordered, non-primary entries only). Commands:

* `project.repo.add` `{project_id, repo_id, path, default_branch?, added_by}` → `ProjectRepositoryAdded`. Pure checks:
  id regex `{:invalid_repo_id, id}`; id equals reserved synthesized id `"main"` or already present `{:repo_id_taken, id}`;
  path absolute `{:repo_path_not_absolute, p}`; path equal to the primary path or another repo's
  `{:repo_path_duplicate, p}`; project archived → existing guard; `task_provider` non-nil → rejected.
* `project.repo.remove` `{project_id, repo_id, removed_by}` → `ProjectRepositoryRemoved`: unknown
  `{:repo_not_found, id}`; the synthesized primary `{:error, :primary_repo_not_removable}`; any
  `active_run_reservations` (`project.ex:20`) `{:error, :project_has_active_runs}` (mirror `validate_archive`).
* `apply_event/2` already has `_ -> state` (`project.ex:93`).

Impure checks (path exists, is a git work tree, `realpath`, **same `origin` URL as another repo of the project →
`{:repo_remote_duplicate, other_id}`**) run in a `CommandGateway.perform_operator_side_effects`-style step before
dispatch (`command_gateway.ex:140` shows the pattern), never inside the aggregate. The remote-duplicate check exists
because two checkouts of one remote would push the same branch name and open ambiguous PRs. Realpath canonicalisation
happens before the duplicate comparison so a symlink cannot alias a repo.

Idempotency: caller-supplied `command_id`; the system caller (E12-S10) uses
`"run-repo-add:<run_id>:<sha256(path)[0,12]>"`. (Not a content-only id, or re-adding after a remove would be deduped.)

### 3.5 Projection

`ProjectionStore` handlers `"ProjectRepositoryAdded"/"…Removed"` store into `project.repositories_extra` (raw `get/2`
like the neighbours, no raise). Public readers:

```elixir
ProjectionStore.project_repositories(project_id) :: [repository] | nil   # nil = unknown project
ProjectionStore.project_repository(project_id, repo_id) :: repository | nil
ProjectionStore.project_primary_repo_id(project_id) :: String.t() | nil  # "main" for every project today
```

`project_repositories/1` = `[synthesized primary] ++ extras`, where the synthesized primary is **computed at read time**
from the projected `path`: `%{id: "main", path: path, default_branch: nil, primary: true, vcs: %{adapter: "git"},
task_provider: nil, added_by: nil, added_at: registered_at}`. No event is written for legacy projects; a legacy project
that gains a second repo needs only `ProjectRepositoryAdded`. `path` changes through `project.update` (the projection
already `maybe_put(:path, …)` `:1025`) therefore move the primary automatically. **Required guard (not yet in the design above):** because that update re-points the primary, `project.update`'s `path` must pass the same validation as `project.repo.add` before `ProjectUpdated` is emitted: `realpath` canonicalisation, uniqueness of checkout path across the project's repositories (primary and extras), and the remote-identity duplicate check, rejecting a path that would give two repositories the same identity or checkout (the §3.4 invariant). `Aggregates.Project.apply_event/2` does not update `State.path` for `ProjectUpdated` today [UNVERIFIED: re-read before implementing], so the design must also have `ProjectUpdated` with a `path` update the aggregate's `State.path`; otherwise a later `project.repo.add` duplicate check compares against the stale old primary path (moving primary A→B would still reject adding A as a duplicate secondary). The aggregate `State.path` update must land before, and be covered by, the `project.repo.add` duplicate check. `project.update` must not accept a `repositories` key; secondary repos change only through `project.repo.*` commands. [UNVERIFIED against current `project.update` code: whether it validates `path` today.] Atom keys internally; string keys only
at the controller/JSON boundary (AGENTS 5.4b).

## 4. Run model (deliverable 2)

### 4.1 The one rule: `repo_id` absent ≡ the run's PRIMARY repo

Every new optional `repo_id` field on an event/command is **absent for the run's primary repo and present for every
other repo**. That is what keeps single-repo runs (and S11 fan-out runs, whose primary is not the project primary)
byte-identical in events and ids. Readers resolve the effective id as `repo_id || run.primary_repo_id ||
project_primary_repo_id`.

* **Primary repo of a run**: task/work request field `repo_id` (default: project primary). Carried on
  `TaskCreated.repo_id` (new, non-enforced; `events/task_created.ex` is strict-decoded) and, for work runs with no
  task, `RunStarted.repo_id` (new, non-enforced; `projection_store.ex:1169` decodes it). It is the repo of the `plan_context["project_root"]`
  override when one exists, else the repo's `path`.
* **Initial extra repos**: optional `repo_ids` (list; primary + extras together ≤ `max_repos_per_run`, default 4, so ≤ 3 extras by default; **validate first**: reject duplicates and any id equal to the effective primary, then count only the remaining non-primary ids toward the cap) on the same payloads. Mid-run
  additions are E12-S10.
* **Registry of a run's repos = its worktree projections**, not a new aggregate or Run event. The executor rebuilds
  `state.run_worktrees` from `ProjectionStore.worktrees_for_run(run_id)` at every phase start (the projection is applied
  synchronously by `CommandRouter`, see `run_executor.ex:901-909`). That is why a worktree attached by another process mid-run (E12-S10) is
  visible to the next phase with no run-state message and no `RunRepoAttached` event.

## 5. Executor changes (deliverable 3)

New pure module `ForemanServer.Workflow.RunWorktreeLayout` (extracted from `run_executor.ex:2375,2599,2668`):
`path(project_id, task_id, run_id, repo_role)`, `branch(spec, state)`, `operation_id(run_id, repo_id | nil)`,
`contained?/…`. It exists because three callers need the same arithmetic without a `RunExecutor` state: the executor,
E12-S10's attach, and E12-S6's `run.pr.retry` (the RunExecutor process is gone by then).

* **Layout**: primary `<root>/<project>/<task>/<run>/workspace` (unchanged, honours `worktree: path:`); secondary
  `<…>/<run>/repos/<repo_id>`. Siblings are outside the primary tree so `git status`/`.gitignore` in the primary are
  unaffected. Containment (`:2668`) already covers `<run>/`.
* **Branch**: the same rendered name in every repo (`foreman/{task_id}/{run_id}`; `worktree: branch:` applies to all).
  Branch namespaces are per repository; same name makes the PRs easy to correlate. The remote-duplicate rule (§3.4)
  is what makes this safe.
* **Base per repo**: `base_branch(repo)` = `repo.default_branch` when non-nil (and `base_ref` = its tip), else
  `checkout_branch(repo.path)` and `base_ref = HEAD` — i.e. exactly today's rule for the primary. Plan-context
  `source_revision` pinning (implementation runs) stays primary-only. This finally gives `default_branch` a consumer.
  Persist each via `run.record_base_branch{repo_id}` (resume-safe, same pattern as `:921`).
* **Provisioning timing: EAGER**, all planned repos at the run's first worktree-enabled phase (primary first). Lazy
  creation needs an interception point at "agent first writes", which does not exist; the agent needs a real path in
  its prompt/env before it can touch it. Mid-run attach (S10) is also eager, effective for the **next** phase's env/prompt
  (`FOREMAN_REPOS` is computed per phase).
* **Rollback**: provision sequentially; on failure at repo N, `Worktree.clean` + branch delete for repos 1..N-1 (the
  existing per-op `Worktree.create` already compensates its own append failure), return
  `{:error, {:multi_repo_worktree_failed, repo_id, reason}}`; the phase fails; no half-provisioned run. Proved in script step 8.
* **cwd**: primary worktree root — identical to today. A synthetic parent directory is **rejected**: it would change
  `FOREMAN_WORKTREE_PATH` and the cwd of every existing single-repo prompt, make cwd not-a-git-repo, and break
  `ArtifactTemplate` paths. Siblings are reachable at `FOREMAN_REPO_<ID>_WORKTREE`, and passed to the provider as
  `add_dirs` (provider CLIs otherwise refuse writes outside cwd).
* **Per-phase repo selection**: none in v1 (see §1).
* **Commit**: `commit_phase_worktree/4` and the pause path (`:962-1008`) commit **every** run worktree; the phase fails if
  any commit fails. `warn_uncommitted_work/1` reports per repo.
* **Resume**: `rehydrate_resume_context` (`:683-718`) rehydrates every non-cleaned worktree projection of the run
  (entries without `repo_id` = primary).
* **Cleanup**: `cleanup_run_worktree/2` (`:2818`, the single funnel; `Review.Capture.close_run` is its first statement)
  iterates repos, continues past a failing one, aggregates errors. Default `cleanup: never` (`:2610`) means worktrees
  are normally kept, so "deferred cleanup for a `create_failed` repo" only matters for `always`/`on_success`.
* **`project_path/1`/`vcs_working_directory/1`**: unchanged semantics for the primary; add
  `repo_root(state, repo_id)` guarded by "repo must be registered on the run's project" (`{:unknown_repo, id}`).

## 7. PR semantics (deliverable 5)

* **Touched** = commits ahead of that repo's `base_ref` (reuse `AutoPR` ahead check). Untouched repos get no PR and no
  association (script step 4: c).
* **Finalisation** `finalize_run/1` (`:1471`): for each run repo, primary first, call a shared
  `Workflow.RepoPr.open(run_id, repo_id)` that builds its context **from projections** (`RepoPrContext.build/2`: project root,
  worktree branch, `repo_base_branches`, task title/description) — not from executor state — so the same function is the body
  of `run.pr.retry`. AutoPR cwd for repo X = X's project root (today's semantics: `git push origin <branch>` from the repo root).
  Never short-circuit: results are collected `[{repo_id, :noop | {:ok, url} | {:error, reason}}]`.
* **Association + signalling per repo**: `PrAssociate.store/3`; `run.pr.ready` per repo with command id
  `workflow:<run>:pr_ready` (primary, unchanged) / `workflow:<run>:<repo_id>:pr_ready`.
  Failure to signal b must not stop a (logged at error, like `:1585`).
* **Cross-links**: after all PRs exist, best-effort `gh pr edit --body` appends "Part of multi-repo run <run_id>" with sibling
  `owner/repo#n` links (non-fatal; skipped for single-repo runs). Initial PR bodies cannot contain siblings (not yet opened).
* **Stacked PRs**: `stack_pr: true` with >1 repo is rejected **at run start** with `{:error, :stack_pr_unsupported_multi_repo}`
  (workflow validation cannot know the repo count — bead S5-T1 says "validation"; correction §14). `PhasePR` stays primary-only.
* **Partial failure**: repo b's push/`gh` fails → typed per-repo state `create_failed` via `RunRepoPrFailed{run_id, repo_id, reason, at}`;
  a succeeded; the run still completes; `completed_with_errors` is a **derived** dashboard/read-model flag (no new run status — the
  status enum is shared). The failed repo's worktree/branch are retained. Script steps 5-6 prove: a pushed, b failed, a
  untouched by b's retry.
* **Retry**: operator command `run.pr.retry {run_id, repo_id}` (operator-only, never MCP): side effect = `RepoPr.open/2` from
  the preserved worktree; idempotent (existing PR → `:noop`/existing url); allowed on terminal runs (extend `run.ex:766` list).
* **Merge gate**: `Run.State.merge_gates :: %{repo_key => :pending|:approved}` inside the Run aggregate (`repo_key` = `nil`
  for primary). Chosen over a per-PR aggregate (`run_pr:<run>:<repo>`) because: the PR lifecycle commands already target
  `run:<id>` and are already allowed on terminal runs (`run.ex:766`); a new aggregate would need a router prefix, an
  event-replay story, and `run_ids_for_pr_url` to know the stream; and the gate must be readable next to run status.
  `merge_approve{run_id, repo_id?}` and `run.pr.merge{run_id, repo_id?}` stay operator-only; there is **no** "approve all".
  Legacy events (no `repo_id`) fold into the `nil` key; legacy error tuples are unchanged for `nil`.
  `RunPrMerge.execute(run_id, repo_id)` filters `PrReady` events by `repo_id` (today `List.last` of all, `run_pr_merge.ex:88`),
  keeps `--match-head-commit` per PR, and never trusts the caller's payload. ETS key becomes `"run:<id>"` / `"run:<id>:<repo_id>"`.
  Fixes two latent multi-PR bugs found here: scalar `PrReady` un-approving, and `approve_by_key` approving an arbitrary entry.
* **Ordering guidance**: free-form; Foreman never auto-merges and never orders. The dashboard lists PRs in `repositories[]` order
  (primary first) and shows sibling PR links. Operators merge dependency-first by their judgement; a merged PR of b never marks a's gate
  (key per repo). (A declarative `merge_after` is deferred — no consumer.)
* **PR watching (E9/E10 contract)**: every PR is addressed as **`{run_id, repo_id}`** with `repo_id` the effective string id.
  `ProjectionStore.pr_associations_for_run/1` is the only enumeration API; `run_ids_for_pr_url/1` becomes
  `[{run_id, repo_id}]` (`projection_store.ex:363`, sole caller `webhooks/github.ex:72`). `PrMonitor.collect_associations`
  (`pr_monitor.ex:150`) flat-maps associations per run. `run.pr.update` payload carries `repo_id`; its command id already includes `pr_url`
  (`pr_update.ex:40`) so dedupe is already per PR. E9 keys `PrWatcher` state, fix threads and comments by `{run_id, repo_id}`; a fix
  thread works only in that repo's worktree/branch (`run_repositories/1` gives the path).

## 9. Jobsite door (deliverable 6) — out of v1

Add `repositories` to `@forbidden_keys` (`jobsite/spec.ex:47`) so it yields the existing typed `:spec_forbidden_key`
(reason text: multi-repo jobsites unsupported). No `Jobsite.Spec`, `Engine`, `Observer`, `JobsiteStarted` or aggregate change.
Rationale: the program is built around one `ctx.worktree` (`jobsite/context.ex:33`), pause keeps *the* worktree and cancel discards *the* worktree
(`executor.ex:259-292`), resume rebuilds one `%Worktree{}` from aggregate state (`:575-580`), and the aggregate stores one

the door opens no PRs anyway. Re-open only if an operator needs multi-repo jobsites; a follow-up story would add `repositories` + a per-repo
commit/diff step list.

## 11. Migration of single-path projects (deliverable 9)

1. **No event rewrite, no backfill.** `repositories[0]` is synthesised at read time (§3.5): `id "main"`, `path`, `default_branch nil`, `primary true`.
2. `path` remains the primary repo path and the only registration input; every reader of `projection.path` (`run_executor.ex:2145,2400`,
   `jobsite/spec.ex:191`, BeadsWatcher) is untouched.
3. Historical events replay unchanged: `WorktreeCreated`/`PrAssociated` without `repo_id` decode (new field non-enforced) and mean "primary".
4. **Replay-safety rules** (EventCodec rejects unknown keys on decode — `event_codec.ex:238-256`):
   * Strictly decoded events (`WorktreeCreated/Cleaned/Orphan*`, `PrAssociated`, `TaskCreated`, `RunStarted`, `JobsiteStarted`): declare `repo_id` in the struct **in the same commit**
     that introduces any writer.
   * Raw-read events (`Project*`, `Pr*`/`MergeGate*` run events, `RunBaseBranchRecorded`): payload keys are safe; new event *types* are ignored by old binaries
     (`projection_store.ex:2192`, `project.ex:93`) **except on the Run aggregate**, whose `apply_event` has no catch-all — add `_ -> state` first.
5. **Rollback safety**: an old binary raises only when it replays an event that carries `repo_id`. Such events exist only after a *multi-repo* run, which the run-start
   gate (§1) prevents until E12-S12. Single-repo behaviour emits zero new keys (the "absent ≡ primary" rule), so rolling back after the feature ships but before any multi-repo
   run is safe; after the first multi-repo run it is not — document this in the release notes.
6. Golden tests (E12 acceptance "byte-identical"): record a single-repo run's event stream types/order/payload keys and worktree op id/path/env before the change; assert equality after,
   except the intentional additive env vars.

## 12. Thread adds a repo to itself (deliverable 10)

* Command `run.repo.request {run_id, repo_id | repo_path}`, system-authored; MCP tool `foreman_run_request_repo` in `Mcp.Policy @write_tools` (`mcp/policy.ex:4`) and the hand-maintained
  seed allowlist in `application.ex`; **not** in `@allowed_operator_types` (`command_gateway.ex:53`) — never callable via `/api/commands`. Only the run's own id is accepted
  (`run_id` non-terminal, belongs to the project).
* Policy lives in the project, operator-edited only through `project.update` config: `repo_allowlist` (list of absolute path prefixes; default **empty = feature off**),
  `max_repos_per_run` (default 4). Whitelist-normalised: reject non-absolute entries, `..` segments, a bare `/` (`{:invalid_repo_allowlist, entry}`).
  Matching is on `realpath` of the requested path and `/`-bounded prefixes (a symlink must not escape; `/srv/repos` must not match `/srv/repos-evil`).
* Decision procedure (each outcome appends one `RunRepoRequested{run_id, project_id, requested_path, repo_id, decision, reason, requested_by, at}` on
  `run_repo_audit:<run_id>`, deterministic `command_id "run-repo-audit:<request_command_id>"` (derived from the request's own command id, so a retry of the same request stays idempotent while a later request for the same path - e.g. after the operator changed the allowlist - appends its own audit event; a `<run>:<sha256(path)>` id would dedupe the second attempt away), new aggregate modelled on `aggregates/jobsite_audit.ex` with `_ -> state`):
  0. For **every** request, resolve the target to a canonical `realpath` first (for a registered `repo_id`, its registered path) and apply `repo_allowlist` and the `max_repos_per_run` cap before either branch below (the cap counts the run's **primary plus all extras**, at run start and at every attachment, so `repo_ids` may hold at most `max_repos_per_run - 1` initial extras and a mid-run attach is denied once the total reaches the cap); an empty allowlist therefore denies registered repos too (feature off means off). If the target is **already attached** to the run, return success idempotently *before* the cap check (a retry of a successful attach must not yield `:max_repos_exceeded`); the cap applies only to a new attachment. Denials return `{:error, {:repo_not_allowed, path}}`.
  1. `repo_id` already registered **and its canonical path is inside the allowlist** → attach.
  2. `repo_path` not registered but inside the allowlist **and** a git work tree **and** passes the remote-duplicate check → system `project.repo.add` (`added_by: "run:<id>"`), then attach.
  3. otherwise `{:error, {:repo_not_allowed, path}}` (audited as `denied`).
  Over `max_repos_per_run` → denied `:max_repos_exceeded`.
* **Attach** = eager: `Workflow.RepoAttach.attach(run_id, repo_id)` creates the worktree through `RunWorktreeLayout` + `Worktree.create` (op id `wt-<run>-<repo>`, idempotent by `command_id vcs.worktree.create:<op>`).
  The executor sees it at the next phase start (§4.1). **Takes effect next phase** — the MCP tool description must say so. No `RunRepoAttached` event (the `WorktreeCreated` event with `repo_id` is the durable record).
* Attached repos get their own PR in finalisation like any other; a thread can never be granted merge/approve (not in write tools).

## 13. Failure / rollback (deliverable 11)

| Failure | Behaviour |
|---|---|
| Worktree N fails at provisioning | compensate 1..N-1 (worktree + branch), `{:multi_repo_worktree_failed, repo_id, reason}`, phase fails. |
| Executor crash after provisioning | resume rehydrates every non-cleaned worktree projection; unresolvable HEAD / vanished dir is the existing hard error per repo. |
| Phase-boundary commit fails in any repo | phase fails (existing 5.2 rule, now per repo). |
| One repo's PR fails | `create_failed` for that repo; others proceed; run `completed`; derived `completed_with_errors`; worktree kept; `run.pr.retry`. |
| Terminal cleanup | per repo, continue-on-error, aggregate errors; repo already gone is not an error. `run.remove` → `Worktree.clean_for_run/1` already iterates all. |
| Run cancelled | `Review.Capture.close_cancelled_run` captures every worktree; worktrees retained as today. |
| `project.repo.remove` while runs active | refused `:project_has_active_runs`. |
| Operator removes a repo after a run finished | run keeps its recorded paths (events carry `repo_path`); read models do not re-join to the live repo list for historical runs. |
