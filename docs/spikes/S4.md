# Spike S4: PR signal source for `PrWatcher` (gh polling vs GitHub webhooks)

Bead: foreman-slyt.4. Base: `origin/main` 32d51be1. Evidence files are in `docs/spikes/S4/`.

## 0. Method and its limits (read first)

The bead asked for a scratch repo with Actions and a protected branch. None was available and the rules for this
spike forbid writing to GitHub. So:

- **Measured for real, read-only, against `ldangelo/foreman`** (token scopes `gist, read:org, repo, workflow`):
  `gh pr view` JSON for PR #565 (merged; 3 reviews, 5 conversation comments, 5 inline comments, a failed then fixed
  CI run) and PR #531 (open, **fork** PR); REST `pulls/N/comments`, `pulls/N/reviews`, `issues/N/comments`,
  `commits/<sha>/check-runs`, `issues/N/timeline`; GraphQL `reviewThreads`; `gh run view --log-failed`;
  `If-None-Match` conditional requests; wall-clock latency; `X-RateLimit-*` headers.
- **NOT recorded (no scratch repo, no write access):** live webhook deliveries. `GET /repos/ldangelo/foreman/hooks`
  returns `[]`: the repo has no webhook, so no deliveries exist to replay. Webhook payload shapes below are from
  GitHub's documented schema plus the repo **Events API** (`repo-events-sample.json`: real `PullRequestReviewEvent`,
  `PullRequestReviewCommentEvent`, `IssueCommentEvent`, `PullRequestEvent` objects that wrap the same payload
  objects a webhook delivers). `check_run` / `check_suite` webhook bodies are **[UNVERIFIED]**; the REST
  `check-runs` object (verified) carries the same fields.
- **Not reproduced:** live merge conflict (no conflicted open PR), force-push (none in #565; its 4 commits are plain
  pushes), check rerun. For each I state the mechanism from the API shape and mark it [UNVERIFIED]. Webhook-side
  latency could not be measured at all; the numbers in section 3 are polling-side only.
- Rate-limit `used` counters were polluted by sibling agents sharing the token, so per-call cost is taken from
  GraphQL's own `rateLimit{cost}` field and from `Remaining` deltas on a single quiet sequence, not from counter
  diffs across batches.

## 1. What exists today (verified in code)

- `PrMonitor` (`pr_monitor.ex`) polls every `:pr_monitor_interval_ms`, default 5 min (line 38). For each run with a
  `PrAssociated` PR it calls `GitHub.PrStatus.fetch/2` and dispatches `run.pr.update` through
  `PrUpdate.command/3`.
- `PrStatus.fetch` runs `gh pr view <url> --json state,mergeable,headRefOid,headRefName,baseRefName`
  (`github/pr_status.ex:33,58`) and collapses to `:open | :merged | :closed | :conflicted`. Typed errors, no
  defaults. No checks, reviews or comments are read.
- Webhook: `POST /webhooks/github` -> `VerifyGithubSignature` (HMAC `X-Hub-Signature-256`, fails closed with no
  `FOREMAN_GITHUB_WEBHOOK_SECRET`) -> `GithubWebhookController` -> `Webhooks.Github.process/1`. It handles **only**
  `pull_request` payloads (closed+merged, closed, reopened, `mergeable_state == "dirty"`), attributes by
  `pull_request.html_url` via `ProjectionStore.run_ids_for_pr_url/1`, and returns 202 `ignored` for everything else
  (`webhooks/github.ex`). Any other event type (check_run, review) is silently ignored today.

## 2. Real payload shapes (verified)

### 2.1 `gh pr view <n> --json statusCheckRollup,reviewDecision,reviews,comments,mergeStateStatus,mergeable,headRefOid`
(`pr565-view.json`, 37.9 KB for a PR with 3 reviews + 5 comments, bodies included)

- `statusCheckRollup` is a **heterogeneous array**: `__typename: "CheckRun"` items
  `{name, workflowName, status: COMPLETED|IN_PROGRESS|QUEUED, conclusion: SUCCESS|FAILURE|..., detailsUrl, startedAt, completedAt}`
  and `__typename: "StatusContext"` items `{context, state: SUCCESS|PENDING|FAILURE|ERROR, targetUrl, startedAt}`.
  #565 had 3 CheckRun + 1 StatusContext (CodeRabbit). The fork PR #531 had only a StatusContext.
  Case differs from REST (`SUCCESS` vs `success`): normalise once.
- `detailsUrl` is `.../actions/runs/<run_id>/job/<job_id>`: gives run id and job id without another call.
- `reviews[]`: `{id: "PRR_...", author.login, authorAssociation, commit.oid, submittedAt, state}`. `state` observed:
  `CHANGES_REQUESTED`, `APPROVED`. `id` is the GraphQL node id, not the REST numeric id (REST `reviews` gives
  `5593481667` etc.). Each review is bound to a **commit oid**, so a review against an old head is visible as stale.
- `comments[]` are **issue (conversation) comments only**: `{id: "IC_...", author, createdAt, url, body, isMinimized}`.
  `url` ends `#issuecomment-6304823603`, the REST numeric id.
- `reviewDecision` is `""` (empty string, not null) when no review is required/present; the GraphQL API returns
  `null`. `mergeable`/`mergeStateStatus` are `UNKNOWN` for merged PRs (and lazily, right after a push); for open fork PR
  #531: `MERGEABLE` / `UNSTABLE` (checks not green, still mergeable). `BLOCKED`, `BEHIND`, `DIRTY`, `CLEAN`, `HAS_HOOKS`,
  `DRAFT` are the other documented values. `mergeStateStatus: DIRTY` / `mergeable: CONFLICTING` is the conflict signal.
- **Not in `pr view`:** inline review comments, thread resolution state, check annotations, log text, and the list of
  conflicting files.

### 2.2 Inline review comments (`pr565-inline-comments.json`, REST `pulls/565/comments`)
`{id (numeric), node_id, pull_request_review_id, in_reply_to_id, path, line, original_line, start_line, side,
commit_id, original_commit_id, position, user.login, created_at, updated_at, html_url}`.
Observed: 4 of 5 comments have `line: null` (outdated: code moved after the push) with only `original_line` set (and
`position: 1`); 1 has both `line: 306` and `original_line: 205`. A fix-thread **must** fall back to `original_line`
when `line` is null.

### 2.3 Review threads (`pr565-review-threads.json`, GraphQL)
`reviewThreads.nodes[] {id: PRRT_..., isResolved, isOutdated, path, line, originalLine, startLine, diffSide,
comments.nodes[]{databaseId, author, createdAt}}`. This is the **only** source of `isResolved`. In #565 all 5 threads
were `isResolved: true, isOutdated: true`; no unresolved example exists in this repo's recent history. `databaseId`
joins to REST inline-comment `id`.

### 2.4 Check runs for a SHA (`commit-6f9e1d7-check-runs.json`, REST)
For the failing head of #565: `foreman_server` `status: completed, conclusion: failure`, `details_url`
`.../runs/39520724067/job/118963631315`, `output.annotations_count: 7`; sibling jobs `success`. `output.title/summary`
were `null` (GitHub Actions jobs rarely fill them), so the failure message is **not** in the check object.

### 2.5 Failure evidence
`gh run view 39520724067 --json conclusion,status,jobs` gives the failing job + failing step name (`Format check`)
cheaply. `gh run view 39520724067 --log-failed` returned **717 lines / 72,766 bytes** for a single formatter failure
(`failed-log-excerpt.txt` is the first 60 lines); the actionable line was `** (Mix) mix format failed due to
--check-formatted.` at line 15, followed by a diff. A fix-thread must bound/tail this (see section 6).

## 3. Measured numbers

| Metric | Measured |
|---|---|
| `gh pr view` full fields (checks+reviews+comments), PR #565 | 1,044 ms wall, one GraphQL query |
| `gh pr view` slim fields (today's `PrStatus`) | 404 ms |
| REST `pulls/565/comments` | 470 ms; `commits/<sha>/check-runs` 476 ms; `pulls/531` 775 ms |
| `gh run view --log-failed` | ~2.3 s (incl. job listing), 72 KB |
| Conditional REST GET (`If-None-Match`, `pulls/531`) | **HTTP 304, `X-RateLimit-Remaining` unchanged (4841 -> 4841)**; an unconditional GET decremented by 1 (4841 -> 4840). 304s are free against the primary limit |
| REST response cache hint | `Cache-Control: private, max-age=60`; Events API `X-Poll-Interval: 60` |
| GraphQL cost of a combined query (PR scalars + last commit rollup (50 contexts) + 100 threads + 50 comments) | `rateLimit.cost = 1` |
| Primary limits | REST 5000/h, GraphQL 5000 points/h (`X-RateLimit-Limit: 5000` both) |
| Webhook delivery latency | **not measured** (no scratch repo). GitHub documents deliveries as near-real-time (typically seconds); [UNVERIFIED] |

`gh pr view` has no ETag path: it always issues GraphQL (no 304). Only the REST path can be made conditional.

### Polling cost model (N open PRs, interval T)
Requests/hour = (requests per sweep) * (3600 / T); for the per-PR rows that is N * (3600 / T) * calls-per-poll. GraphQL **points**/hour are a separate quantity (points per request x requests/hour) and the 5000/h budget is counted in points for GraphQL and in requests for REST. With batch size M, a sweep issues ceil(N/M) requests, not N.

| Strategy | N=5, T=60s | N=20, T=60s | N=20, T=300s |
|---|---|---|---|
| Full `gh pr view` + threads (2 GraphQL pts/PR) | 600/h (12%) | 2,400/h (48%) | 480/h (10%) |
| One combined GraphQL query per PR (cost 1) | 300/h (6%) | 1,200/h (24%) | 240/h (5%) |
| **Batched** (batch size M >= N, one request per sweep): requests = ceil(N/M) * 3600 / T | 60 req/h | 60 req/h | 12 req/h |
| ...same, GraphQL points (cost ~ ceil(M*nodes/100) per query; measured cost 1 per **single-PR-sized** query) | <= ~300 pts/h | <= ~1,200 pts/h | <= ~240 pts/h |
| REST `pulls/N` with ETag, steady state (mostly 304) | ~0 charged; 304s are free; one 200 per actual change | same | same |

Percent is of 5000/h. The batched points row is an upper bound assuming each aliased PR costs what a single-PR query costs; the cost of an actual aliased multi-PR query was **not measured** [UNVERIFIED] and must be measured (read `rateLimit { cost }`) before relying on batching. Secondary (abuse) limits: GitHub documents <= 100 concurrent requests, <= 900 points/min per
REST endpoint class, and 80 content-generating requests/min; a sequential per-PR loop with jitter is far below. These
secondary-limit figures are from documentation and were not exercised. The practical constraint is not the primary
limit but that **`gh` is a subprocess (~0.4-1 s per call)**: 20 PRs x 1 s serial = 20 s of wall time per sweep.

## 4. Comparison

| Concern | A: gh/GraphQL polling | B: webhooks |
|---|---|---|
| Reachability | Outbound only. Works behind NAT, laptop, local-first | Needs inbound public HTTPS: tunnel (cloudflared/ngrok/smee), or public host. Foreman is typically not reachable. Verified: the repo has no hook configured |
| Auth | Existing `gh` login; scopes `repo` (`read:org` irrelevant, `workflow` not needed to read runs). Fine-grained PAT: Pull requests: read, Checks: read, Commit statuses: read, Actions: read, Contents: read | Webhook secret (`FOREMAN_GITHUB_WEBHOOK_SECRET`, already supported, fails closed) + repo admin to create the hook; one hook per repo (or org/App) |
| Latency | 0..T (+ ~1 s call). Floor set by T, which cost limits to ~30-60 s | Seconds [UNVERIFIED] |
| Rate cost | 1 point per PR per poll (section 3); 304s free on REST | None against the primary limit |
| Review comments / threads | Needs a **second call** (REST inline comments or GraphQL `reviewThreads`); `pr view` lacks both | Event carries the one comment, no thread/resolved state; a fix-thread still has to fetch the full set |
| Failing check detail | URL only; needs `gh run view` for text | `check_run` body: name, conclusion, `details_url`, `output`; text still needs a fetch |
| Conflict file list | Not provided by either; needs local `git merge-tree`/merge attempt | `pull_request.mergeable_state` only; no file list |
| Missed delivery / offline server | Self-healing: next poll sees current state | Lost unless redelivery; GitHub does not retry failed deliveries automatically (manual redelivery / `X-GitHub-Delivery` + Deliveries API) |
| Ordering | Observes state, not transitions: no ordering problem, but intermediate states (fail->fixed within T) are missed | Out-of-order delivery possible; must key on `head_sha`/ids, not arrival order |
| Fork PRs | Works (`gh pr view` on base repo URL; verified on #531). Head repo differs: `headRepository.nameWithOwner = bautrey/foreman`, `maintainerCanModify: true` | Works for base-repo hook; `pull_request_review*` delivered. **Secrets/`GITHUB_TOKEN` are read-only for fork workflow runs**: unrelated to the source but affects what CI reports |
| Terminal runs | Poll set is built from non-terminal state; trivial to stop | Events keep arriving after the run is terminal; the handler must look up the run and drop/record |
| Complexity | One loop, `gh` already a dependency | Plug + secret + tunnel doc + per-event dispatch + dedupe + reconcile loop anyway |

## 5. Recommendation

**Primary: polling** (candidate A), implemented as a REST/GraphQL poll with adaptive interval and ETag on the REST
parts. **Fallback/accelerator: webhooks** as an opt-in, for users who can expose an endpoint; polling stays on as
reconciliation either way (a lost webhook must be healed by a poll, so polling is mandatory regardless of choice).

Reasons, all measured or code-verified above: Foreman is not publicly reachable by default; polling cost is 1
GraphQL point per PR-poll, e.g. 6-24% of the hourly budget at 60 s for 5-20 PRs and ~5% at 300 s; unchanged REST
resources cost nothing with `If-None-Match`; the existing webhook handler only understands `pull_request` and no
check/review event reaches it.

Outcome per the bead: **polling-primary** -> E9 builds the `PrWatcher` poll loop with adaptive interval + ETag;
extending `GithubWebhookController` for check/review events is **P3**, optional.

### Poll interval / backoff policy
- `PrStatus` stays the cheap structural fetch. `PrWatcher` adds one **combined GraphQL query per PR** (scalars +
  `commits(last:1).statusCheckRollup` + `reviewThreads` + conversation `comments`; cost 1 measured) so the checks,
  reviews, threads and comments need no second call. `gh api graphql` is used instead of `gh pr view` (which cannot
  return threads).
- Intervals per PR, driven by its last observed state: **30 s** while any check is `QUEUED|IN_PROGRESS` or
  `mergeable == UNKNOWN`; **60 s** for 10 min after a head push or a new review/comment; **5 min** (today's default,
  `pr_monitor.ex:38`) when all checks are terminal and nothing changed; **15 min** after 24 h idle. Reset to 30 s on
  any observed change (new `head_sha`, new check conclusion, new review/comment id).
- Add +/-10 % jitter, poll PRs sequentially (not concurrently), cap one sweep at 20 PRs/min.
- Backoff on `gh` error: 2x per consecutive failure up to 15 min, reset on success. On HTTP 403/429 read
  `Retry-After` / `X-RateLimit-Reset` and sleep to that instant; never retry inside the window. Treat
  `X-RateLimit-Remaining < 10 %` as a signal to widen all intervals 4x.
- `mergeable: UNKNOWN` is lazy computation, not an error: re-poll at 30 s, at most 3 times, then record `unknown`.
- Use REST `If-None-Match` for the `pulls/N` guard poll (304 = free) **only to detect changes to the PR object's own scalar fields** (head, state, mergeable, title). It is NOT a sufficient trigger for the GraphQL signal query: new reviews, comments, review threads and check runs are separate resources and are not guaranteed to change the `pulls/N` ETag [UNVERIFIED either way; not tested]. Schedule the GraphQL signal query independently on the interval ladder above (or poll reviews/comments/threads/check-runs with their own conditional requests), and additionally run it whenever the ETag changed or a check is non-terminal. ETags are not available via `gh pr view`.

### Webhook event allowlist (P3 accelerator)
`pull_request` (actions `synchronize`, `closed`, `reopened`, `ready_for_review`, `converted_to_draft`),
`pull_request_review` (`submitted`, `dismissed`), `pull_request_review_comment` (`created`, `edited`, `deleted`),
`pull_request_review_thread` (`resolved`, `unresolved`; both actions are listed in GitHub's webhook docs for this event; needed for `isResolved`), `issue_comment`
(`created`; filter to `issue.pull_request` present), `check_run` (`completed`, `rerequested`), `check_suite`
(`completed`), `status` (for StatusContext checks such as CodeRabbit). Reject everything else with 202 `ignored`
(existing behaviour). Verify the existing `X-Hub-Signature-256` HMAC first; use `X-GitHub-Delivery` as a replay key.
**[UNVERIFIED]**: live bodies of the check events.

| Need | Source | Second call? |
|---|---|---|

| Log URL | `detailsUrl` (`.../runs/<run_id>/job/<job_id>`) | no |
| Log excerpt | `gh run view <run_id> --log-failed` (72 KB for a formatter failure) or `gh api repos/R/actions/jobs/<job_id>/logs` | **yes**. Fetch lazily when a fix-thread is created, not on every poll; keep the last ~80 lines + the first `##[error]`/`** (` line, cap 8 KB |
| Annotations (file/line for compiler, credo, test failures) | `commits/<sha>/check-runs[].output.annotations_count` then `.../check-runs/<id>/annotations` (7, 12, 3 on #565) | **yes**; cheapest structured source when `annotations_count > 0` |
| Unresolved review threads with file/line | GraphQL `reviewThreads` (`isResolved == false`, `path`, `line` or `originalLine`, `isOutdated`) | no if folded into the combined poll query; `gh pr view` cannot provide this |
| Comment body text | `reviewThreads.comments.nodes[].body` (not fetched in the capture; add to the query) | no |
| Conversation comments | `pr view comments` / GraphQL `comments` | no |

| Conflict flag | `mergeable == CONFLICTING` / `mergeStateStatus == DIRTY` | no |
| Conflict file list | neither source; run `git merge-tree --write-tree --name-only <base> <head>` (or a trial merge) in the worktree | **yes**, local, free of API cost |

## 7. Normalized `PrSignal` (for E9 PrWatcher, consumed by E7 Overview and E10 notifications)

```elixir
@type check_conclusion :: :success | :failure | :cancelled | :timed_out | :skipped | :neutral | :action_required
@type check_state :: :queued | :in_progress | :completed
@type review_state :: :approved | :changes_requested | :commented | :dismissed | :pending

@type t ::
        %PrSignal.ChecksChanged{}       # one per (head_sha, check) transition
      | %PrSignal.ReviewSubmitted{}
      | %PrSignal.ThreadOpened{}        # unresolved thread / new inline comment
      | %PrSignal.ThreadResolved{}
      | %PrSignal.CommentAdded{}        # conversation comment
      | %PrSignal.MergeStateChanged{}   # CONFLICTING/DIRTY/BEHIND/CLEAN/BLOCKED/UNSTABLE
      | %PrSignal.HeadChanged{}         # new headRefOid (push or force-push)
      | %PrSignal.Closed{}              # merged | closed
      | %PrSignal.Reopened{}            # closed -> open again (webhook `reopened`, or poll sees state OPEN for a PR removed from the watch set)
```

Common envelope on every signal (all `@enforce_keys`; no defaults):
`pr_url :: String.t()`, `repo :: "owner/name"`, `pr_number :: pos_integer()`, `head_sha :: String.t()`,
`source :: :poll | :webhook`, `observed_at :: DateTime.t()`, `dedupe_key :: String.t()`, `is_fork :: boolean()`.

Per-type fields:

- `ChecksChanged`: `check_name`, `kind :: :check_run | :status_context`, `state`, `conclusion | nil`,
  `details_url`, `run_id | nil`, `job_id | nil` (parsed from `detailsUrl`), `workflow_name | nil`.
  Dedupe key: `"chk:" <> head_sha <> ":" <> to_string(kind) <> ":" <> check_name <> ":" <> check_instance <> ":" <> to_string(state) <> ":" <> to_string(conclusion)`,
  where `kind` separates a `CheckRun` from a `StatusContext` with the same name, and `check_instance` is a stable check-run identity (`run_id` + `run_attempt`, else `job_id`; `"-"` for a StatusContext, which has none). A **rerun** of the same SHA reuses the check name and is distinguished only by that instance, so it must be in the key (otherwise a same-state rerun collapses into the earlier event). [UNVERIFIED for reruns: not reproduced here.]
- `ReviewSubmitted`: `review_id` (use the **GraphQL node id on the poll path and map REST numeric id through
  `databaseId`**; choose one canonical form, recommended numeric), `author`, `state`, `commit_oid`, `stale :: boolean()`
  (`commit_oid != head_sha`). Key: `"rev:" <> review_id`. A review that later flips to `dismissed` is a new state and
  a new key `"rev:" <> id <> ":dismissed"`.
- `ThreadOpened`/`ThreadResolved`: `thread_id` (`PRRT_...`), `path`, `line | nil`, `original_line | nil`,
  `is_outdated`, `first_comment_id`, `author`, `body` (bounded). Key: `"thr:" <> thread_id <> ":open|resolved"`.
- `CommentAdded`: `comment_id` (numeric from `url` fragment on the poll path), `author`, `body` (bounded),
  `created_at`. Key: `"cmt:" <> comment_id`. Edited comments keep the id: include `updated_at` in the key only if
  edits must retrigger (recommended not to).
- `MergeStateChanged`: `mergeable :: :mergeable | :conflicting | :unknown`, `merge_state_status` (the 8 documented
  values + `:unknown`), `conflict_files :: [String.t()] | nil` (filled lazily by local `git merge-tree`).
  Key: `"mrg:" <> head_sha <> ":" <> merge_state_status`.
- `HeadChanged`: `previous_sha | nil`, `forced :: boolean() | nil` (nil on poll; known from webhook `forced` /
  timeline `head_ref_force_pushed`). Key: `"head:" <> head_sha`.
- `Closed`: `merged :: boolean()`, `closed_at`. Key: `"closed:" <> head_sha <> ":" <> merged <> ":" <> closed_at` (a close/reopen/close cycle on one SHA must not collapse).
- `Reopened`: `reopened_at`. Key: `"reopen:" <> head_sha <> ":" <> reopened_at`. PrWatcher re-adds the PR to the watch set on `Reopened` (and a poll that finds a previously-closed associated PR `OPEN` synthesises it), resuming polling at the 30 s interval.

Dedupe and ordering:
- Dedupe keys are content keys, not delivery ids, so a webhook and a poll reporting the same fact collapse to one
  event. `PrUpdate.command` already derives its command id from status + head SHA for the same reason; follow that
  pattern (`CommandRouter` deterministic event id).
- Never order by arrival. A poll emits current-state diffs against the last stored snapshot; a webhook is applied
  only if its `head_sha` **equals the current PR head** taken from a trusted snapshot (the stored poll snapshot or a fresh API read; process `HeadChanged` first). Git SHAs are identifiers, not ordered versions, so "newer" is never decided by comparing SHA values. Signals whose `head_sha` does not match the current head are recorded for history but must not start a fix-thread; if the stored head may be stale (webhook for an unseen SHA), refresh the snapshot with an API read and re-evaluate once.
- **Force-push [UNVERIFIED live]:** `headRefOid` changes, old checks/reviews stay attached to the old SHA, threads
  turn `isOutdated`. The `head_sha` in every key makes old-SHA signals inert. The timeline API exposes
  `head_ref_force_pushed` (event list in #565 had none: `committed` x4).
- `ReviewSubmitted` ids and `ThreadOpened` ids are stable forever; check names are stable only per SHA.

### Fork PRs and terminal runs
- Fork PR (#531 verified): `isCrossRepository: true`, `headRepository.nameWithOwner` differs, `statusCheckRollup`
  was only a StatusContext (CodeRabbit); Actions on fork PRs run with a read-only token and may need approval, so
  "no checks" is **not** "green". `is_fork` is part of the envelope; a fix-thread cannot push to a fork head unless
  `maintainerCanModify` is true (it was true on #531, false on #565 same-repo). Polling uses the base-repo PR URL
  and works unchanged.
- Terminal runs: PrWatcher's watch set comes from runs with `PrAssociated` and a non-terminal PR state. When the PR
  reaches `Closed`, remove it from the set (a `Reopened` signal restores it). If the **run** is terminal but the PR is still open (the E9-SP1 question
  of where watch state lives), keep polling at the slow interval; signals are appended and surfaced to E7/E10 but
  never auto-start a thread without an operator action.

## 8. Downstream effects

- **E9-S1-T1 (`PrStatus` extension):** add `checks`, `reviews`, `threads`, `comments`, `merge_state_status` to the
  parsed result; the one-query GraphQL form replaces `gh pr view --json state,...` as the source; keep typed errors.
  `reviewDecision` must treat `""` and `null` identically. Upper-case GraphQL enums vs lower-case REST enums must
  be normalised in exactly one place (AGENTS.md 5: one key/enum convention per boundary).
- **E9-S2 (`PrWatcher`):** poll loop with the adaptive policy above, REST ETag guard, rate-limit/`Retry-After`
  handling, `PrMonitor` becomes its slow reconciliation tier (or is absorbed).
- **E9-S2-T4 (webhooks):** demoted to P3 optional accelerator. Requires: allowlist in section 5, a tunnel doc
  (Foreman is not public), per-repo hook, redelivery handling. Today's controller ignores all but `pull_request`.
- **E9 "Address comments" fix-thread:** needs an explicit fetch step for review comment text/threads only if the poll
  query omits bodies; with the combined query it does not, but it **does** need the lazy log/annotation fetch and the
  local `git merge-tree` conflict-file step (section 6).
- **E7 Overview:** can show per PR: head_sha, aggregate check state, failing check names, unresolved-thread count,
  review decision (+ stale flag), mergeability, `is_fork`. Latency expectation to display: up to the poll interval.
- **E10 notification classes:** derive from signals: `checks_failed`, `checks_recovered`, `changes_requested`,
  `review_approved`, `new_comment`, `thread_unresolved`, `merge_conflict`, `pr_merged`, `pr_closed`. Because polling
  cannot see a fail->fixed flip shorter than the interval, `checks_recovered` must be computed from snapshot
  diff and not assumed to be preceded by a `checks_failed`.
