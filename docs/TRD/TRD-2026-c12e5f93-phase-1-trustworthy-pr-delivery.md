## 1. Context

Phase 1 of the SunStone software factory (umbrella `PRD-2026-b7c2e941`) makes a PR's quality evidence machine-verifiable and bound to the exact head SHA, publishes a risk record, and keeps every merge operator-approved. The operator accepted the Phase 0 engine decision on 2026-11-12 (extend the current event-sourced engine; no Temporal, Conductor or Pi Durable) with three preconditions and one design rule on Phase 1 code (PRD §5): P-1 `foreman-by6nl`, P-2 `foreman-tnlqt`, P-3 the durable idempotency store, and P-4, every Phase 1 effect keyed by head SHA. PR #862 (`c7e9929b`) recorded that acceptance, the precondition table and the disposition of every Phase 0 follow-up in `docs/decisions/phase-0-durable-execution-engine.md`, so PR 1 of this TRD is shipped apart from one column (TRD-001). This TRD plans the preconditions first (PR 2), then the evidence core, the required-checks policy, structured findings, the risk record, the publish effect, the gate and the visibility, and last the adversarial suite.

Every design claim in §5 carries a `path:line` read on disk in the worktree on 2026-11-12: first at `0699076a`, then re-checked at `c7e9929b`, the base of this branch (`git diff 0699076a c7e9929b` touches only `docs/decisions/phase-0-durable-execution-engine.md`, +65/-1, and the branch's own commits add only the PRD and this TRD, so no code line moved). The scout reports that preceded this TRD were treated as leads: several of their claims were re-read and some corrected (see §14). Two independent source-checked reviews of version 1.0.0 (citations and premises; design soundness and safety) then found a stale PR 1, two design blockers and a number of majors; each finding was opened at its cited line before the text changed, and §14 lists what remains a gap. Where the repository has no evidence, the TRD says so and puts the choice to the operator (§11). ## 2. Scope and Non-Goals

In scope: the three preconditions and the head-keyed effect rule (REQ-001 by way of PRD §5), including an explicit path for the effect keys of a terminal run, per-head check evidence from GitHub and its invalidation (REQ-001, REQ-005), the `required_checks` setting, the typed evaluator and the operator waiver (REQ-001), structured review findings (REQ-002), the versioned risk record (REQ-003), the keyed, redacted PR comment and the operator command that publishes it or retries it (REQ-003), the approval gate and the visibility of evidence, reasons and next actions (REQ-001, REQ-004, REQ-005), the two folded follow-up beads `foreman-rsbx1` and `foreman-87h5g`, and the adversarial suite and exit record (REQ-004, all).

Non-goals: auto-merge (Phase 2); idea-to-spec (Phase 3); server-run command checks (deferred, §6); a new workflow-manifest key (`PhaseSpec.@fields` is closed); any change to `Review.Verdict` and `Review.Analyzer` (a bead-bound concept, kept separate); an authenticated approver login (the approver identity stays a claim checked against `ApproverAuthorizer`'s list, as for `merge_approve`); trusting a webhook payload as evidence (a webhook only asks for a re-read); re-running a review for a completed run; re-checking evidence after an approval is given (approval is a point-in-time decision, §14); a per-project sensitive-path table (the one in §11 is v1 for this repository).

## 4. Binding Design Constraints

From `AGENTS.md` and `docs/standards/constitution.md`; they apply to every task.

- Only `CommandRouter` appends to the EventStore; aggregate handlers return event specs. Every domain event is a module in `lib/foreman_server/events/` with `@enforce_keys` and `@type t`; adding the module is its registration; new fields on an existing event are optional so old streams decode. Whether an older build can read a stream written with a new field depends on which of its readers decode strictly: `EventCodec.decode!/2` rejects an undeclared field and an unregistered event type, the Run aggregate and the PR projections read raw maps (rollback, §13).
- Aggregate handlers stay deterministic and network-free: the actor re-runs `handle_command/2` on a version conflict (`run_pr_merge.ex:7-12`). Every GitHub read happens in `CommandGateway` or an observer before dispatch, and every input a decision needs (the project's policy, the observation it relies on, the time) arrives in the command payload: a handler reads no clock, table or network for a decision, so a replay gives the same answer.
- Typed boundaries (AGENTS.md §5): result payloads are structs with `@enforce_keys`; no catch-all that turns an unknown value into success; absent is not malformed; one key convention per boundary, normalised once; never insert `nil` for an absent key.
- The merge gate and everything that loosens it are operator-only: `merge_approve`, `run.pr.merge` and the new waiver are never MCP tools or agent paths (`mcp/no_merge_tool_test.exs` forbids the words merge and approve in tool names and descriptions; `operator_only_pr_commands_test.exs` pins the command lists).
- The workflow vocabulary is closed; the PR base is the branch the run was cut from, with no default.
- Documentation Gate: a task that adds, removes or renames an externally visible identifier is listed in TRD-027's list, which updates `CLAUDE.md`, `README.md`, `docs/user-guide.md` and `docs/cli-reference.md`.
- Tests: a failing test is a failed build. Run one file with `devbox run -- bash -c 'cd packages/foreman_server && MIX_ENV=test mix test <path>'`; recovery and effect tests are `async: false`.

## 6. Architecture Decision

Decision: extend the current engine (the operator's Phase 0 decision) with a per-head evidence record folded into the Run aggregate, a deterministic evaluator read by the approval gate, and a keyed, redacted PR comment. Four things were considered.

- **A. Server-observed GitHub evidence, decided in the aggregate (chosen).** Check results come from the GitHub rollup in the same `gh pr view` response that names the head. The aggregate records them, so `merge_approve` decides from folded state plus the context the gateway puts in the command, and stays deterministic. The cost is more events and a second fold (the projection), kept equal by one shared fold module.
- **B. Server-run command checks (deferred).** They would run project code in a checkout of the head on a host whose filesystem and network the Phase 0 execution profile records as unenforced. Revisit in a later phase with an enforced profile.
- **C. A model-only rubric (rejected).** A model's level cannot be reproduced, so it cannot be tested or audited; the model may only raise the deterministic level (AC-003-5).
- **D. Evidence held outside the aggregate (rejected).** An evaluator that reads the projection or GitHub inside `merge_approve` is not deterministic on replay and is not network-free (`run_pr_merge.ex:7-12`); one that reads a clock to apply a freshness window has the same flaw, so the time and the policy come in the payload.

**Components.** `PrEvidence` (new): the evidence sub-record, one fold used by both `PrWatch.apply_event/3` and `PrWatchFold.apply_event/3`, `evaluate/2` (pure over the folded evidence and a context `%{head_sha, policy, now_ms, checks_ref}`), `evaluate_checks/2`, `project_policy/1`. `PrRisk` and `PrRisk.Rubric`: the judgement parser and the pure rubric. `PrReport`, `PrReport.Publisher` and `GitHub.PrComment`: the rendered, redacted comment and its write. `GitHub.PrLookup`: the PR lookup (`find/4`, `find_open/3`). `Reconcilers.PrComment`: the reconciler of the new effect class. Changed: `PrStatus`, `PrObservation`, `Observer`, `PrWatch`, `Run`, `CommandGateway`, `RunPrMerge`, `Effect`, `KeyStore`, `Reconciler`, `BootReconciliation`, the settings vocabulary, the DTO, `ProjectionStore.init/1`, Overview and the dashboard.

**Data flow.** An observation (poll, webhook or the gateway's own read at approval) yields one `PrStatus`; `PrObservation.commands/6` turns it into `run.pr.update`, `run.pr.checks` (every check, the policy, and an `evidence_digest` beside the unchanged notification `digest`) and `run.pr.risk` commands; the aggregate folds them into `evidence`. At finalisation the review artifact is parsed once into `run.pr.findings` (findings and judgement, agent-authored claims bound to the reviewed head). `merge_approve` is decided in the aggregate from the command payload and folded state only. At approval the gateway reads the live PR (`RunPrMerge.observe_head/3`, a new function that returns the `PrStatus`; `verify_head/3` stays a wrapper that returns `:ok | {:error, term}`) and the project's current `required_checks` (`PrEvidence.project_policy/1`), dispatches a forced fresh `run.pr.checks` for the named head with `run.pr.update` and `run.pr.risk` (its command id carries a nonce, so the digest-equality rule that silences an unchanged PR, `pr_observation.ex:134-139`, cannot swallow it, and the observation has its own `observed_at`), and rewrites the payload with a gateway-owned `evidence` map (`policy_required`, `policy_version`, `checks_ref`, `now_ms`; an `evidence` key supplied by the operator is dropped). When the gate is not pending, `verify_head/3` reads nothing and returns no `PrStatus` (`run_pr_merge.ex:86-87`), the gateway dispatches nothing, and the aggregate refuses with its own typed error (`:merge_gate_already_approved` or `{:merge_gate_not_found, :run}`, `aggregates/run.ex:1275-1281`). A project with no `required_checks` gets the answer `:off` and approval proceeds as today; a policy that cannot be read (`{:policy_unavailable, reason}`) refuses the approval and is never read as off. The handler evaluates `PrEvidence.evaluate/2` over the folded evidence and that context for `approval.head_sha`, before `PrGate.record_approved` (`aggregates/run.ex:940-948`: that call approves the gate in the ETS-backed `MergeGate`, `pr_gate.ex:82-88`, so the evaluation comes first and a refusal leaves the gate pending): checks count only when they were observed for that head under that `checks_ref`; findings, risk and waiver count only for that head. The inputs of the decision are recorded on `MergeGateApproved.evidence`; a refusal is the typed `{:evidence_ineligible, head_sha, codes}` carrying the same inputs and appends nothing, because a refusal of a pending gate changes no state (the gateway logs it and emits telemetry). Clearing `required_checks` takes effect at the next approval, with no observation needed. The publisher reacts to `PrRiskRecorded` and to `PrReportRequested` (the operator's `run.pr.publish_report`) and writes one comment through the keyed `pr_comment` effect.

**Head invalidation.** When an event brings a head different from the record's non-nil head, the fold resets the current-head observation fields (`checks_state`, `failing`, `checks_digest`, `review_decision`, `review_digest`; the projection record has `failing`, the aggregate record does not) and voids `evidence.waiver` unless the waiver is for the head the event brings; it keeps `evidence.checks`, `evidence.findings`, `evidence.risk`, `evidence.report` and `evidence.delivery_issue`, each with the head it was recorded for, and the evaluator compares that head with the head being decided: checks of another head are `other_sha`, findings `findings_other_sha`, risk `risk_other_sha`, and a report is shown stale. A findings record that is `absent` or `malformed` stays `findings_absent` or `findings_malformed` (or `findings_legacy_format`) whatever the head, so a head move never turns a non-waivable defect into a waivable one. Per surface: the fold (reset, TRD-007); the DTO (evidence of another head is labelled stale, TRD-023); the published comment (it names its head and digest; a new head edits it, TRD-021); the waiver (dropped with the head, TRD-012); the approval (re-held by the existing `run.pr.rehold`, `command_gateway.ex:177-189`); the effect (keyed by head, P-4: a settled key is re-run, `effect.ex:159-182`).

**What must be on.** The gate does not depend on monitoring: at approval the gateway re-reads GitHub, forces a fresh checks observation for the named head and passes the policy it has just read (TRD-022), so a stable green PR approved hours after its last observation is eligible. The PR monitor (`FOREMAN_PR_MONITOR_ENABLED=true`) or a verified webhook is needed only for the status to show a head change, a new check result or a published report without anyone approving; the doctor reports it (TRD-009, TRD-010). The 900-second figure of §11 is a display hint for the status, not an input of any decision.

## 7. Design Principles for Every Task

- A proof task is a real run: its `-TEST` sibling states the mutation that must make it fail, so a green test cannot pass vacuously.
- No stub reconciler, no fake backend result, no placeholder event.
- New event fields are optional; existing streams must replay. Each event change includes a codec round-trip test.
- Every Phase 1 effect is keyed by head SHA (P-4), registered with a reconciler before it can run, and refuses an undecided key (P-1); an effect whose outcome never gates a run and whose repeat is harmless (the comment) is declared repeatable and is the one exception.
- A decision input arrives in the command payload (the policy, the observation reference, the time); an aggregate handler reads no clock, table or network for a decision.
- Machine evidence (check results, size, changed paths, the base branch) is trusted only when Foreman read it from GitHub in the same response as the head it is bound to. Review findings and the model judgement are agent-authored claims read from an artifact the agent controls: they are inputs bounded below by the machine rules, never proof that a check ran, and the operator's approval is the real control. Agent-run output and a prompt claim are never evidence.

### PR 6: Risk is a versioned, recorded classification bound to the head

**Shippable State:** For each head the run stream holds a risk record (HIGH, MEDIUM or LOW, `rubric_version`, rationale, evidence, unresolved findings, human-review instructions) computed by a deterministic rubric. The machine-observed inputs (required checks, changed paths and size, the base branch) set the floor; the review findings and the model judgement are claims the review agent wrote and can only raise the level above that floor. A missing, malformed (including more than one block), other-head or ambiguous input gives HIGH. A missing judgement is HIGH by default, so a well-formed LOW block removes that default and nothing else: the level is bounded below by the machine floor and by nothing the agent wrote. The record is written for every observed PR, gate on or off, and LOW is unreachable where the gate is off, `required_checks` is `[]` or a waiver was needed. Nothing publishes the record before PR 7 and nothing enforces `risk_missing` or `risk_other_sha` before PR 8.

Phase 1 treats a truncated rollup as not eligible (`checks_truncated`) and an incomplete file list as HIGH; it does not page to read more.

## 11. Open Technical Decisions

Eleven decisions need the operator. Each is a proposal with its basis; the repository has no evidence for the numbers, so none is presented as measured. TRD-026 records the operator's answer to each.

1. **Rubric thresholds.** Proposed in the table below; the level is the maximum over all rows and the model can only raise it. The PRD names the inputs (size in lines, sensitive paths, required checks, findings, the base branch, the judgement) and gives no number: every number below, the changed-files row (10 and 25 files) included, is a proposal of this TRD and not a PRD input.
2. **Gate semantics.** `merge_approve` is refused with a typed reason unless the evidence for the head being approved is eligible or explicitly waived (still operator-approved and SHA-pinned). The decision uses only the command payload and the folded state: at approval the gateway reads the live PR and the project's current policy and forces a fresh checks observation, so the aggregate reads no clock, table or network (§6). Basis: PRD REQ-004 and the operator's decision on waivers.
3. **Observation.** Turn the PR monitor on for any deployment that gates a project (the webhook is optional): the status then shows a head change, a new check result or a published report without anyone approving, and the doctor warns when the monitor is off. The gate does not depend on it: a stable green PR approved hours after its last observation is eligible (TRD-022).
4. **Sensitive-path table v1** (below). It lists paths of this repository, so another repository gets only the machine rules until a per-project table exists; a file renamed out of a listed prefix reports only its new path (probe, §5), so that rename is not seen. 5. **Waivable reasons.** `no_checks_configured`, `missing`, `skipped`, `findings_absent`, `findings_legacy_format`, `findings_other_sha`. A waiver is for one head and is lost when the head moves or the run is reset (§13). `findings_legacy_format` is waivable because a run that completed before the review prompts were refreshed holds an earlier-format block and no command re-runs a review for a completed run (§13); `skipped` is waivable because a standing `allow_skipped` (item 9) is weaker than a per-head waiver with a reason. An absent or malformed model judgement is HIGH (conservative; it makes LOW rare until the review prompts reliably emit the block).
6. **Default per project.** The gate is off until `required_checks` is set; publication follows the gate switch. Recording does not: the check list, the findings and the risk are recorded for every project (§13).
7. **Durable-store guard.** Enabling `required_checks` is refused (not only warned) while the idempotency store is ETS-only; the guard's switch `:require_durable_store_for_gating` is true in `config/config.exs` and false in dev and test. 8. **Freshness window.** The 900-second figure is a display hint only: the status labels check evidence older than 900 seconds `stale`, and no decision reads it. The gate decides on evidence forced for the named head at approval, so age is never a reason (§6).
9. **Skipped and neutral required checks.** `PrStatus` counts SKIPPED and NEUTRAL as passing in `checks_state` (`github/pr_status.ex:144`), and GitHub reports a job skipped by a job-level `if` as skipped (PR #862, §5). Proposed: a required check whose conclusion is SKIPPED or NEUTRAL is not passing (reason `skipped`) unless its `required_checks` entry carries `"allow_skipped": true`; the evaluator reads the conclusion and not `checks_state`. Basis: a skipped required job says no test ran. Cost: a project whose required jobs are legitimately skipped on some PRs (a docs-only change) sets `allow_skipped` on those entries or waives the reason.
10. **Truncated check list.** `PrStatus` computes `checks_state` over all checks and keeps the newest 100 (`github/pr_status.ex:334-347,539-541`). The doctor says so.

The sweep could not decide the effect key of a terminal run: it records `effect_retried` through `run.recovery_attempt`, which the aggregate rejects on a terminal run (`aggregates/run.ex:759-766`), so a crash in the `gh pr create` window followed by a failed run left the key refused for good; PR 2 writes the decision first and the audit event second and gives each verdict a path (TRD-003, TRD-039). The checks digest hashes the rollup state and the failing checks, not the passing set (`pr_observation.ex:43-51`), so a separate `evidence_digest` carries every check. `record_intent/3` is in `idempotency/effect.ex` (`:235`, `:245-246`), not in `key_store.ex`. `PhasePR` has a closed-PR guard (`:matching_pr_closed`) that a lookup helper must keep (TRD-038). `gh pr list --head` matches the branch name whatever repository the head is in, so a same-named fork PR must not be adopted (TRD-004, probe in §5). A project with the gate off is not unchanged (§13), and the binary rollback boundary is the first deployment of PR 3, not the first gated PR (§13).
- **Not built.** Sweep ordering before executors resume (the third item of `foreman-by6nl`): a `started` key of a run whose executor is alive is not orphaned by the sweep (`boot_reconciliation.ex:836-842`), so it stays refused until that executor ends and a later scan or a restart decides it. A refusal casts an on-demand scan, coalesced to one further scan; it does not remove this wait. A `branch_push` key with the verdict `done` or `unknown` on a terminal run stays refused (limitation (xix) is closed only for `not_done` and for the PR itself, TRD-039); no clearing command exists for it.
- **Terminal-run keys.** For a terminal run the sweep decides `not_done` and the next Create PR works; for `done` or `unknown` the key stays refused (`effect_undecided` before the sweep decided it, `effect_unresolved` after), but the operator's Create PR is adopted through the lookup when GitHub already has the PR, and an operator who opens a missing PR by hand has it adopted the same way (TRD-004, TRD-039). Advisory classes (the PR comment) never block a run (TRD-039).
- **Adoption needs the head to equal the tip.** P-2 adopts an open PR only when GitHub reports it is not from a fork and its head equals the tip just pushed; a same-branch PR with another head is refused with `{:pr_lookup_mismatch, url, expected, actual}` and a fork PR of the same branch name is ignored. The operator closes or aligns such a PR by hand.
- **Findings and the model judgement are agent-authored claims.** The parser only observes that exactly one marker pair is present, that it parses and which head it is for; what the findings say is the agent's claim. The machine-observed inputs (required-check results, changed paths and size, the base branch) are the floor, and the findings and the judgement can only raise the level above it. A missing judgement is HIGH by default and a well-formed LOW block removes that default, so the judgement is raise-only relative to the machine floor and not to the no-block baseline; `findings: []` is the agent's say-so. An agent that controls the artifact can understate both: the operator's approval is the real control. The artifact also chooses the PR's head branch today (the `FOREMAN_BRANCH=` override, `workflow/auto_pr.ex:163-169,182-197`), an adjacent instance of the same limit that Phase 1 does not change. How often agents obey the write-once prompt rule (one block, markers never quoted) is `[UNVERIFIED]`; a block that breaks it is `findings_malformed`, which has no waiver, and its exits are a new run or the gate off for the project.
- **Approval is a point-in-time decision.** `run.pr.merge` needs an approved gate and re-checks that the PR is open and that its head is the approved one (`aggregates/run.ex:1260-1267`; `run_pr_merge.ex:185-197`); it does not re-check checks, findings or risk, so a check that turns red on the same head after approval still merges (a Phase 2 concern). No command re-runs a review for a completed run (`run.reset` is accepted from `failed`, `stuck`, `blocked` and `paused` only, `aggregates/run.ex:1432-1436`).
- **Out-of-order observations** can rewind the head of record; the effect is fail-safe (a refusal or a re-hold), not fixed here.
- **`status_context` is weaker than `check_run`.** A status context has no creator or app (probe), so anyone who can create statuses can satisfy an entry of that kind; an entry names its kind, and the operator chooses `check_run` where the source matters.
- **Truncated rollup.** `PrStatus` computes `checks_state` over all checks but keeps the newest 100 (`github/pr_status.ex:334-347,539-541`); a required entry outside the kept list makes the checks not eligible (`checks_truncated`, never waivable, §11). No paging past 100 for checks or files is built.
- **Matrix jobs.** GitHub lists a skipped matrix job under its unexpanded name (`foreman_server_p${{ matrix.partition }}` on PR #862, §5), so a required entry for one partition reads `missing` on such a PR (waivable); there is no matching by pattern.
- **Sensitive-path table v1** is this repository's list: another repository gets only the machine rules; a file renamed out of a listed prefix reports only its new path (probe, §5); a file beyond the first 100 is not listed and the PR is HIGH on incomplete evidence. LOW is unreachable for a project with the gate off, with `required_checks` of `[]`, or with a waiver.
- **Secondary-repository PRs are always HIGH.** `State.base_branch` stays the primary's (`aggregates/run.ex:409-421`), so a secondary PR's base is compared with the primary's, and findings are recorded for the primary PR only, so it reads `findings_absent` and needs a waiver. An operator-created PR (Create PR) has no findings record.
- **Findings are re-needed after every fix push:** `findings_other_sha` makes the PR ineligible until the review is re-run or the reason is waived, and no phase re-runs the review for a fix push, so risk is HIGH until findings are recorded for the new head; a phase PR whose local tip is ahead of the pushed head reads `findings_other_sha`.
- **A waiver on a terminal run is accepted.** The waiver clause sits in `Run` beside `merge_approve`, which has no terminal-run guard (`aggregates/run.ex:936-967`), and does not call `allow_pr_lifecycle_on_terminal_runs` (`:1305-1321`); a gate is normally pending on a completed run. The PrWatch system commands are accepted on a terminal run through `@pr_watch_types` (`:874-878,1316`).
- **The durable-store re-check at approval** (TRD-022) ties a gated project's approvals to the key-store database; clearing `required_checks` is the way out (§11).
- **A reset run has no gate** while its PR record survives in the projection (§13); this is today's behaviour and is derived from the code read, not exercised.
- **Limitation (xviii) stays open.** A refused primary-repo PR leaves no record: failures are recorded only when `secondaries != []` (`workflow/run_executor.ex:2557-2565`). TRD-008 and TRD-033 record a failed ready signal for a PR that exists; a refused creation has no PR URL to attach an event to. A route not taken: record the primary's failure for a single-repository run through `RunRepoPrFailed` (`workflow/repo_pr.ex:72-77` accepts the primary's id), but a single-repository run reclaims its worktree (`workflow/run_executor.ex:4672-4674`), so `run.pr.retry` could not resolve it; that needs an operator decision.
- **Event volume.** Each change of a PR's check set appends one `PrChecksChanged` for every watched PR of every project, gate on or off (§13); the volume was not measured.
- **AC-001-1 holds for check runs only** (PRD 1.1.1): a status context carries no completion time (probe, §5) and server-run command checks are deferred (§6).
- **PRD §3 item 4** lists the `gh` write calls as `pr create`, `pr merge` and `git push`; `gh pr edit --body` is a fourth (the multi-repository cross-link, `workflow/repo_pr.ex:184-186`). No comment or review write exists.
- **Proposals, not measurements:** the thresholds (the file-count row included), the sensitive-path table, the waivable set and the rule for skipped checks; the 900-second figure is a display hint and not a decision input (§11).
- **Unverified:** every `gh` write of a comment, the create and the update (TRD-019 probes them on a scratch PR), and what they print; the strict-decode readers not read, and the supervisor's restart behaviour after the `ProjectionStore.init/1` stop (§13); that the development-configuration test of TRD-005 can evaluate `config/dev.exs`; `foreman init --force` beyond the installer code read (§13); how often agents obey the write-once prompt rule; the `go test` invocation; that a second reader would find every cited line unchanged (line numbers drift).
- **A run with no review phase** records `absent` and needs a waiver when the gate is on.
- **Large PRs:** `gh pr view --json comments` pages every comment (26 s for 908), which slows the reconciler and `list/2`; over 100 changed files the list is incomplete and the rubric gives HIGH.
- **Operator-only is a convention of the API token:** whoever holds the token can send `run.pr.waive_evidence` and clear `required_checks`; one bearer token authorises both the HTTP API and the MCP server (`mcp/auth.ex:43-60`), so the MCP refusal of TRD-028 is defence in depth; the approver identity is a claim checked against `ApproverAuthorizer`'s list, as for `merge_approve`.
- **Constitution §5:** new events, new commands and a new CLI verb are changes that need the operator's approval (`docs/standards/constitution.md:132-140`); this TRD is the artifact for that review.
