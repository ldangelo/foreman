# TRD: Foreman × Beads Rust — Task-Provider Integration

## 1. Executive Summary

This TRD turns PRD `PRD-2026-48f7b420-foreman-beads-task-provider` (v1.0.1, readiness 4.0, 19 REQs, 64 ACs) into a concrete implementation plan for the `ForemanServer.TaskProvider` boundary and its production `BeadsAdapter`. The PRD micro UUID `48f7b420` is preserved unchanged so PRD/TRD artifacts correlate 1:1. The label prefix changes from `prd-` to `trd-` (`trd-foreman-beads-task-provider`); the label is display-only and all cross-references use the micro UUID.

The implementation lives under `packages/foreman_server/` (the Fortium foreman repo's existing Phoenix package — paths in this TRD are package-relative). The slice is supervised by the existing `ForemanServer.Application` supervisor tree; the new supervisor(s) are children, not a parallel OTP application.

The TRD delivers, in four vertical slices:

1. **PR 1a** — Foundation: `TaskProvider` behaviour (11 callbacks), `BrRunner` boundary (`SystemBrRunner` is the sole `System.cmd("br", ...)` site; `BrRunnerMock` lives at `test/support/` for Mox), typed `ProviderError` with closed-vocab codes + 7-key allowlist context (includes `missing_fields` for `SCHEMA_VALIDATION_FAILED` from local validation), `JsonSchemaCache` (cached schemas + 24h refresh + contract-version gate), `ConcurrencyLimiter` (`max_in_flight: 4` + `BR_TIMEOUT_QUEUE` on queue timeout), and 3 surgical config updates (mix.exs `Mox` dep + `elixirc_paths`; `config/config.exs` `br_runner` + `task_provider` config; `config/test.exs` `br_runner` → `BrRunnerMock`). v1 has no `SensitiveFieldScrubber` — REQ-019 redaction is emission-only: argv passed to `br` is unscrubbed (original); `scrub_argv/1` (defined in PR 1b's TRD-023) produces a verbatim-copy with sentinels replaced for telemetry/log/ProviderError.context only. PR 1a's REQ-019 obligation is limited to struct shape (TRD-002, TRD-005) since no argv flows through PR 1a code at runtime.
2. **PR 1b** — Adapter: `BeadsAdapter` skeleton with all 8 operational callbacks (`list_ready/2`, `get/2`, `claim/3`, `complete/3`, `fail/3`, `reopen/3`, `set_priority/3`, `add_dependency/3`) raising `{:error, :not_implemented}`; the 3 metadata callbacks (`name/0`, `capabilities/0`, `available?/0`) return live values. `preflight_database/2` pre-flight check via the `ConcurrencyLimiter`. All 8 per-callback implementations route through `CodeMap` and validate payloads against the `JsonSchemaCache`.
3. **PR 2** — On Foreman server boot, `Workflow.BootReconciliation` invokes `BeadsAdapter.reopen/3` against orphaned claims (reopens with `"foreman-run-reconciled"` transition-comment, emits `[:foreman_server, :task_provider, :reconcile, :reopened]`), no-ops on matching `RunStarted` in_progress (emits `[:foreman_server, :task_provider, :reconcile, :healthy]`), and emits `[:foreman_server, :task_provider, :reconcile, :already_closed]` for in-progress run + already-closed issue pairs. `foreman doctor task_provider` reports per project: provider_id, contract_version, `br --version`, `br capabilities --json`, sample `br ready --limit 1 --json`, schema-validation failures, plus `DATABASE_NOT_FOUND` + `stderr_byte_count` + `redacted_fields`. Docs (`docs/user-guide.md`, `docs/cli-reference.md`, `README.md`, `CLAUDE.md`) updated per `foreman-doc-gate`.
4. **PR 3** — Three architecture tests fail the suite on any direct br call outside `SystemBrRunner.cmd/3`, any out-of-`task_providers/` adapter alias, or any `%ProviderError{}` construction outside `BeadsAdapter.CodeMap.build_provider_error/3`. Side-channel capture tests (Logger/IO/telemetry/ProviderError) verify REQ-019 with sentinels. AC-005-4 property-based isolation test verifies two concurrent projects with different `database_path` values never cross-leak paths in captured br argv (start barrier + per-pid `Mox.allow/3` + `Task.async`/`Task.await_many` + exact-argv-count assertion).

The slice is intentionally bounded: it integrates the new modules into the aggregation pipeline (Project aggregate's `config` projection, RunExecutor's lifecycle hooks, BootReconciliation, doctor) but does not migrate any existing functionality. Existing Task/Run/Project aggregates that do not opt into `task_provider` continue to operate exactly as before.

## 2. Architecture Decision

### 2.1 Alternatives Considered

Three options were prepared. The skill mandates a user pause for selection; the recommended option was Option C (PRD-as-specified), and that decision is recorded here. The alternatives are documented for posterity.

#### Option A — Simplest (REJECTED)

Single `ForemanServer.TaskProviders.Beads` module that shells out to `br` directly from the runner integration point. No behaviour, no adapter pattern, no mock, no registry, no closed-vocab error envelope. Caller calls `Beads.list_ready(project_id)` directly.

- **Pros:** Fewest files (~150 LOC). One module to read.
- **Cons:** Violates REQ-001 (no behaviour), REQ-002 (no capability declaration), REQ-004 (no registry), REQ-005 (no per-project isolation), REQ-006 (no compile-time BrRunner binding — every test must shell out to a real `br` or wrap the whole module), REQ-008 (no closed-vocab error envelope), REQ-013 (no architecture test), REQ-014-2 (no claim-before-dispatch), REQ-019 (no side-channel discipline). Net: violates ~10 Must/Should REQs.
- **Risk:** HIGH. The slice would need to be redesigned within two PRs.

#### Option B — Most scalable (REJECTED)

`TaskProvider.Registry` GenServer with per-adapter Process supervisor children, ETS-backed hot-swap registry, liveness heartbeats, runtime add/remove without restart, and a `TaskProvider.Supervisor` orchestrator. Adapter dispatch is dynamic — callers receive the module from `route/2` and invoke it.

- **Pros:** True multi-provider hot-swap. New providers drop in without restart. Capability surfacing is rich.
- **Cons:** Adds machinery the v1 PRD does not require (only BeadsAdapter exists). The PRD already mandates a `TaskProvider.Registry` GenServer (REQ-004) — Option B's distinguishing feature is *live, ETS-backed* registration, which is more sophisticated than the PRD's *boot-time* `Application.get_env`-driven registration. Elixir can dispatch to module variables natively via `module.fun(args)` or `apply/3` (no `Code.eval_string` required), so a dynamic registry does not inherently violate REQ-006 (compile-time binding is at the *BrRunner* subprocess layer, independent of the *adapter* dispatch layer). Still, the dynamism is unused at v1.
- **Risk:** MEDIUM-HIGH. The supervision tree real estate is 2–3x Option C's, and the extra machinery exists for hypothetical future providers.

#### Option C — PRD-as-specified (CHOSEN)

Single `ForemanServer.TaskProvider` behaviour with 11 callbacks; one production adapter (`ForemanServer.TaskProviders.BeadsAdapter`) that dispatches every callback through a commit-time-bound `@runner` module attribute (Mox cannot replace modules at runtime — the call site MUST be compile-time-bound to either `ForemanServer.TaskProviders.SystemBrRunner` or `ForemanServer.TaskProviders.BrRunnerMock`). `ForemanServer.TaskProviders.SystemBrRunner` is the sole `System.cmd("br", ...)` site in the entire `lib/foreman_server/` tree. `ForemanServer.TaskProviders.BrRunner` is the behaviour contract, reinstated under `lib/foreman_server/task_providers/` so the compile-time swap is a single Application env knob. `ForemanServer.TaskProvider.Registry` is a GenServ…

The lifecycle is partitioned cleanly by **invocation context**:

- **Post-execution (RunExecutor-driven):** `claim/3`, `complete/3`, `fail/3`. The runner fires `fail/3` on `TaskExecutionFailed`, which performs `br update --status open --transition-comment <reason>` per AC-015-2. The runner NEVER fires `reopen/3` — that would duplicate the fail transition on the same `br update --status open` outcome.
- **Crash reconciliation (BootReconciliation-driven):** `reopen/3` exists on the adapter exclusively for the orphan-reopen path (AC-017-2). BootReconciliation is the sole caller.

- **Pros:** 1:1 aligned with PRD. Follows the existing `AgentRuntime.BackendAdapter` / `AgentRuntime.AdapterCatalog` / `PiAdapter` pattern that already lives in the codebase. The shape is reproducible when a second provider (ADO, Jira, GitHub, Linear) lands: implement the behaviour, register it in config, ship. Architecture tests are naturally structural — the `System.cmd("br", ...)` scan is a single AST walk.
- **Cons:** Adds 18 library files + 1 test-support file + 8 test files (per-PR count below). The 11-callback surface is opinionated; future providers must conform to it.
- **Risk:** LOW. The implementation is bounded by what the PRD specifies; every AC has a directly-implementable test.

### 2.2 Chosen Architecture (Option C)

Plus surgical updates to 3 existing modules (`ForemanServer.Aggregates.Project`, `ForemanServer.Workflow.RunExecutor`, `ForemanServer.Application`).

#### 2.2.2 Data Flow

**Happy path (read — `list_ready/2`)**

```
caller (ForemanServer.Workflow.RunExecutor)
  │
  ▼
ForemanServer.TaskProvider.Registry.route(:list_ready, %{project_id: id})
  │ returns {:ok, ForemanServer.TaskProviders.BeadsAdapter}
  ▼
ForemanServer.TaskProviders.BeadsAdapter.list_ready(project_id, opts)
  │ resolve project.task_provider config → %{provider: BeadsAdapter, config: %{database_path: "/abs/path"}}
  │ validate database_path is absolute (Path.expand/1, then Path.type/1 == :absolute)
  │ acquire slot from ForemanServer.TaskProviders.ConcurrencyLimiter (max_in_flight: 4)
  ▼
@runner.cmd({:ready, %{database_path: "/abs/path"}}, %{database_path: "/abs/path"}, opts)
  │ if Mox (test): returns mock expectation
  │ if SystemBrRunner: System.cmd("br", ["ready", "--db", "/abs/path", "--json"], env)
  │   ├─ Port.open + spawn /bin/sh -c "exec 'br' 'ready' '--db' '/abs/path' '--json'"
  │   ├─ capture OS PID via Port.info/2
  │   ├─ SIGTERM after timeout_ms, then SIGKILL after 5s
  │   └─ return {stdout, stderr_byte_count, exit_code}
  ▼
parse JSON → validate against cached schemas (JsonSchemaCache.ready_issue_schema)
  │ if validation fails: ForemanServer.TaskProviders.BeadsAdapter.CodeMap.build_provider_error(CodeMap.ProviderErrorInput.from_local(:SCHEMA_VALIDATION_FAILED, "JSON does not match ready-issue schema", "Re-fetch br JSON or refresh cached schema", false, ["priority", "assignee"]), nil, 0)  (TRD-006 arity-3 contract; no br envelope here — local validation failure constructs the input; `missing_fields` flows into `ProviderError.context[:missing_fields]`)
  ▼
map to [%ForemanServer.TaskProvider.Issue{}]
  ▼
ForemanServer.TaskProviders.ConcurrencyLimiter.release/1
  ▼
{:ok, [%ForemanServer.TaskProvider.Issue{}]}
```

**Error path (claim race — `claim/3`)**

```
ForemanServer.TaskProviders.BeadsAdapter.claim(project_id, task_id, actor)
  │
  ▼
@runner.cmd({:update, %{subcommand: "update", flags: ["--claim", task_id, "--json"]}}, %{database_path: "/abs/path"}, opts)
  │ if br returns {error: {code: "NOT_CLAIMABLE", message: "...", hint: "...", retryable: false, context: br_raw_context}}
  │   ├─ br_envelope = %{code: "NOT_CLAIMABLE", message: "...", hint: "...", retryable: false, context: br_raw_context}  (parsed br error map; line 185)
  │   ├─ command = %{binary: "br", subcommand: "update", flags: ["--claim", task_id, "--json"]}  (structured invocation)
  │   ├─ stderr_byte_count = byte_size(stderr)  (drop the bytes; retain the count only)
  │   └─ input = ForemanServer.TaskProviders.BeadsAdapter.CodeMap.ProviderErrorInput.from_br_envelope(br_envelope)  (Layer-1 normalization: source = :br_envelope)
  ▼
ForemanServer.TaskProviders.BeadsAdapter.CodeMap.build_provider_error(input, command, stderr_byte_count)
  │ input.code "NOT_CLAIMABLE" is in the 12-row mapping table → dispatch to translate/3 (NOT translate_unknown/3)
  │ translate/3 (internal call, shown for clarity):
  │   ├─ retryable? = mapping-table value (false here); input.retryable? ignored by KNOWN-row policy
  │   ├─ Foreman.code = "NOT_CLAIMABLE"
  │   ├─ message = template closed on Foreman.code
  │   ├─ hint = template closed on Foreman.code
  │   └─ context = %{id: task_id, command: cmd, exit_code: 2, stderr_byte_count: 47, sanitized?: true, redacted_fields: []}
  │ returns: %ForemanServer.TaskProviders.ProviderError{code: "NOT_CLAIMABLE", message: "...", retryable?: false, context: ...}
  ▼
{:error, %ForemanServer.TaskProviders.ProviderError{code: "NOT_CLAIMABLE", message: "...", retryable?: false, context: ...}}
(ForemanServer.TaskProviders.BeadsAdapter.claim/3 returns this tuple verbatim — adapter is a thin factory caller; TRD-006 is the factory.)
(For UNKNOWN codes — e.g. a future `br` revision adds `CLAIMED_BY_FOO` — build_provider_error would dispatch to translate_unknown/3 instead, which preserves input.retryable? and passes input.message/hint through; the translate/3 internal branch shown above would not execute.)
```

**Post-execution lifecycle (RunExecutor) — claim → execute → complete (or fail)**

```
ForemanServer.Workflow.RunExecutor.start_run(run_id, project_id, task_id)
  │
  ▼
ForemanServer.TaskProvider.Registry.route(:claim, %{project_id: id})
  │ returns {:ok, ForemanServer.TaskProviders.BeadsAdapter}
  ▼
ForemanServer.Workflow.RunExecutor.claim(project_id, task_id, actor)
  │ resolves provider via registry
  │ provider.claim(project_id, task_id, actor)
  │ on {:ok, %Issue{assignee: actor, status: "in_progress"}}:
  │   emit [:foreman_server, :task_provider, :beads_adapter, :claim, :success]
  │   proceed to TaskDispatched
  │ on {:error, %ProviderError{code: "NOT_CLAIMABLE", ...}}:
  │   provider.list_ready(project_id, opts) ← retry once
  │   if the target task_id is back in the ready set: drop it from the dispatch set
  │   if not: emit [:foreman_server, :task_provider, :claim, :lost] and continue with claimed_by_other branch
  │ on {:error, %ProviderError{code: "CLAIMED_BY_OTHER", ...}}:
  │   surface ProviderError to operator; do NOT start the run; the project supervisor decides next steps
  ▼
[TaskExecutionCompleted]
  │
  ▼
ForemanServer.Workflow.RunExecutor.complete(project_id, task_id, run_id, artifact_path)
  │ resolves provider via registry
  │ provider.complete(project_id, task_id, %{run_id, artifact_path})
  │ on {:ok, :already_terminal} or {:ok, %Issue{status: "closed"}}: idempotent completion
  │ emit [:foreman_server, :task_provider, :beads_adapter, :complete, :success]
  ▼
  ── ALTERNATIVELY ──
[TaskExecutionFailed]
  │
  ▼
ForemanServer.Workflow.RunExecutor.fail(project_id, task_id, run_id, reason)
  │ resolves provider via registry
  │ operator_comment = reason["transition_comment"] || "foreman-run:<run_id>:<artifact_path>"
  │   ↑ deterministic default from RunExecutor; no operator input required
  │ provider.fail(project_id, task_id, %{run_id, transition_comment: operator_comment})
```

#### 2.2.3 Integration Points

The slice integrates with the existing aggregation pipeline at three points:

1. **`ForemanServer.Aggregates.Project`** — accepts and persists a `task_provider` block on `project.register` and `project.update`. The block is appended to the project's `config` projection map (KEY: `:task_provider`). REQ-003.
2. **`ForemanServer.Workflow.RunExecutor`** — adds 3 post-execution lifecycle hooks: `claim/3` before dispatch, `complete/4` on `TaskExecutionCompleted`, `fail/4` on `TaskExecutionFailed`. The hooks route through `ForemanServer.TaskProvider.Registry.route/2` (the runner NEVER aliases `BeadsAdapter` directly — REQ-013-2). The runner does NOT call `reopen/3`; crash-induced reopening is exclusively `Workflow.BootReconciliation`'s responsibility (REQ-017). REQ-014, REQ-015, REQ-016.
3. **`ForemanServer.Application` supervisor tree** — adds `ForemanServer.TaskProvider.Registry`, `ForemanServer.TaskProviders.JsonSchemaCache`, `ForemanServer.TaskProviders.ConcurrencyLimiter`, and `ForemanServer.Workflow.BootReconciliation` as children. The `TaskProvider.Registry` is started after the schema cache (the registry refreshes schemas on contract-version update). The BootReconciliation is started after the registry.

No other existing module is touched. The TRD does not modify `ForemanServer.Aggregates.Task`, `ForemanServer.Aggregates.Run`, or any existing projection. The slice is a forward-compatible capability; projects that don't opt into `task_provider` continue to operate unchanged.

| **Hand-rolled semaphore** for `ConcurrencyLimiter` | Avoids a new dep. `:queue` + `Process.send` + per-call timeout. |

### 2.4 Architecture Issues Identified in Self-Critique

The TRD's adversarial review (Phase 5) raised 3 issues, all resolved by the slice design:

1. **Sensitive-field round-trip vs side-channel discipline.** AC-001-2 requires the four sensitive fields to be present as explicit Issue struct fields (so REQ-019 capture tests can assert their round-trip). The PRD's risk #4 (sensitive data leakage) requires them NEVER to appear in side-channels. The slice honors both: the fields are first-class on the struct, but ALL `Logger.*` / `IO.*` / `:telemetry` / `ProviderError.context` (other than `redacted_fields`) sites are write-time-scrubbed (the `sensitive_field_scrubber` reflect-and-scrub is invoked by every emit site). The side-channel capture test in PR 3 enforces the discipline.
2. **Stderr unconditional discard vs operator-visible diagnostics.** REQ-008 rule 6 says stderr is always discarded; REQ-018-2 says the doctor must report `stderr_byte_count` to the operator. The slice records the byte count at the subprocess layer (where the bytes are first measured) and never copies them anywhere else. The doctor reports the byte count from the `ProviderError.context` field. The doctor NEVER reports `sanitized_stderr_excerpt` (no such field exists). The byte count is informationally useful and non-sensitive by construction (PRD §10 Testability).
3. **Lifecycle-partition correctness.** Reopening of orphaned Beads claims (post-crash) belongs exclusively to `Workflow.BootReconciliation` (AC-017-2), NOT to `Workflow.RunExecutor`. The runner's post-execution hooks are `claim/3`, `complete/3`, `fail/3` only — `fail/3` itself performs `br update --status open --transition-comment` (AC-015-2), so a runner-side `reopen/3` hook would duplicate the same `br update --status open` operation and risk conflicting concurrent transitions. The `BeadsAdapter.reopen/3` callback exists on the adapter exclusively to be invoked by BootReconciliation.
