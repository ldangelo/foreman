## 1. Context

Phase 0 of the SunStone software factory (umbrella `PRD-2026-b7c2e941`) is a **prove-and-close-gaps** phase, not a redesign. The PRD fixes the expected outcome: extend Foreman's event-sourced engine; Temporal or Conductor are admissible only for a criterion that cannot be closed in it. This TRD designs the smallest change that makes each PRD criterion true and provable, and plans the decision record (REQ-001) last, citing the evidence the earlier tasks produce.

Every design claim below was read from source on 2026-11-08 and carries a `path:line`; the claims changed in the 1.0.5, 1.0.7, 1.0.9, 1.0.10, 1.0.11 and 1.0.12 refinements were re-read on 2026-11-09, the claims changed in the 1.0.14 amendment on 2026-11-10, the claims changed in the 1.0.16 amendment (the shipped behaviour of PR 2 and PR 3) on 2026-11-11 at `74f1df26`, and the claims changed in the 1.0.17 amendment (the shipped behaviour of PR 4 to PR 8, which also corrects premises of TRD-011 to TRD-022 that the implementation disproved) on 2026-11-11 at `1d316d3f`. Preparing this TRD revised the PRD repeatedly (v1.1.3 to v1.1.13); each correction is a place where a plausible assumption was wrong, so the TRD re-verifies rather than inherits. Areas that rest on the author's own source reads, and that an implementer should re-validate before relying on them, are marked in §5.

## 2. Scope and Non-Goals

In scope: restart/resume proof and gap closure (REQ-002), human-wait durability (REQ-003), effect reconciliation for PR create, branch push and task-provider state change (claim, complete, fail and boot reopen; REQ-004), stage provenance and project-context identity on the existing projections (REQ-005), an inspectable isolation profile with fail-closed rules (REQ-006), skill preflight at kickoff (REQ-007), and the engine decision record (REQ-001).

Non-goals: replacing the engine; a new workflow-manifest key (`PhaseSpec.@fields` is closed); Kubernetes; `kata` or `herdr` as isolation backends; **building host filesystem confinement** (the PRD requires it to be recorded as unenforced, AC-006-6); phase-level retry policy and `PhaseRetryExhausted` (owned by `PRD-2026-af25d0cb`); auto-merge, idea cultivation, external memory, chat adapters.

## 3. Reused Capabilities

The foundational-capability registry (`trd-graph-cli capabilities docs/TRD`) is empty, so no TRD is reused. Reuse is of existing Foreman modules, called out per task: `Idempotency.KeyStore`/`CrashRecovery`/`BootReconciliation`, the `Phase`, `Run` and `RunSlots` aggregates, `ProjectionStore`, `EventCodec`, `RunExecutor.kickoff_preflight/1`, `Jobsite.NetworkPolicy`, `Workflow.Validator`, `PreflightFailure`, and the test-support helpers `DispatcherRestart`, `RunDrain`, `TestApplication`, `KeyStoreReset`, `UniqueIds`, `ProjectionLeakGuard`.

## 4. Binding Design Constraints

From `docs/standards/constitution.md` and `AGENTS.md`; they apply to every task.

- Only `CommandRouter` appends to the EventStore; aggregate handlers return event specs (constitution §4). `packages/foreman_server/test/foreman_server/event_store_enforcement_test.exs` enumerates the allowed append sites (`command_router.ex` only).
- Every domain event is a module in `lib/foreman_server/events/` with `@enforce_keys` and `@type t`; adding the module is the registration, because `EventCodec` derives its registry from `events/**/*.ex` at compile time (`event_codec.ex:10-15,44`), so replay works with no codec edit. New fields on an existing event are optional (default `nil`) so old streams still decode; the reverse does not hold, because `EventCodec.decode!/2` raises on a field the module does not declare (`event_codec.ex:254-257`), so a stream written with a new field cannot be decoded by an older build (§13). Aggregate state is a typed struct; `apply_event` uses struct-update syntax.
- Extend existing projections and events; add no parallel store. The run status DTO is built once, in `mcp/tools.ex` (`run_status_dto/2`, which carries only `current_phase`); a new field is added there and not re-derived per transport (AGENTS.md §5.7: never duplicate a boundary across transports or adapters).
- Total result handling (§5.2): no catch-all that turns an unknown value into success. Absent is not malformed (§5.3).
- Phase execution stays on the Jobsite engine; no second phase loop in `RunExecutor`. The workflow vocabulary stays closed.
- Tests: a failing test is a failed build. Recovery tests are `async: false`, use `UniqueIds`, never `Application.stop`, and reset projections with the sanctioned helpers (`docs/lessons/run-logs-known-issues.md`, `packages/foreman_server/test/support/projection_leak_guard.ex`). Run one file with `devbox run -- bash -c 'cd packages/foreman_server && MIX_ENV=test mix test <path>'`.

## 6. Architecture Decision

### Alternatives considered

**Option A — record-only.** Add the profile, provenance and loss fields as log lines and telemetry, and write tests. Smallest, but AC-002-2/5/6 and AC-005-2 require *durable, inspectable* records, and a log line does not survive a restart or reach the status DTO. Rejected.

**Option B — new durable-execution substrate.** Adopt an external engine (Temporal or Conductor) or add a new effect-intent event store and execution model. Satisfies the criteria but is not justified by evidence: every gap found is closable in the current engine, and a second effect record beside `KeyStore` would be the parallel store §4 rules out. Rejected; this is also the REQ-001 conclusion.

**Option C — extend the existing seams (chosen).** Close each gap inside the module that already owns the concern. The two decisions that were open were confirmed by the product owner on 2026-11-08: durable attempt counting with phase-level exhaustion deferred to `PRD-2026-af25d0cb`, and intent key plus external-truth reconciliation for effects.

### Components and changes

1. **Phase attempts (REQ-002).** Add a typed `PhaseRetried` event (adding the module is enough: `EventCodec` derives its registry from `events/**/*.ex` at compile time); let `phase.retry` apply to an in-flight phase when `reason: "resumed"`; set `attempt` in `PhaseStarted`'s apply and keep a resumed retry `in_progress` in the Phase aggregate, the Run aggregate and the projection fold; `RunExecutor` dispatches `phase.retry` after reaping orphans when it resumes an in-progress phase, with a command id that carries `Incarnation.id()`, so a repeat within one boot is deduplicated and each restart advances the attempt. The attempt is then derived from the stream. Not a policy retry; it only records that a crash abandoned the earlier attempt. `PRD-2026-af25d0cb` builds its own events for scheduled retries (`PhaseRetrying`, `PhaseRetryExhausted`), as OTD-1 records.
2. **Recovery records (REQ-002, REQ-004).** Two records replace the one ETS counter, because the counter guards slot cleanup and no run. (a) The boot cleanup budget lives on the `RunSlots` aggregate: a typed `RunSlotRecoveryAttempted` event (`attempt`, `outcome` `failed | exhausted | dispatched`, `kind`, `reason`, `elapsed_since_boot_ms`) and a `run_slots.recovery_attempt` command, folded into `RunSlots.State.recovery` and the projection's `orphan_recovery`; `BootReconciliation` reads the count from the state it already loads and appends the event (TRD-003). **Budget arithmetic:** `handle_dispatch_failure/4` increments the count, then `RestartBackoff.next_attempt/1` retries while `attempt <= 5` and stops otherwise (`restart_backoff.ex:8-19`, `boot_reconciliation.ex:1297`), so five retries are permitted and the **sixth consecutive failure is recorded as `exhausted`**: boot then skips the entry (log, telemetry, queue status) instead of re-dispatching it with a fresh budget, and no run is blocked, because the run is absent or terminal. **Who can re-arm it:** nothing in boot; a successful dispatch clears a count that has not reached the limit, and an entry's record is dropped when its holder or waiter leaves the stream by another route (the Dispatcher's terminal release or the 30 s backstop sweep); Phase 0 builds no operator verb for it (Deferred, TRD-023). (b) The run-level record is a typed `RunRecoveryAttempted` event on the run stream (`outcome` `resumed | effect_retried | effect_blocked`, `elapsed_since_boot_ms`, optional `reason`, `effect_class`, `effect_key`, `effect_verdict`) with a `run.recovery_attempt` command, folded into `run.recovery` and shown as `RunStatus.recovery` (TRD-005): `RunExecutor` writes `resumed` once per boot for a resumed run, and the effect step writes the other two (TRD-012). When the effect step blocks a run it dispatches the existing `run.block`: `RunBlocked` is already terminal, already mapped by the notifier and projection, and already used by `Overwatch.CrashLoopDetector`, so no new "blocked" outcome is invented. `RunBlocked.reason` is a `String.t()`, so every Phase 0 block uses a stable snake_case code (`effect_outcome_ambiguous`, `effect_already_done`, `effect_class_unregistered`) and puts structured detail in the preceding `RunRecoveryAttempted`, never in a tuple inside the string. `run.resume` is rejected for a blocked run (accepted only from `paused`, `aggregates/run.ex:588`); an operator `run.reset` (accepted from `blocked`, `aggregates/run.ex:1353`, and `RunReset` deletes the run's projection row, `projection_store.ex:2641`) is the one exit from an effect block (Deferred); **1.0.17:** the exit is real only because the key carries a refusal marker that `run.reset` lifts (TRD-011), so a reset run does not simply repeat the effect.
3. **Worktree loss and context identity (REQ-002, REQ-005).** Optional `prior_worktree_discarded` and `input_artifacts` fields on `PhaseStarted` and `PhaseRetried`; a new `PhaseContextRecorded` event dispatched from `build_agent_launch`, from a single `ProjectContext.build/1` per launch (today the bundle is built at least twice per launch and is only logged per run and phase). All fold into the existing `state.phases` entry; the projection shows every phase, while the status DTO carries only the current phase.
4. **Effects (REQ-004).** `Idempotency.Effect.run/4` writes a `started` intent key before an effect and `completed`/`failed` after; boot already marks orphaned `started` keys `ambiguous`. A `Reconciler` behaviour registered by key class is consulted by a new effect-recovery step in `BootReconciliation`, which partitions the ambiguous keys: `effect:` keys go to that step and every other key keeps the exact `CrashRecovery.reconcile/2` path, which is not changed (the registry does not use `CrashRecovery`'s one-arity `side_effects_check`, a boolean predicate that cannot carry a three-valued verdict). Effect done or unknown yields a block (`run.block`) when the run is not terminal, never a retry; not done permits the retry; an unregistered class blocks (fail closed). A terminal run rejects `run.block` (`aggregates/run.ex:766-771,1348-1349`), so for it the verdict is logged, counted in telemetry and leaves the key `ambiguous`, and PRD AC-004-2's block is not met (TRD-012). **1.0.17:** whenever the sweep cannot resolve a key (a block, or a terminal or absent run) it marks the key unresolved with the run stream's version, and `Effect.run/4` and `Effect.preflight/3` then refuse it (`effect_unresolved`, `effect_check_failed`, `effect_marker_malformed`) until an operator `run.reset`, which `KeyStore.lift_unresolved/3` applies by compare-and-set; a key the sweep never decided (still `started`, or `ambiguous` with no marker) is not refused and AC-004-2 is only partly met (§5, TRD-023 (xv)). The reconcilers read the key's metadata after a restart, so `KeyStore` keeps stored metadata across a status change (TRD-011); with no durable store configured nothing survives a restart and effects are unprotected (TRD-014). Three classes covering four state changes: PR create, branch push, task-provider state change (claim, complete, fail, reopen).
5. **Isolation profile (REQ-006).** `Jobsite.ExecutionProfile` resolves `{backend, filesystem, network, credentials, cleanup}` each as `enforced | unenforced(reason)` from the real backend, is recorded on `PhaseStarted`, and kickoff preflight blocks a host run when the project requires a network policy the host cannot enforce.
6. **Skill preflight (REQ-007).** `SkillResolver` checks the skill a `command:` names against the launching provider's own skill directories on a host run, never a union: **1.0.17 (the 1.0.5 premise was wrong, §5):** `SkillResolver.resolve/4` mirrors pi 1.5.0's own loader (project `<cwd>/.pi/skills`, user `<agent_dir>/skills`, `.agents/skills`, settings `skills` arrays and filters, declared packages' `pi.skills`, extensions) and is fail-safe: `:available` only for a positive find in an unfiltered user-scoped source, `:missing` only when absence is proven everywhere, otherwise `:unverifiable`; `~/.foreman/skills` is not searched, and a provider with no repo-defined skill directory (claude) or a non-host backend is `:unverifiable`, reported and never available. A public skill extractor on `Workflow.Validator` serves the validator and the resolver alike. `PreflightFailure` gains a `:skill_not_found` class and optional `backend` and `skill` fields (default `nil`), which `RunExecutor` sets on the missing-skill and missing-harness refusals; `backend` is `:host_workflow`, defined by `ExecutionProfile`.
7. **Decision record (REQ-001).** `docs/decisions/phase-0-durable-execution-engine.md`, the repo's only decision-record location (`docs/decisions/project-delete.md` is the single precedent: plain Markdown, no front matter).

### Data flow

```
crash -> boot -> BootReconciliation ──reads RunSlots.recovery (run_slots:global)──▶ release the orphan slot entry? (exhausted: skip, log, count)
                     │ ambiguous agent-phase keys ──▶ CrashRecovery.reconcile/2 (unchanged) ──▶ skip | retry
                     │ ambiguous effect: keys ──▶ effect-recovery step ──▶ Reconciler[class] ──▶ retry | RunRecoveryAttempted + run.block (run not terminal) | log + telemetry (run terminal)
                     └ run_slots.recovery_attempt (RunSlotRecoveryAttempted: failed | exhausted | dispatched) via CommandGateway.dispatch_system/1; no run.block (the run is absent or terminal)
resume ─▶ RunExecutor ─ reap orphans ─▶ phase.retry(reason: resumed) ─▶ PhaseRetried (attempt+1) ; run.recovery_attempt(resumed) ─▶ RunRecoveryAttempted
launch ─▶ build_agent_launch ─▶ one ProjectContext.build/1 ─▶ PhaseContextRecorded ; ExecutionProfile ─▶ PhaseStarted fields
effect ─▶ Effect.run(class, key, fun): started key ─▶ fun ─▶ completed|failed
```

## 7. Design Principles for Every Task

- A proof task is a real run: its `-TEST` sibling states the mutation that must make it fail (revert the guarded behavior in a scratch copy and observe red), so a green test cannot pass vacuously.
- No stub reconciler, no fake backend result, no placeholder event. A class without a call site is not given a reconciler (the PR-comment class stays fail-closed under AC-004-3).
- New event fields are optional; existing streams must replay. Each event change includes a codec round-trip test.

## Deferred (explicitly not in this plan)

- **Phase-level retry exhaustion**: the maximum-attempt setting, scheduled retries and `PhaseRetryExhausted` belong to `PRD-2026-af25d0cb` (Draft, unimplemented), a blocking prerequisite for any exhaustion guarantee. This TRD makes the attempt number and the boot re-dispatch budget (the cleanup of orphaned run-slot entries) durable only. The retry policy and the default-safety rule for non-idempotent work (its REQ-011, REQ-012) also stay with that PRD.
- **Slot and queue recovery**: `PRD-2026-d3051d4b` and `PRD-2026-0eac69b3` own it (PRD REQ-002 defers it); TRD-003 only makes the retry budget of the boot cleanup durable on the `run_slots:global` stream.
- **Merge gate and chat delivery** (PRD REQ-003): the operator-only, SHA-pinned merge gate belongs to Phase 1 and chat-channel delivery of questions to Phase 4.
- **Work-log authoring, stall facts and redaction soundness**: authoring task work-log comments belongs to `PRD-2026-3a76a0f0` (PRD REQ-004); stall facts stay on `RunStallReported` and per-chunk redaction soundness (`WorkerLogPolicy` redacts per chunk) belongs to foreman-l30ao.5 (PRD REQ-005).
- **`annotate` as an effect**: not in the enumerated set, because a repeated annotation is a duplicate comment, not corrupted external state. Its callers (`mcp/tools.ex:3175`, `review/bead_sink.ex:134`) are operator and review paths outside recovery re-entry, and the `complete` calls in `aggregate/actor.ex` and `task_providers/beads_orphan_janitor.ex` are not keyed either. An effect keyed without a reconciler fails closed (AC-004-3).
- **Unprotected boot `reopen`**: an orphaned `in_progress` issue with no projected run has its reopen unkeyed (TRD-015), so a crash during it is not reconciled and the next boot's scan repeats it. A known gap, logged and listed in the decision record as unprotected; it is not a fail-closed path.
- **Blocking a terminal run**: `run.block` is rejected for a terminal run (`aggregates/run.ex:766-771,1348-1349`) and `run.recovery_attempt` carries the same guard (TRD-005), so an effect verdict on one cannot block it. That is the usual case for a boot `reopen` (its run is non-active by construction, `boot_reconciliation.ex:342-357,397`) and the exception for the effects of a live run. For such a run the step logs a warning, emits `[:foreman_server, :workflow, :boot_reconciliation, :effect_on_terminal_run]`, appends nothing and leaves the key `ambiguous`; a run already `blocked` gets the same warning and event. PRD AC-004-2 and AC-004-3 (v1.1.11) prescribe exactly this surfacing for a terminal run, and `foreman_doctor` lists the key (TRD-014). The boot cleanup budget has the same shape (its runs are absent or terminal), so TRD-003 records an exhausted slot entry and blocks no run. A record of the verdict on the run status for a terminal run is not built: it would need the verdict in the ambiguous key's metadata and a read of that key into the status DTO, but `KeyStore` has no metadata-only update and no by-run lookup (`idempotency/key_store.ex:53-104`) and `run_status_dto/2` reads no key (`mcp/tools.ex:3504-3530`); for the same reason the doctor section shows the key, class, run id and the run's current status and not the verdict.
- **`fail` retries 2 and 3**: only attempt 1 of the task provider's `fail` is keyed (TRD-015), because retries 2 and 3 run from a detached `Task` after `run.fail` has made the run terminal (`run_executor.ex:198-209,255,1884-1885`), where no verdict could block it. A crash during them is not reconciled and the log is the only record; the decision record lists it as unprotected.

## 13. Rollout and Rollback

Not everything here is additive. New in PR 1 to PR 8, none operator-visible until implemented: events `PhaseRetried` and `RunRecoveryAttempted` (PR 1; the latter with `effect_class`, `effect_key`, `effect_verdict`), `RunSlotRecoveryAttempted` (PR 1, on the `run_slots:global` stream) and `PhaseContextRecorded` (PR 6); the command types `run.recovery_attempt` and `run_slots.recovery_attempt`, dispatched through the system path; the projection fields `run.recovery` and, in `queue_status/0`, `orphan_recovery`; `Incarnation.started_at_ms/0`; the telemetry events `[:foreman_server, :workflow, :run_executor, :resumed]` and `[:foreman_server, :workflow, :boot_reconciliation, :effect_on_terminal_run]`, and the `skipped: true` metadata on the existing `dispatch_blocked` event; the `foreman_doctor` store line and "Unresolved effect keys" section (PR 4, TRD-014); optional fields on one existing event (`PhaseStarted`: `prior_worktree_discarded` in PR 1, `input_artifacts` in PR 6, `execution_profile` in PR 7); the behaviour `Idempotency.Reconciler` and the modules `Idempotency.Effect`, `Jobsite.ExecutionProfile` and `SkillResolver`; and the `run.block` reason codes `effect_already_done`, `effect_outcome_ambiguous` and `effect_class_unregistered`. **Not additive:** (1) the existing `run.block` command is widened: it gains a dispatch site (the effect reconciler), and because `RunBlocked` is terminal that widens its blast radius beyond `CrashLoopDetector`; the effect site blocks only a run that is not already terminal (a terminal run rejects `run.block`, so its verdict is logged, counted and listed by `foreman_doctor`, TRD-012, TRD-014); (2) the effect block gains a deliberate agent-cancel step that the dispatcher does not perform for `RunBlocked`; (3) the ETS `:boot_recon_dispatch_attempts` table is removed in TRD-003 with no migration, since its contents are intentionally transient: the count now lives on the `run_slots:global` stream, so the first boot after the upgrade starts every orphan at zero; (4) `reset_dispatch_attempt` is removed from the blocked branch (`boot_reconciliation.ex:1331`), so reaching the limit no longer clears the count: only a successful dispatch, or the entry leaving the stream, does; (5) `queue_status/0` gains `orphan_recovery`, an API field of `foreman_queue_status` and `GET /api/queue` (two existing exact-map assertions and one JSON assertion are edited, TRD-003-TEST); (6) on the repo-backed path `KeyStore`'s record call merges a status change into the stored row instead of only the ETS copy (TRD-011), so a key keeps its metadata across a restart: a behaviour change for every key writer on that path. **Field writes are forward-only.** Old streams replay unchanged, but an older build cannot decode a stream written with a newer field: `EventCodec.decode!/2` raises on a field the event module does not declare (`event_codec.ex:254-257`), and that includes `PhaseStarted`, an event older code already knows. The PR 1, PR 6 and PR 7 fields are therefore gated like the new events: nothing writes them in production until the whole PR is deployed, and a PR is rolled back by reverting it before any stream carries its fields or events (a stream containing a new event type fails to decode on the older code in the same way; events are only emitted by the code that registers them). `RunSlotRecoveryAttempted` lands on the global stream every run touches, but it is appended only when a boot cleanup fails or an entry that failed before succeeds, so that stream carries none until one happens. **1.0.17, as shipped in PR 4 to PR 8:** the additions above landed with the same forward-only rule, and four more changes are not additive: (7) `AutoPR` and `PhasePR` no longer reach `git push` when the context has no `cwd` or the origin's head cannot be read: the result is `{:error, {:intent_not_recorded, reason}}` instead of `:git_push_failed` (TRD-013); (8) a run whose effect key is unresolved is refused by `Effect.run/4` and `Effect.preflight/3` until an operator `run.reset` (TRD-011), so a re-run of that effect now returns a refusal where it used to repeat; (9) **a project that already had a `none` or `allowlist` network policy and runs on the host workflow door is now refused** with `{:isolation_unsupported, :network, :host_workflow}` (TRD-019), a breaking change for operators; (10) a workflow whose `command:` phase names a skill pi provably cannot load is refused at admission (TRD-022), which on a typical host never happens because the preflight is fail-safe. Rollback of PR 6 to PR 8 follows the forward-only rule: `PhaseContextRecorded`, `input_artifacts` and `execution_profile` (with its `skill` entry) are written by the code that declares them, and an older build cannot decode a stream that carries them.

## 14. Self-Review Findings

Architecture:
1. `PhaseStarted` gains three optional fields (`prior_worktree_discarded` in PR 1, `input_artifacts` in PR 6, `execution_profile` in PR 7) and `PhaseRetried` two. A typed event with several optional fields is a smell. Kept, because splitting each into its own event multiplies commands and aggregate paths for data that is read together; revisit if a fourth field appears. Each field is a forward-only write (§13).
2. Boot-time dispatch of `run_slots.recovery_attempt` (TRD-003) and `run.recovery_attempt` (TRD-012) must go through `CommandGateway.dispatch_system/1`, the call `BootReconciliation` already makes for its other commands (`boot_reconciliation.ex:851`), not the operator gateway; `RunExecutor` reaches `run.recovery_attempt` through `dispatch_system/5`, which ends in the same gateway (TRD-005).
3. The `PhaseRetried` reuse crosses into `PRD-2026-af25d0cb` territory; OTD-1 records the boundary.
4. The per-phase fields live on the phase projection and `RunStatus` carries only `current_phase`; the decision record lists this against PRD AC-005-1 (TRD-023).
5. A boot `reopen` with no projected run is unkeyed and unprotected (TRD-015); it is recorded as a limitation and under Deferred, not described as fail-closed.
6. `KeyStore`'s record call dropped a key's stored metadata on the first status change after a restart, which would have blinded every reconciler to `cwd`, the push SHAs and the issue identity; TRD-011 fixes it and tests across a restart, because TRD-012, TRD-013 and TRD-015 read that metadata.
7. The boot cleanup budget was first designed on the Run aggregate (`RunRecoveryAttempted`, then `run.block` at the sixth failure). The implementation found that the counter's only callers release the slot of a run that is absent or terminal, so no such write can succeed and no run can be blocked: the same terminal-run defect as PRD v1.1.11's AC-004-2, because both designs assumed a block is always possible. The count now lives on the `RunSlots` stream (TRD-003), `RunRecoveryAttempted` records `resumed` and the effect outcomes (TRD-005, TRD-012), and PRD v1.1.12 says so (AC-002-4, AC-002-6). Any future "block the run" step must first name the run's status at that point.

Coverage:
1. AC-006-3 is provable only on docker (OTD-2); the host door is explicitly unenforced, which AC-006-6 allows.
2. The "waiting on a human" restart boundary in TRD-006 overlaps TRD-009; they share fixtures, not assertions.
3. PRD AC-005-2 and AC-005-3 are met for workflow-door launches only; docker jobsite sessions record no context identity (TRD-017, Deferred).
4. PRD AC-004-2 and AC-004-3 (v1.1.11) block only a run that is not terminal: the effects of a live run block, a boot `reopen`'s run is non-active and usually terminal, and for it the verdict is logged, counted and the key listed by `foreman_doctor`; the verdict itself is not stored (TRD-012, TRD-014, TRD-015, Deferred, TRD-023). REQ-004's guarantees also need a durable idempotency store (TRD-014, TRD-023).
5. PRD AC-002-4 (v1.1.12) measures boot-to-resumed time for every resume, including an operator `run.resume`, which `RunExecutor` cannot tell from a restart, and boot-to-blocked time only for a run that recovery can block; PRD AC-002-6 (v1.1.12) is met by an exhausted slot entry that is recorded, skipped and listed in the queue status, not by a blocked run, and has no operator re-arm (TRD-003, TRD-005, TRD-012, TRD-023).
6. (1.0.17) Criteria that PR 4 to PR 8 left partly met or met differently, each named with its engine decision in TRD-023: PRD AC-004-2 is only partly met (undecided effect keys can be repeated, bead foreman-by6nl); AC-005-1 is met as "which artifacts it was given", not "read"; AC-007-1 and AC-007-2 refuse only on a provably complete skill lookup, so on a typical host `:missing` is unreachable; AC-006-3 and AC-006-4 rest on one recorded local `:docker` run (Docker Desktop for macOS); TRD-012-TEST's "a verdict handled twice" Test AC is not met by mutation evidence for the versioned block command ids. The engine decision "extend the current engine" must hold for each, because the gap is closable in the engine (a bead) or accepted for Phase 0, never by omission.
