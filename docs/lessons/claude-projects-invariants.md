## 20.1 Threads (Claude-Projects parity, E6)

`ForemanServer.Threads` is a pure read model over existing projections (task, run, worktree, PR association, review, and legacy jobsite history); no event backs a thread except the disposition flag. Rules:

- Operator disposition is the `thread.resolve` / `thread.reopen` commands (events `ThreadResolved` / `ThreadReopened` on `thread:<id>`), allowlisted in `CommandGateway`. Config `config :foreman_server, :threads` keys are `idle_resolver`, `idle_resolve_after_days`, `sweep_interval_ms`; `IdleResolver` only sets the flag, never stops a run.
- Live mid-phase steering (docs/plans/live-steering.md): `Workflow.LiveSteer`. Phases of `:claude`/`:pi` launch with harness `provider_options: %{live_input: true}` (config `:live_steering, enabled:`); the dispatcher first calls `LiveSteer.deliver/2` (`Jido.Harness.Run.send_input/3` into the running session; the provider takes it after its in-flight tool call) and only on a typed refusal falls back to pause/resume. System-only commands `run.steer.deliver` / `run.steer.undeliver` append `RunSteerDelivered` / `RunSteerUndelivered`; `run.steer.consume` takes `delivery: live|prompt`. A steer still pending when the run goes terminal (`RunCompleted|Failed|Cancelled|Deleted`) is recorded `RunSteerUndelivered` (projection `undelivered_steering`), never silent. `run.steer.deliver|undeliver` MUST stay out of `@allowed_operator_types`. jido_harness is a GIT dep (`Sunstone-Partners/jido_harness`, ref in `foreman_server/mix.exs`); `packages/jido_harness` is a vendored mirror, change both.
- `jido_harness` is compiled from the vendored `packages/jido_harness` (path dep in `foreman_server/mix.exs`, `override: true`), NOT from the Sunstone-Partners fork; the tree was synced to fork `e41fc165` and Foreman-specific harness changes (live input, `Run.send_input/3`) are ordinary commits there (see `packages/jido_harness/UPSTREAM_PIN.md`). Source-contract tests read `packages/jido_harness/lib/...`, not `deps/jido_harness`.
- Steering fallback is `"pause_resume"` (constant `steering` on the Thread DTO; `Threads.Steerer`). `run.steer` (operator-allowlisted) appends `RunSteerQueued`; the dispatcher pauses the run (the executor commits partial work) and resumes it; `RunExecutor` injects the message into the next phase prompt and then dispatches the system-only `run.steer.consume` (`RunSteerConsumed`) so it is injected once. The durable queue is `RunSteerQueued` minus `RunSteerConsumed`; `RunControl`'s ETS mailbox is only a cache. `run.steer.consume` MUST stay out of `@allowed_operator_types`. A thread of the retired jobsite door answers `{:error, :jobsite_retired}` (HTTP 410) to stop and steer.
- Routes (router.ex): `GET /api/projects/:project_id/threads`, `GET /api/projects/:project_id/threads/find`, `GET /api/threads/:id`, `.../transcript`, `.../stream`, `POST /api/threads/:id/stop`, `POST /api/threads/:id/steer`, `POST /api/threads/:id/rereview` (`Threads.Actions.rereview/1` -> `Review.Analyzer.rerun/2`; 202 / 404 `thread_not_found` / 409 `not_reviewed`, `not_rerunnable`, `already_running` / 422 `archive_unusable` / 503 `analysis_disabled`; no MCP tool). MCP: `foreman_thread_list|get|stop|steer|transcript|find` (`stop` and `steer` are write-gated; `find` and `transcript` are read tools). CLI: `foreman thread list|get|stop|steer|resolve|reopen|rereview`.
- `Threads.Finder` is deterministic (no LLM): exact external_id/branch/PR matches outrank text matches (Jaccard >= 0.5), resolved/deleted threads never text-match. `Threads.Actions.follow_up/2` never starts a run: a live thread is steered; a terminal thread with a branch returns `{:error, {:needs_new_run, %{branch:, session_id:}}}`; a resolved thread returns `{:error, :thread_resolved}` (reopen is never implicit).
- Transcripts are bounded and honest about omissions: `run_logs` keep a bounded tail (`omitted_entries` / `truncated`); legacy jobsite turns have no timestamps and no operator turns because jobsite resume prompts were not events.

## 20.2 Overview (Claude-Projects parity, E7)

`ForemanServer.Overview` is the operator's glance at a project: a pure read model over `Threads`, the PR / merge-gate state folded into `ProjectionStore`, review verdicts and approval / question counts (`Overview.Signals`). Rules:

- `Overview.Group.classify/1` is pure and total: `{group, reason}` with groups `ready_for_review`, `waiting_on_you`, `working`, `landing`, `idle`, `resolved` (first match wins; the rules table is in the moduledoc). Unknown status is `{:idle, :unknown_status}`; a closed-without-merge PR classifies `resolved` but is never auto-resolved. An open PR whose watched `checks_state` is `failing` classifies `waiting_on_you` / `ci_failing` (`Input.checks_state`, read from `ProjectionStore.pr_watch/1`). The same watch's `review_decision == "changes_requested"` / non-empty `thread_ids` classify `waiting_on_you` / `changes_requested` / `review_threads` (`Input.review_state`; conversation `comment_ids` are excluded: no resolved state), ranked after `ci_failing`. An open PR that holds a PENDING merge gate whose approval evidence is `ineligible` or `unknown` (`Input.evidence_blocked?`, Phase 1 PR 8: `PrWatch.DTO`'s `eligibility` under the project's policy, which `Overview.classify` reads once per project) classifies `waiting_on_you` / `evidence_blocked`, ranked after `merge_in_flight` and before `pr_ready`, so it replaces `ready_for_review` / `pr_ready`; `off`, `eligible` and `waived` evidence blocks nothing. `ThreadCard.pr_actions` (`Overview.PrActions`) carries the workspace's Fix CI / Address comments / Resolve conflicts / Create PR buttons with disabled reasons; they dispatch the existing `run.pr.*` commands via `Workspace.Actions.pr_action/5`, and there is no merge button.
- PR state is folded by `Overview.PrFold` from `PrAssociated`, `PrReady`, `MergeGatePending/Approved`, `PrUpdated`, `PrMerged`, `PrRetargeted`, `PrReset` into `state.pr_states` (read via `ProjectionStore.pr_state/1`, `pr_states_for_project/1`; also carries the run's `failure_reason`). Folds log and skip malformed payloads; a merged PR is not reopened by a stale `PrUpdated`. `PrReady` itself sets `merge_gate :pending` because the Run aggregate treats it as the gate hold; a separate `MergeGatePending` event is emitted only when a push voids an approval (`run.pr.rehold`, see "Merge gate per PR"), and `PrFold` folds it to `:pending` the same way.
- **The head `PrReady` records is the head GitHub names (Phase 1 PR 3).** `ForemanServer.PrReadySignal.signal/2` is the one implementation of the `run.pr.ready` signal (called by `RunExecutor`, `PrCreate` and `RepoPr`): it reads the PR once with `gh pr view` (`GitHub.PrStatus.fetch`, bounded by `Idempotency.Reconcilers.Command.default_timeout_ms/0`, 30 s; stub it with `PrReadySignal.set_command_runner/1`) and dispatches `run.pr.ready` with that SHA under `Identity.run_pr_ready_command_id/2`; no local `git rev-parse` is read any more (`PrCreate.head_sha/2`, `PrCreate.run_command/3` and `RepoPr.head_sha/2` are gone). A GitHub that cannot be read is `{:error, {:head_read_failed, reason}}` (`reason` includes `{:timeout, ms}` and `{:read_crashed, term}`), a refused dispatch `{:error, {:ready_dispatch_failed, reason}}`; `PrCreate` wraps either as `{:pr_ready_signal_failed, _}`. Before returning, either error dispatches the system-only `run.pr.ready_failed` (`PrReadyFailed`: `stage` `head_read|ready_dispatch`, `reason` the head atom of the error, with the exit code for `gh` (`gh_failed:1`), never `gh` output, and `failed_at`; best effort, a refused record is logged), which `PrEvidence` folds into `evidence.delivery_issue` of the PR's watch record until a later `PrReady` clears it. The command id holds no head, so a repeat after GitHub's head moved keeps the first `PrReady`. A failure before `PrReadySignal` is reached (`run_base_branch` or `resolve_head_branch` failing in `RunExecutor.signal_pr_ready/2`) is not recorded.
- Surfaces: `GET /api/projects/:project_id/overview` (`include_resolved`, `resolved_limit` 0..200, default 20; 404 `project_not_found`), MCP read tool `foreman_overview` (with `project_id`: full overview; without: one attention line per active project), `attention` / `attention_count` on `GET /api/projects`, `GET /api/projects/:id`, `foreman_project_list` and `foreman_project_get`. Config `config :foreman_server, :overview`: `attention_groups` (default `[:waiting_on_you, :ready_for_review]`; an entry `Overview.Group` does not define raises `ArgumentError`), `tab_providers`, `merge_resolver`, `catch_up_limit`.
- Bound: only the newest `Threads.max_limit/0` (500) threads of a project are classified; `Overview.t()` / the overview DTO / each MCP attention line carry `truncated` (`true` when older threads were left out of `counts`, `attention` and `groups`). Project lists read the threads of all projects once (`Overview.project_fields_many/1`, `Overview.summaries/2` over `Threads.by_project/0`), never once per project.
- Tabs: `pull_requests`, `library` and `scheduled` are built in (`Overview.Tabs.Scheduled`: `{available: true, rows: [Schedule.DTO maps]}`, the same read model as `GET /api/projects/:id/schedules`; a read-model failure is reported as `provider_failed`, not an empty list). A custom `Overview.TabProvider` in `tab_providers` may not name any of the three (it raises like any duplicate). A raising provider only disables its own tab (a `tab/0` that raises is logged and skipped); two providers naming one tab (a configured one shadowing a built-in included) make `Tabs.build/1` raise `ArgumentError`.
- `Overview.Signals` reads pending approvals, open questions and (for a paused thread) expired approvals, undelivered approvals and undelivered answers (`undelivered_reason` on an `answered` question; reason `answer_undelivered`, ranked after `question_expired`) from `ProjectionStore`; `Overview.Group.classify/1` turns them into `waiting_on_you` reasons. The marker never clears, so those reasons are shown only while the thread is `paused` and go away once the operator steers the run. An expired question is the exception: nothing pauses a run for a question, so it is shown on any non-terminal thread (`question_expired`) and stops showing when the thread reaches a terminal status.
- **Approvals and questions (E8)**: operator commands `tool.approve|deny` and `question.answer`; system commands `tool.request|finish|expire`, `question.open|expire|answer.undeliver` (`Approvals.Dispatch` is the closed list). `question.answer` text is bounded by what the steer cap leaves after the delivery prefix: `Run.steer_text_max_chars/0` (8000) minus `OperatorQuestion.steer_text/2`'s `Answer to your question <id>: ` (`OperatorQuestion.max_answer_chars/1`, per question id); over it is `{:error, {:answer_too_long, length, max}}` (HTTP 422) and nothing is recorded; `question.open` refuses a `question_id` over `OperatorQuestion.max_question_id_chars/0` (200) with `{:question_id_too_long, length, 200}` so that cap never reaches 0. `POST /webhooks/operator/ingest` (and `OperatorQuestionDispatcher.dispatch/1`) checks the same limit through `OperatorQuestion.question_id_length/1` before ingesting, answering HTTP 422 `{"error": "question_id_too_long", "length": length, "max": 200}` and recording nothing. A repeated delivery of the same `question_id` is deduped by the inbox (`SharedInbox.ingest/2` answers `:deduped`) but still opens the question: `question.open` is idempotent (deterministic `command_id`, and the aggregate refuses a re-open), so a repeat delivery can retry an open that failed (best effort: nothing retries a failed open on its own, and a failed open is still only logged); `Agents.OperatorTimeout.schedule/3` is armed only by the delivery that started the item, so a deduped delivery stacks no second timer. `Questions.Deliverer` sends exactly `steer_text/2`, so there is no second constant: never hard-code 8000 for an answer. An answer recorded before that limit existed and over it can never be delivered: `Questions.Deliverer.recover/1` logs it once at :error and appends the system command `question.answer.undeliver` -> `QuestionAnswerUndelivered` (the question stays `answered`, gains `undelivered_reason`, notifies `Answer could not be delivered`, and is skipped by later recoveries); the operator remedy is `foreman thread steer --message <text> <thread-id>`. Read surfaces: `GET /api/projects/:id/approvals|questions`, `GET /api/runs/:run_id/approvals`, `foreman approvals|questions`, and the read-only MCP tools `foreman_approvals_list` / `foreman_questions_list`, which return the typed `Approvals.Listing` / `Questions.Listing` the HTTP endpoints serialize (one build, shared). `run.steer` accepts the optional `approval_mode_override` (`default|prompt|auto_edit|auto_approve`; `Aggregates.Run` refuses any other name with `{:invalid_approval_mode_override, name}`; stored on `RunSteerQueued`; applied by the next launch, command phases included, and consumed with the message); `Approvals.Deliverer` is its only producer. An approval decides ONE request, but on the post-hoc path (`resume_with_override`) the override is a mode for the whole next phase (no per-tool grant: Claude `bypassPermissions` cannot be narrowed by `allowed_tools`, pinned in `approvals/capability_test.exs`); only `inflight` is per call. Both deliverers recover at start (`recover/1`: approved-unsettled and denied-paused calls, answers of runs that have not ended; deterministic command ids; a run is resumed only while it holds the decision's steer message; a bus reply is never replayed). `Questions.Deliverer` retries a failed delivery while the server is up: a refused `run.steer`/`run.resume` re-runs the recovery pass on a bounded backoff (`@retry_delays_ms` `[1_000, 5_000, 30_000, 120_000]`, overridable with the `:retry_delays_ms` start option); the pass is idempotent (deterministic command ids; `paused?`/`steer_pending?` gate the resume), after the last delay the failure is logged once at :error and left to the next start, and a bus reply (a question of no run) is not replayed by a pass, so it is not retried. `Overview.Signals.for_threads/1` reads `ProjectionStore.needs_you_counts/1` once per classification, and a `project.adopt` move re-homes a subject's tool calls and questions with it.
- `Overview.MergeResolver` (a `ProjectionStore` subscriber with a bounded catch-up sweep) dispatches `thread.resolve` (reason `pr_merged`, `command_id` `thread-merged:<thread>:<sha>`) when a PR merges; the live path and the sweep both respect `ThreadReopened` (a merge counts only if its `pr_updated_at` is newer than `reopened_at`), find the thread by run id with no recency window (`Threads.by_run_ids/1`), and it never merges or approves.
- **The merge gate stays operator-only** (`merge_approve` -> `run.pr.merge`). No overview/MCP surface may merge or approve; `test/foreman_server/mcp/no_merge_tool_test.exs` pins this for every advertised MCP tool and cards carry only a text hint.
- **Merge gate per PR (E12-S6)**: `Aggregates.Run.State.merge_gates :: %{repo_key => :pending | :approved}` (`repo_key` `nil` = the run's primary; legacy events without `repo_id` fold into `nil`; read it with `Run.merge_gate/2`). `merge_approve` and `run.pr.merge` take an optional `repo_id` (absent = primary; present only for a non-primary repository on `PrReady`/`MergeGatePending`/`MergeGateApproved`/`PrMerged`). There is NO approve-all; each PR is approved and merged on its own head pin (`RunPrMerge.execute(run_id, repo_id)` reads that repository's approval pin via `Run.merge_pin/2`, falling back to its `PrReady` head only when no pin is recorded). ETS `MergeGate` requester keys are `run:<id>` / `run:<id>:<repo_id>` (`PrGate.gate_key/2`); `approve_by_key` approves only the newest PENDING entry of the key. `merge_approve`, `run.pr.merge` and `run.pr.retry` stay operator-only: never MCP tools, never on the coordinator/approvals/PR-watch dispatch lists (`operator_only_pr_commands_test.exs`).
- **One thread, several PRs in the Overview (E12, foreman-w0tnj)**: a non-primary repository's PR events (payload `repo_id`) fold into `state.repo_pr_states` (`%{run_id => %{repo_id => entry}}`, read through `ProjectionStore.repo_pr_states/1` and `repo_pr_states_for_project/1`; `fold_pr_state/3` must not go through `Map.update/4` for it: that stores the default WITHOUT calling the function when the key is absent, which lost the first such event of a fresh projection). `Overview` and `Overview.MergeResolver` read the primary's `pr_state` view and those views as ONE through `Overview.PrFold.rollup/2` (a run with a single PR is returned untouched): `pr_state` is `:conflicted` while any PR is conflicted, `:open` while any PR is open, and once none is live `:merged` when any merged, else `:closed`; `merge_gate` is the strongest gate of the LIVE PRs; `pr_updated_at` the newest. So a failing check on a non-primary PR is `waiting_on_you` / `ci_failing` after the primary's PR merged (`Group.classify/1` and `Input` are unchanged: the roll-up is its `pr_state`/`merge_gate`, `watch_records/2` reads the head run's PR watch whenever any PR is live, and `checks_state`/`review_state` already span every live watched PR), the card's `pr_state`/`merge_gate` are the roll-up, and `MergeResolver` resolves a thread only once no PR of any repository is live. The Pull requests tab (`Overview.Tabs.PullRequests`) has one row per PR: the primary's row as before, each non-primary row additionally carrying `"repo_id"` (no key = the run's primary, so a single-repository run is unchanged).
- **Head-pinned approval and re-hold (foreman-ehxy6)**: `merge_approve` REQUIRES `head_sha` (absent or blank is `{:missing_or_invalid, :head_sha}`; `Run.validate_approval/1` is the one validator, shared by the aggregate and the gateway). `CommandGateway` reads the live PR head (`gh pr view` through `GitHub.PrStatus.fetch`; stub it with `RunPrMerge.set_command_runner/1`) before dispatch and refuses a different head with `{:head_sha_mismatch, supplied, live}`. The recorded `pr_watch` head is NOT the authority: it lags a push and polling is opt-in. `MergeGateApproved.head_sha` is the pin, held in `State.merge_pins :: %{repo_key => %MergePin{pr_url, head_sha, approved_at}}` (a legacy approval event with no `head_sha` pins the `pr_watch` head recorded at that point in the stream). A push after approval returns the gate to `:pending` with the pin cleared: the system-only `run.pr.rehold` (state-based and idempotent: `PrGate.rehold_command/4` asks `Run.stale_approval/4`, the handler emits `MergeGatePending` with `reason: "head_moved_since_approval"`, `approved_head_sha`, `head_sha`) is dispatched by `CommandGateway` after every `run.pr.update|checks|review` observation (`@pr_head_observations`; also when the router deduplicated the observation, because a head returning to an earlier recorded one appends no `PrUpdated`) and by the `run.pr.merge` side effect when `RunPrMerge` answers `head_moved_since_approval` (an unobserved push is caught there). The moved head is never adopted as the pin: only a fresh operator `merge_approve` naming it reopens the gate, and the old approval is never honoured again. The rehold `command_id` carries the approval's `approved_at`, so each approval cycle can be voided once. `run.pr.rehold` is on no operator allowlist and in no MCP/coordinator/approvals dispatch list (`operator_only_pr_commands_test.exs`).
- **Partial completion (E12-S6)**: a multi-repo run whose repo PR cannot be created still completes; finalisation appends `RunRepoPrFailed{run_id, repo_id, reason, at}` (system command `run.repo_pr_failed`, `RepoPr.record_failure/4`), keeps that repo's worktree (`cleanup_run_worktree/3` skips it), and `ProjectionStore.run_repositories/1` reads it as `pr_state: :create_failed` (+ `pr_failure`) until the repo has an association. `completed_with_errors` is DERIVED (`OperatorDashboard.RunDTO`), never a run status. The operator retries with `run.pr.retry {run_id, repo_id}` (`RepoPr.retry/2`: idempotent, allowed on terminal runs, reclaims the worktree on success). Single-repo runs emit no `RunRepoPrFailed`.
- **Live multi-repo e2e and rollback caveat (E12-S12)**: `scripts/e2e/multi_repo.sh` (POSIX sh; run it as `devbox run -- sh scripts/e2e/multi_repo.sh`; assets in `scripts/e2e/multi_repo/`) drives ONE real task over two scratch git repos (local bare origins, recording fake `gh`, private port and database, real `pi` + MiniMax agent) and asserts worktrees, sibling-path edit, commits, pushed branches, two PRs, archive `diffs/b.patch` + manifest `repositories[]`, the per-repo merge gate, a read-only-origin failure with `run retry-pr` recovery, and an unchanged single-repo run. The recorded transcript is `docs/lessons/multi-repo-e2e-2026-10-21.md`. **Rollback caveat (release note)**: single-repo runs write no new event keys, so rolling back after this release but before any multi-repo run is safe; an older binary raises when it replays an event that carries `repo_id`/`repo_ids`, and those exist only after the first multi-repo run. After that first run rolling back to a build without E12 is NOT safe; `runs: false` stops new multi-repo runs but cannot remove events already written.
- **Live Claude Projects acceptance (E16-S8)**: `scripts/e2e/claude_projects_flow.sh` and `scripts/e2e/failure_injection.sh [scenario ...]` (bash; `devbox run -- bash scripts/e2e/<script>`; shared harness and assets in `scripts/e2e/claude_projects/`: `lib.sh`, `boot.exs`, `webhook_listener.py`, scratch `workflows/` pinned to pi/minimax, not the bundled defaults). Each starts its own throwaway server (private Postgres database `foreman_e2e_claude_projects_<cp|fail>`, port, scratch git repo with a local bare origin and its own `br` database, redirected `HOME`, `FOREMAN_VFS_ALLOWED_ROOT`, local webhook sink, real `pi` agent) and prints `PASS`/`FAIL`/`UNVERIFIED` per assertion; exit 3 on any FAIL; only its own PIDs/database/work dir are cleaned up (`E2E_KEEP=1` keeps them). The flow covers project settings, memory, library, a bead imported by `BeadsWatcher` into a thread that sees instructions/memory/library, steer/stop/resolve/reopen, Overview groups, coordinator chat, notifications and the review archive with its bead comment. Failure scenarios: `provider-down`, `agent-crash`, `coordinator-crash`, `server-crash` (exec-port + server `kill -9` -> `OrphanReaper` #607), `port-closed` (exec-port only `kill -9`, server alive -> the failed run's cleanup reaps the orphaned agent, foreman-zmhzw), `cancel-strays` (`run cancel` and `thread stop` of a run blocked in a `sleep 300` tool -> the agent AND the tool process, which runs in a session of its own, are gone: nothing is left running in the run's worktree, foreman-zmhzw), `shutdown-strays` (SIGTERM of the server with such a run in flight -> the same, foreman-zmhzw), `project-paused`, `br-down`. Approve/deny and question/answer are reported UNVERIFIED by the scripts (pi has no permission mechanism); real GitHub is exercised only when `FOREMAN_E2E_GITHUB_REPO` is set (stage 8, `docs/acceptance/github-live-run.md`), and the Claude provider paths have their own live write-ups (`docs/acceptance/README.md`). Evidence: `docs/acceptance/claude-projects-acceptance-2026-10-22.md`; per-capability verdicts: `docs/acceptance/parity-audit.md`; runbook: `docs/acceptance/README.md` and `docs/user-guide.md` "Running the live acceptance".
- **Failure evidence of the live harnesses (foreman-azc2o)**: the harness removes its work dir and drops its database at exit, so `scripts/e2e/claude_projects/lib.sh` `cleanup` (installed by `install_traps`, i.e. every harness that sources it) calls `evidence_keep` WHILE THE SERVER IS STILL UP whenever the harness exits non-zero or an assertion failed (`E2E_EVIDENCE=always` also on a pass, `E2E_EVIDENCE=0` off). It writes `summary.txt` (exit status, failed assertions, every run that did not complete with its `failure_reason`, failure events, server-log errors), `server.log`, `notifications.jsonl`, `api/` (project, threads, Overview, runs and each thread's projection/transcript/task), `events.jsonl` (`claude_projects/event_store_dump.exs`: every event of the throwaway event store, decoded), `agent-sessions/` (pi's own session files), `run-artifacts/`, `worktrees/` + `worktrees.txt`, `repo-beads/`, `repo.bundle` (every ref of the scratch repository, bounded by `E2E_EVIDENCE_REPO_MAX_KB` = 204800: a completed thread's committed branch lives there once its worktree is gone), `environment.txt` (load, disk, memory, the other harness stacks alive, the database's connections and what `pi --list-models <model>`, the kickoff preflight's own question, answers then), `processes.txt` and `database.dump` (`pg_dump -Fc`) to `$E2E_EVIDENCE_DIR/<name>-<UTC start time>-<pid>/` (default `<checkout>/tmp/e2e-evidence`, git-ignored; `github_live_extras.sh` keeps its `tmp/gx-evidence`). Every part is best effort and says what it could not keep, and the capture runs in a subshell so it can never skip the teardown. `claude_projects_flow.sh`'s `wait_thread` stops waiting for a thread that has sat in `failed`/`cancelled` for `E2E_FAILED_GRACE` seconds (default 20) instead of `E2E_RUN_TIMEOUT`; `E2E_FIRST_THREAD_ONLY=1` runs setup and steps 1-3 only (about 30 s), the loop for an intermittent first-thread failure.
- **Live Claude + in-flight approvals harness**: `scripts/e2e/live_claude/` (`stack.sh up|restart|crash|stop|start|down`, `approvals_ui.mjs` Playwright driver, `events.exs`/`rpc.sh`, `fake-old-claude.sh` SIMULATED old CLI, claude workflows `claudeedit`/`claudeprompt`): a long-lived private stack with REAL claude (redirected `HOME` with the claude auth symlinks, `TMPDIR` under the scratch dir), driven step by step; evidence in `docs/acceptance/live-claude-and-approvals.md`. Live finding: Cowboy's 60 s `idle_timeout` (no data RECEIVED) used to kill a blocked in-flight prompt, so `AgentPermissionController` lifts the idle timeout of that stream. Orphaned in-flight requests (a restart, a run that ends with nobody waiting, a killed connection) are expired by `Approvals.Inflight` (reasons `server_restart` / `run_ended` / `client_gone`; a late decision is refused with `{:tool_call_expired, reason}`; the approvals DTO carries `reason` and `outcome`; foreman-u0646), and `Approvals.ClaudeCli` probes the claude CLI (`FOREMAN_CLAUDE_CLI`, else `claude`) for `--permission-prompt-tool` at launch so an old CLI falls back to the pause-and-re-run path instead of failing the phase (foreman-dc618; `claude --help` cannot tell, the flag is hidden from it). ## 20.3 Scheduled tasks (E11)

## 20.4 Project coordinator (Claude-Projects parity, E15)

- One event-sourced conversation per project, stream `coordinator:<project_id>` (`Aggregates.Coordinator`). Operator-allowed commands: `coordinator.message`, `coordinator.restart` (the one allowlist in `CommandGateway`, which `CommandController` reads; add the type to the controller's `aggregate_prefix/1`/`id_field_for/1` too); `coordinator.append`, `.turn.start`, `.action.record`, `.turn.complete`, `.turn.fail`, `.usage.record` are system-only and MUST stay off every operator allowlist. `Aggregates.Coordinator.apply_event/2` ends in a catch-all (an unknown event type must not crash replay). The read model is `Coordinator.Conversation`, folded in `ProjectionStore` (`coordinator_state/1`, `coordinator_conversation/2`, `coordinator_status/1`, `coordinator_pending_projects/0`); `seq` is assigned in the fold so a rebuild yields identical cursors. The page the CLI/HTTP/MCP read carries `status` AND `pending_messages` (trigger messages no completed turn consumed): `status` is `idle` between two turns while a message is still pending, so a waiting client (`foreman project chat`) must wait for `idle` and `pending_messages: 0`.
- `Coordinator.Runner` (subscribe FIRST, then scan `coordinator_pending_projects/0`, because `replay_existing: false` loses messages appended while down) wakes one `Coordinator.ProjectWorker` per project; `Coordinator.TurnRunner` runs context -> agent -> reply -> actions -> `turn.complete`. The turn id is `<first trigger message id>:a<attempt>`; the reply message id is `reply:<trigger message id>`; action ids are `sha256(project, trigger, action)` (`Coordinator.Action`), command ids derive from them: re-running an interrupted turn must be a no-op for effects already done. Never put a timestamp or random value in a coordinator command id. A turn task is LINKED to its `ProjectWorker` (which traps exits), so a worker crash ends its turn, and every turn registers `{:turn, project_id}` in the runtime registry, so a replacement worker answers `{:failed, :turn_in_flight}` and retries instead of running a second concurrent turn (E16 acceptance defect foreman-42t7a).
- The agent is behind `Coordinator.Agent` (`Agent.Harness` in production: provider agent via `DetachedRun`, `sandbox_mode: :read_only`, scratch cwd, pi with extensions/skills/MCP/session off; `Agent.Stub` in tests, driven by a per-test script process, never global env). Output contract = one fenced JSON block parsed by `Coordinator.ActionSource`; a bad block is `:malformed_output` and executes nothing (one repair retry in `Harness`). Unit/integration tests MUST NOT call a live provider.
- `Coordinator.Executor` is the single choke point for effects; every command goes through `Coordinator.Dispatch.system/2` whose `@command_types` is closed (no `merge_approve`, `run.pr.merge`, `project.archive`, `task.retry`, ...). Authority (`Coordinator.Authority`): an operator-authored message from a source not in `untrusted_sources` gives `:operator`; reports, agent and MCP messages give `:machine`, which `Coordinator.Policy` limits to answer/ask/propose_threads/route_followup/remember. Tuning (`Coordinator.Tuning`, settings `coordinator_propose_before_start|max_active_threads|reuse_threads`) is enforced in the Executor, not the prompt. Third-party text in prompts goes through `Coordinator.Untrusted.wrap/2`; stored text through `Coordinator.Redact`. `Coordinator.MemoryGuard` refuses merge/approve-automation notes. Do not add an action kind without a Policy decision, a recorded outcome and an adversarial test.
- `add_repo` and `schedule` are operator-grade actions. They need an operator turn AND the operator's own words (`quote`, verified by `Coordinator.Policy.quote_verified?/2` like loosening `set_tuning`); `Coordinator.Dispatch` then sends `project.repo.add` / `schedule.create` through `CommandGateway.dispatch_operator/1` (never `dispatch_system`), so the repository checks (realpath, git work tree, not a member, remote identity) and the schedule limits (interval floor, per-project cap, installed workflow, `at` stamped by the gateway) are exactly those of `foreman project repo add` / `foreman project schedule create`. Command ids are `coord:repo.add:<action id>` and `coord:schedule.create:<action id>` (the schedule id is the MCP `foreman_schedule_create` derivation with the action id as request id); a re-run of an `add_repo` already done answers `executed` with `already_registered`, and a schedule is created with `auto_approve: false` when the project's `propose_before_start` is on. The `schedule` action carries `spec` (interval or 5-field UTC cron), `prompt`, `workflow` or `task_type` (chosen by `WorkflowSelector`, like a thread) and an optional `name`.
- A thread the coordinator starts or proposes (and a `schedule`) must say how its workflow is chosen: `WorkflowSelector` takes an explicit installed `workflow`, else a `task_type` that `Catalog.type_to_workflow/1` maps, else `:no_workflow` (rejected, recorded and shown to the operator, nothing starts). The action schema marks both keys optional, so the contract lives in the prompt (`priv/coordinator/system_prompt.md`: `start_thread`/`propose_threads` say "workflow or task_type (at least one)", rule 6) and in the `# WORKFLOWS` section, where `Sources.Live.workflows/0` lists per workflow the task types that resolve to it (`[task_type: bug, chore]`, read from `Catalog.type_to_workflow_map/0`, the selector's own map). Without that the real coordinator left both keys out in about 8% of three-item pastes and all three threads were rejected (foreman-ig27o); `thread_workflow_contract_test.exs` pins the prompt and the source.
- Coordinator usage: the `TurnRunner` records the provider usage of every turn that ran a provider (also a turn that then fails) with `coordinator.usage.record` -> `CoordinatorUsageRecorded` (command id `coordinator:usage:<project>:<turn id>`, so a replay appends nothing twice). It is NOT `UsageRecorded`: that event is run-keyed and its fold creates a run projection. The fold feeds the shared usage ledger under role `coordinator` with `thread_id: nil`, so the usage rollup counts it in the total and the day/model/provider/role breakdowns but not in `by_thread`. Counts and cost stay nil-preserving (`Usage.from_run_result/1`, repair-retry attempts summed in `Agent.Harness`); an all-nil usage is not recorded. Each turn logs one `info` line when it starts (trigger ids with role/kind/source) and one when it completes (authority, reply bytes, action kinds with their status and reason), plus a `warning` when it fails or `turn.complete` is refused: that is what to read when a turn produced no threads.
- `Threads.Actions.follow_up/3` takes steer options (`message_id:` makes a repeated follow-up a no-op); the coordinator passes `coord-<action id>`.

## 21. Outbound messaging delivery

`ForemanServer.Notifier` (supervised, started by default; `config :foreman_server, :start_notifier?, false` stops it) is the production producer of `Messaging.notify/2`. It subscribes to projection events (no replay) and maps them through the table in `ForemanServer.Notifier.Mapping`: run (and legacy jobsite) failure and CI failing -> `failure`; run stall (`RunStallReported`, `RunFlaggedStuck`) -> `stall`; a blocked run (`RunBlocked`), a not-met review verdict, an agent question, an approval request/expiry, PR changes requested and exhausted PR fix attempts -> `action_needed`; run or jobsite completed, PR ready for review and any other review verdict -> `run_update`. Rows match by event name (`RunFailed`, `JobsiteFailed`, `RunStallReported`, `RunFlaggedStuck`, `RunBlocked`, `RunCompleted`, `JobsiteCompleted`, `ReviewRecorded`, `QuestionOpened`, `QuestionExpired`, `ToolCallRequested`, `ToolCallExpired`, `PrReady`, `PrChecksChanged`, `PrReviewChanged`, `PrFixExhausted`) and, for some rows, a payload `match`: `ReviewRecorded` on `verdict`, `PrReviewChanged` on `review_decision` `changes_requested`, and `PrChecksChanged` only when `checks_state` is `failing` AND `source` is `watch` AND `change` is `digest` (an observation forced for the approval gate carries `source: "gate"`, and an evidence-only change such as a passing check added, removed or re-run carries `change: "evidence"`; neither notifies, so one failing set is announced once; an event with no `source` or `change`, written before they existed, no longer maps); an event Foreman does not produce simply never matches. The PR row is `PrReady`, which every PR a run opens records (AutoPR, a stacked phase PR, another repository's PR, the Create PR button); `PrCreated` is only the button's audit fact and is deliberately unmapped, so one PR is announced once (foreman-ehz7l). `RunCancelled` and `JobsiteCancelled` are unmapped on purpose (an explicit stop), and the Notifier skips `JobsiteCompleted` for the jobsite of a PR fix thread (the PR's own events report that fix). Extend or override rows with `config :foreman_server, :notifier, rules: [%{event_type:, class:, severity:, level: :blocked | :progress, subject:, key_fields: [...], body_fields: [...], match: %{field => [values]}, url_field:}]` (configured rules win; a malformed rule raises at startup). Per project, the `notification_preference` setting (`every_turn`, `blocked_only` (default) or `off`) filters by level: `blocked_only` delivers only failures, stalls, blocked runs, needs-input, approvals, CI failing and review not met; `every_turn` also delivers progress rows and enables the `run_update` class for that notification; `off` delivers nothing. `run_update_rate_limit_ms` is enforced by the Notifier: at most one `run_update` per run per window (a run's PR ready and its completion share one). Replays collapse through the `dedupe_window_ms` check because the correlation id is a digest of the event type and the rule's `key_fields`. Notification events never carry a secret: the recipient is the label `default` and Slack/webhook destinations are resolved from config by the dispatcher (a Slack or webhook recipient is never used as the URL). A Slack webhook URL (env or any config) must be https, no userinfo, public host, no opt-out: `{:unsafe_url, :slack_destination, reason}` / `{:invalid_field, :slack_destination, :webhook_url}` at config resolve and again before each send (`Providers.Slack`). A third provider, `webhook: [url:, secret:, allow_insecure_http:, allow_private_hosts:]` (`url` literal or `{:system, "ENV"}`; https, no userinfo and no private host (loopback, link-local, RFC 1918, carrier-grade NAT, `localhost`) unless the matching `allow_*` opt-out is `true`; optional `secret` signs the body with HMAC-SHA256 in `x-foreman-signature`; every request carries `x-foreman-delivery: <notification id>`), POSTs a `foreman.notification.v1` JSON document. `ForemanServer.Messaging.WebhookUrl` judges the URL when the config resolves (`check/2`, no network; refusal `{:unsafe_url, :webhook_destination, :insecure_http | :userinfo | :private_host}`) and again before each send (`check_resolved/3`: a `{:system, "ENV"}` URL and every address a host name resolves to; an unsafe URL fails the delivery terminally, an unresolvable host retryably; no reason carries the URL). Env wiring: `FOREMAN_NOTIFY_WEBHOOK_URL`, plus `FOREMAN_NOTIFY_WEBHOOK_ALLOW_INSECURE_HTTP=true` and `FOREMAN_NOTIFY_WEBHOOK_ALLOW_PRIVATE_HOSTS=true` for an http or private-network receiver (a local http sink needs both). `Notifier.status/0` and `Notifier.stats/1` back the `notifier` row of `GET /api/doctor` (`foreman doctor`): off is `ok`; enabled with an invalid config, a stopped notifier or dispatcher, or refused events is `warn`. There is no desktop-push provider.

Keep outbound chat delivery behind `ForemanServer.Messaging`. Runtime/run/recovery/inbox code may enqueue provider-neutral notifications only; provider HTTP belongs in `ForemanServer.Messaging.Providers.*`. `ForemanServer.Messaging.Dispatcher` is supervised after `CommandRouter`. On boot it replays the event log and redelivers any enqueued notification that has no durable terminal outcome — a bare delivery-attempt event (crashed mid-send) or a retryable failure is redelivered, not treated as done; only a recorded success or a non-retryable failure is terminal. Within one dispatcher process lifetime, the first delivery attempt (from catch-up or a live projection event) claims the notification id for the rest of that process's life, so a notification enqueued during dispatcher startup cannot be delivered twice by both paths racing. A catch-up read failure or a projection-subscribe failure crashes the dispatcher under supervision rather than silently continuing without live/replay delivery. Redact provider URLs/tokens/errors before persistence/logging. Provider delivery failure is notification lifecycle state, not a recursive run failure trigger.


## 22. Project memory

A project keeps agent- and operator-written memory under `<project path>/.foreman/memory/` (`MEMORY.md` index plus one `<topic>.md` per topic). Content lives on disk, never in events: `ProjectMemoryWritten` / `ProjectMemoryForgotten` (stream `project_memory:<project_id>`, `Aggregates.ProjectMemory`) carry metadata only (name, description, sha256, bytes, redaction count, author). Always go through `ForemanServer.ProjectMemory` (`write/3`, `forget/3`, `list/1`, `read/2`, `index/1`, `verify/1`, `sync/2`); it takes a per-project lock, redacts (log-policy patterns plus `ProjectEnvironment.secrets/1`: every secret-store value and the values of secret-named env vars) before the disk write, enforces caps (`config :foreman_server, :project_memory`: 64 KiB topic, 200 topics, index 200 lines / 25 KiB), rejects log/env dumps (`:content_not_durable`, thresholds in the same config) and rolls the file back if the audit command is rejected. `ForemanServer.ProjectMemory.Store` is the filesystem layer and has no CQRS knowledge; `project.memory.write|forget` are system-dispatched only and must NEVER be added to `@allowed_operator_types` / the operator allowlist. `ForemanServer.ForemanDir.ensure_ignored/2` appends `memory/` to `.foreman/.gitignore`; only content paths are ever ignored (`.foreman/Dockerfile`, `bead.exs`, `pi-models.json` stay tracked). MCP: `foreman_project_memory_list|read` (read-only) and `foreman_project_memory_write|forget` (in `MCP.Policy.@write_tools`); their descriptions come from `ProjectMemory.Guidance`, whose `text/0` is the block E3 injects. Operator surfaces: `/api/projects/:id/memory[/:name|/sync]` (`ProjectMemoryController`) and `foreman project memory list|read|write|forget|sync`. The audit command ids carry a unique suffix on purpose: event ids derive from `command_id`, so a content-only id would silently drop a later A -> B -> A rewrite.

## 23. Standing context injection

`ForemanServer.ProjectContext.build/2` is the ONLY producer of standing project context (instructions, repositories, provider sections such as `ProjectContext.Memory`); never assemble it elsewhere. Config `:foreman_server, :project_context` (`max_chars`, `section_caps`, `section_providers`); every cap and the total budget count CHARACTERS (`String.length/1`), the unit of the settings limits, so instructions the validator accepted (16000 characters) are never cut for being multibyte. It returns a `%ProjectContext.Bundle{}` (`system_text` nil when empty, `sections`, `truncated`, `bytes`, `sha256`, `redactions`); truncation is visible inside the text (`[truncated: N lines omitted from ...]`), caps cut at line/character boundaries (`truncated[].omitted_bytes` and `bytes` stay byte counts of what was cut and of the final text), and a section `trailer` always follows a cut body so delimited blocks stay closed. Memory is agent-written, so it renders inside `<project_notes>` labelled informational, never as instructions. `ProjectContext.deliver/3` decides delivery by provider capability: `system_prompt` where the adapter declares it, else prefixed to the prompt. Workflow door: `RunExecutor.build_agent_launch` builds per launch and `append_system_prompt/2` merges with (never overwrites) the command-phase inbox prompt (context first); `prompt_template_assigns/4` exposes `project_context` / `project_instructions` / `project_memory`. Follow-up runs build it the same way as any run (`Engine` passes `system_prompt` in `runner_opts`, `AgentRunner` puts it into the `RunRequest`). `Review.Capture.put_project_context/2` and `put_run_project_context/2` archive `project-context.md` plus a manifest `project_context` block (first launch only). Read-only inspection: `GET /api/projects/:id/context`, `foreman project context`.

The `Repositories` section carries the project checkout's path as ORIENTATION ONLY (foreman-2onq1): its line says it is the main checkout, that every thread works in its OWN git worktree (its current working directory) and that nothing is to be written under the path or put into a worker's prompt. Handed over bare (`- primary: <path>`), the coordinator copied it into a worker's brief (`Repository: <path>` ... "at the repository root") and the worker obeyed it: it wrote its file into the main checkout, the run's branch came out empty and step 5b of the live flow failed (1 of 20 runs). `priv/coordinator/system_prompt.md` rule 13 tells the coordinator never to put the checkout's absolute path in a thread's `prompt` (paths inside pasted data, such as a stack trace, stay verbatim; `ProjectContextTest` and `ThreadWorkflowContractTest` pin both texts). This is prompt-level only: nothing deterministic stops an agent that writes into the main checkout anyway.

## 24. PR watching and bounded auto-fix (E9)

`ForemanServer.PrWatcher` (config `:pr_watcher`, `enabled: false` or `FOREMAN_PR_WATCHER_ENABLED=false` stops it) folds observed PR state into the run's `pr_watch` projection through typed events `PrChecksChanged`, `PrReviewChanged`, `PrFixRequested`, `PrFixStarted`, `PrFixFinished`, `PrFixExhausted`, `PrCreated`, `PrWatchStarted`, `PrWatchStopped` (commands `run.pr.checks|review|fix_ci|address_comments|resolve_conflicts|fix_started|fix_finished|fix_exhausted|create|watch_stop|watch_start`). Polling is the separate opt-in `ForemanServer.PrMonitor` (`FOREMAN_PR_MONITOR_ENABLED=true`; pending checks 30 s, recent change 60 s, stable `:pr_monitor_interval_ms` 5 min, idle >24 h 15 min, +/-10% jitter); GitHub webhooks only make a PR current early: `check_run`/`check_suite` (`completed`, `rerequested`), `pull_request_review`, `pull_request_review_comment`, `pull_request_review_thread`, PR `issue_comment` and `pull_request` `synchronize|ready_for_review|converted_to_draft` ask `PrWatcher` to re-read it, while a `pull_request` `closed|reopened` (or any other action on a conflicted PR) appends `PrUpdated` itself. A fix (`ForemanServer.PrFix.plan/4`) is a FOLLOW-UP RUN (`run.followup.request`, see §27) attached to the PR head branch, pushing only that branch with a plain fast-forward-only `git push` (never force); `PrFixStarted.fix_run_id` names the run (`jobsite_id` only on a fix started before the door was retired). PR text and CI logs are untrusted and fenced in the prompt. The loop guard lives in the Run aggregate (`Aggregates.Run.PrWatch`): one fix in flight per PR, hard cap 5 attempts per kind, a fix that changed nothing on the same head is `no_progress`, optional cooldown; a fix that cannot start or whose start task crashes is finished as `failed` (`PrFixFinished.error_code`: the typed start error, `start_crashed`, or `lost_on_restart` for a request a restart found without a run), never left in flight; automatic fixes (`pr_auto_fix` project setting, `PrWatcher.AutoFix`) are off until a project opts in. **Merge stays operator-only**: `merge_approve`/`run.pr.merge` are not in `PrWatch.operator_types/0` and no MCP tool, reactor or auto-fix path can merge or approve. The one thing a PR observation does to the gate is make it stricter: a head it records that differs from an approved PR's pin voids the approval (`CommandGateway` sends the system-only `run.pr.rehold`; see "Merge gate per PR" and "Head-pinned approval"). Surfaces: `GET /api/runs/:id/prs`, MCP `foreman_pr_status` (read) and `foreman_pr_fix`/`foreman_pr_watch_stop` (writes), CLI `foreman run prs|fix-ci|address-comments|resolve-conflicts|create-pr|watch-stop|watch-start`. Live webhook delivery, force-push handling, check re-run, conflict resolution and unresolved-thread reads are UNVERIFIED against real GitHub (spike S4). **Multi-repo (E12-S7)**: a PR is addressed as `{run_id, repo_id}`: `ProjectionStore.run_ids_for_pr_url/1` returns `[{run_id, repo_id}]` (primary included), `PrUpdate.command/4` / `PrObservation.commands/5` and the watch lifecycle commands carry `repo_id` only for a non-primary repository (absent == the run's primary), the watch fold never erases a recorded `repo_id`, and `PrFix.plan/4` attaches the PR's own repository path and worktree only. A merged/closed PR of repo b never touches repo a's record or gate.
`PrWatch` also records per-check evidence (Phase 1 PR 3). `run.pr.checks` carries every check of the head GitHub reported (`checks`, at most 100, newest kept: `name`, `kind`, `state`, `conclusion`, `workflow`, `started_at`, `completed_at`), `checks_truncated`, `evidence_digest` (moves when a passing check is added, removed or re-run, or when the policy version changes; the notification `digest` does not), `observation_ref` (a forced observation's nonce), `required`/`policy_version` (the project's `required_checks` and `PrEvidence.policy_version/1` of them as `PrWatcher.Observer.observation_policy/2` read them from the projection on that observation, Phase 1 PR 4; both nil when the gate is off or the policy could not be read, which is logged `required_checks policy unreadable`: a warning for an unknown project, an error otherwise), `source` (`watch` observer, `gate` forced observation) and `change` (`digest` or `evidence`, see the Notifier row). A policy change with no new check therefore emits one evidence-only `run.pr.checks` (`PrObservation.commands/6` takes `policy: %{required, version} | nil`). `ForemanServer.PrEvidence` folds these, `PrEvidenceWaived` and `PrReadyFailed` into an `evidence` sub-record (`checks`, `waiver`, `delivery_issue`, `findings`, `risk`, `report`; `findings` is written by `run.pr.findings`, `risk` by `run.pr.risk` and `report` by `run.pr.comment_published`, all below) on the `PrWatch` aggregate and on the `pr_watch` projection, through ONE fold both call first. The sub-record itself is not on the wire, but since Phase 1 PR 8 `PrWatch.DTO` derives `eligibility`, `checks`, `findings`, `risk`, `waiver`, `report`, `delivery_issue` and `next_actions` from it, so `GET /api/runs/:id/prs`, `foreman run prs` and `foreman_pr_status` show them (see "Phase 1 PR 8" below). A head move (`PrUpdated`, `PrReady`, `PrChecksChanged`, `PrReviewChanged` with another `head_sha`) resets the current-head observation (`checks_state`, `checks_digest`, `review_decision`, `review_digest`, `failing`) and voids a waiver for another head; the evidence records keep the head they were recorded for, and `PrObservation.commands/6` then re-records an unchanged review in the same batch. `PrObservation.commands/6` takes `force: %{nonce:, now_ms:}` (a forced observation: always one `run.pr.checks` with `source: "gate"`, no review command; anything else is `{:error, {:invalid_force, term}}`); since Phase 1 PR 8 `CommandGateway` uses it at every gated `merge_approve`. `PrEvidenceWaived` is emitted only by the operator command `run.pr.waive_evidence` (below). `GitHub.PrStatus` refuses a check run or status context with a blank name, and a `COMPLETED` check run without a valid `completedAt` (the zero date means not completed), as a typed payload error, never a default. Read from the source and tests; none of it is observed against a live PR.

- **Typed review findings and their record (Phase 1 PR 5).** `Workflow.ReviewFindings` is typed: `read/1` -> `{:recorded, %Record{findings, artifact_sha256}}` | `:absent` | `{:malformed, reason}` | `{:error, {:unreadable, posix}}`, plus `parse/1`, `defect/1`, `unresolved/1` and `pr_section/2` (`extract/1`, `extract_from/1` and `unterminated_section/1` are gone). The block between `<!-- FOREMAN_REVIEW_FINDINGS_START -->` and `..._END -->` is JSON of schema `foreman.review_findings/1` (`schema`, `reviewed` = true, `findings`; a finding has `severity` critical|major|minor|nitpick, `path`, `line` (positive integer <= 1e9, or null), `description`, `disposition` fixed|declined|open, `source`); exactly one start/end pair counts (fences, indentation, blockquote markers and CRLF are handled). Malformed reasons: `unterminated_block`, `multiple_blocks`, `legacy_format` (the old bullet format), `invalid_json`, `unknown_schema`, `invalid_field` (control characters, duplicate JSON keys), `too_large` (block > 32768 bytes, file > 4 MiB), `too_many_findings` (> 100). - **The setting.** `required_checks` is a project setting (`Aggregates.Project.Settings`, `ProjectSettings.required_checks`, `foreman project update --required-checks <json>`, printed by `foreman project settings`). `nil` (the default; `--clear required_checks`) is the gate off, `[]` the gate on with no checks, otherwise a list of at most 20 entries `name` (1..200 characters, no control characters), `kind` (`check_run` or `status_context`), `workflow` (`check_run` only) and `allow_skipped` (`check_run` only, `true` or the default `false`, which is dropped). An entry with an unknown key, a bad value or two `allow_skipped` values for one name/kind/workflow is a typed `{:required_checks_*, ...}` error; exact duplicates collapse and the list is stored sorted. It is operator-only: MCP `foreman_project_settings_update` answers `Unknown arguments: required_checks` and a `clear` naming it is a `ToolError` `operator_only_setting`; the coordinator's `project.update` that sets or clears it is refused `{:forbidden_setting, :required_checks}` (`Coordinator.Dispatch.forbidden_setting?/1`).
- **The durable-store guard.** `CommandGateway.require_durable_store_for_gate/1` refuses a `project.update` or `project.register` (operator or `dispatch_system/2`) whose payload SETS `required_checks` (`[]` included; `Settings.changed_keys/1` says `:set`) with `{:error, {:store_not_durable, note}}` while `KeyStore.require_durable/0` does (`:require_durable_store_for_gating` on and the store not durable; HTTP 422 from `CommandController`), before anything is appended. Clearing it or touching other settings is never refused. `require_durable/0` is total: a switch that is not a boolean is read as on, never as off and never a raise, and the refusal note names the bad value.
- **The evaluator.** `PrEvidence.evaluate/2` is pure (`(record, %{head_sha, policy, now_ms, checks_ref})`) and returns `%Eligibility{head_sha, status, reasons, waived, waiver, policy_version, inputs, evaluated_at}`: `status` is `off` (no policy), `eligible`, `ineligible`, `waived` (every reason is waivable and covered by an applying waiver) or `unknown` (the checks record cannot be read: the reason `evidence_unreadable`; an unreadable or unrecognised risk LEVEL is NOT `unknown`: `level_reasons/1` gives `ineligible` with the never-waivable reason `evidence_unreadable`, and only `LOW` and `MEDIUM` pass). ## 25. Project library

A project's library is a read-only file store every agent of the project can use (Claude "Project knowledge" parity), at `<project primary repo>/.foreman/library/<entry_id>/{entry.json,files/...}`. ONLY `library/` is gitignored (`ForemanDir.ensure_ignored(path, "library/")`); `.foreman/Dockerfile`, `bead.exs` and `pi-models.json` stay tracked, and `Library.StoreTest` pins that with `git check-ignore`. Bytes live on disk, never in events: `ProjectLibraryAdded` / `Replaced` / `Removed` (stream `project_library:<project_id>`, `Aggregates.ProjectLibrary`) carry metadata only (entry id, name, kind, counts, manifest digest, source, skipped summary, author). Always go through `ForemanServer.Library` (`add/4`, `replace/5`, `remove/3`, `list/1`, `get/2`, `read/3`, `index/1`, `env/1`, `delivery/2`, `register_produced/4`); it takes a per-project `:global` lock, plans with `Library.Ingest`, writes to disk with `Library.Store` (staging dir + rename swap, files 0444 / dirs 0555, streamed sha256), then dispatches the system command (not on the operator allowlist, like memory); a rejected command rolls the disk back. Replace/remove need a unique `command_id` (the event id derives from it, so a deterministic one drops an A -> B -> A rewrite). Limits mirror Claude and live in `config :foreman_server, :library`: at most 100 files per add, 480 MB per file, 512 MiB per add in total (`upload_max_bytes`: one request, 413 `upload_too_large` beyond it, reported in the `limits` of the list response; the CLI refuses a larger plan locally); a folder takes the first 100 files within 200 MB (sorted, depth-first), skipping hidden files, `node_modules`, symlinks and files over 30 MB; at most 10 `folder` entries per project (aggregate guard `{:too_many_folders, 10}`); every skipped file is reported back with a reason. Delivery: `FOREMAN_LIBRARY_PATH` is set only when the library is non-empty — the absolute host directory on the workflow door and the host sandbox, a read-only bind mount at `/library` for docker runs (`Library.delivery/2`; nothing is copied or linked into the worktree because Foreman commits the whole worktree); the index is the `ProjectContext.Library` section provider. Thread-produced files (`PhaseCompleted` artifacts and the session archive's `analysis.md` / `diff.patch`) are registered by `Library.Collector` into one `produced-<run_id>` entry (kind `produced`, exempt from the folder cap, idempotent per run/path/sha256, bounded by `produced_max_files_per_run` / `produced_max_bytes_per_run`, containment-checked against the run's directories) ONLY when the project setting `library_collect_produced` is true. Surfaces: HTTP `ProjectLibraryController` (multipart upload with a raised, route-scoped body limit via `Plugs.LibraryUploadParser`; `server_path` adds need `allow_server_paths: true`; every API write is audited with author `operator`/`api` because the API has one shared bearer token: the caller-supplied `x-foreman-operator` header is not an identity and is ignored here), read-only MCP tools (`MCP.LibraryTools`: no add/remove tool for agents) and `foreman project library list|add|replace|remove`.

## 27. Follow-up runs and the retired jobsite door

The separate "jobsite" dispatch path (`/api/jobsites`, `foreman jobsite`, `Jobsite.Executor`) is retired
(plan and decisions: `docs/plans/retire-jobsites.md`). Its worthwhile capabilities live in runs:

- **Follow-up run** (`run.followup.request`, SYSTEM-ONLY, never on an operator allowlist): a task-less run attached
  to an existing branch (a PR's head), producing `RunFollowUpRequested` on `run_followup:<run_id>`
  (`Aggregates.RunFollowUp`; kind `pr_fix` only). The Dispatcher reads the request back from the projection
  (`ProjectionStore.followup_request/1`) and admits it through `RunAdmission.start/2` (the only run-start entry), so
  slots, project limits, daily cap and paused/archived refusals apply and a fix can queue behind full slots.
  `Workflow.FollowUp` builds the one-phase `fix` snapshot (`provider_tracked: false`: no task, no Bead, no
  `task.execution_*`); `Workflow.AttachBranch` fetches the remote branch, creates or fast-forwards the local one
  (never discarding a commit; refuses unpushed local commits, a dirty holder and the main worktree) and reuses the
  linked worktree already holding it (so a cwd-keyed provider session resumes) or creates one; the run publishes with
  a plain push of that one branch and opens no PR. `config :foreman_server, :followup_runs, enabled:` is a kill switch
  (default on). `RunFollowUpRequested`/`PrFixStarted.fix_run_id` are new event keys: after the first one is recorded,
  rolling back to a build without them is NOT safe (`EventCodec` rejects unknown keys); new keys must stay optional.
- **Session resume**: `RunExecutor` start option `resume_session: {provider, id}` makes the first phase an in-place
  harness resume (validated by `ForkSession`, provider must match, never a blank agent, exclusive with a fork).
- **Sandbox**: a workflow-level `sandbox: docker` (Interpreter, snapshot digest, strict approval render) runs every
  phase's agent through the docker sandbox shim (`Lowering` sandbox/release steps, `Runners.Overwatch` `cli_path`) with
  the project network policy; single-repo runs only; in-flight approvals are skipped for a sandboxed run. A PR fix
  runs in Docker by default (`config :pr_fix, sandbox:`), `host` needs `allow_host_sandbox`
  (`FOREMAN_PR_FIX_ALLOW_HOST_SANDBOX`, formerly `FOREMAN_JOBSITES_ALLOW_HOST_SANDBOX`).
- **Kept for history**: the `jobsite:<id>` streams, `Events.Jobsite*`, `Aggregates.Jobsite` fold and projections
  stay readable forever (no event is rewritten); `Exec.BootRecovery` fails every open jobsite at boot with code
  `jobsite_retired` (worktrees and branches stay on disk). Threads of that door answer `:jobsite_retired` (HTTP 410).
  The execution substrate (`Exec.Engine`, `Program`, `Runners.*`, `Sandboxes.*`, `Git`, `Worktree`,
  `NetworkPolicy`, `HostCommand`) is what workflow runs execute on and stays.
- **Dropped on purpose**: remote spec API and templates, prompt-to-template, `merge_into`, the iteration loop
  (`completion_signal`), `foreman_client`, the jobsite skill, `FOREMAN_JOBSITES_*`.
- **Not verified live**: a follow-up run executing a real agent and pushing, and the sandboxed-run paths against
  real Docker; the live PR-fix acceptance (`docs/acceptance/live-claude-prfix-resume.md`) must be re-run on runs.

**Namespace note (PR 9).** The execution substrate formerly named `ForemanServer.Jobsite.*` is now
`ForemanServer.Exec.*` (`Exec.Engine`, `Program`, `Step`, `Runners.*`, `Sandboxes.*`, `Git`, `Worktree`,
`NetworkPolicy`, `HostCommand`, `BootRecovery`). Persisted strings (`agent.provider`, sandbox provider names such as
`"docker"`) and telemetry event names were NOT renamed, and neither were the legacy `Events.Jobsite*` structs,
`Aggregates.Jobsite` and the `jobsite:` streams: they are the history the retirement keeps.
